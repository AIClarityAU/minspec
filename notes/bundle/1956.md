+# DR-092: One-hour broker tokens, and what actually bounds the exposure
+
+> **Born `proposed` per DR-029** — acceptance is a separate human act
+> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
+> field, not this note.
+
+## Context
+
+SPEC-034's broker exchanges a GitHub Actions OIDC token for a GitHub App installation
+token, so an adopter's CI can post as `minspec-sdd[bot]` without holding the App private
+key. DR-054's reasoning is that one leaked App key mints tokens for every repository that
+ever installed the App, so the blast radius of the key dwarfs the blast radius of any one
+token. Short token lifetime was the compensating control.
+
+FR-3 asked for "a TTL no longer than needed (target <=10 min; GitHub's ceiling is 1h)".
+AC-3 restated that as "expires within the target TTL (<=10 min)", and `mint.ts`
+implemented it as a hard refusal above 600 seconds.
+
+**The <=10 min half is not obtainable.** `POST /app/installations/{id}/access_tokens`
+accepts exactly three body parameters - `repositories`, `repository_ids`, `permissions` -
+and no lifetime field; the documentation states installation tokens "expire one hour from
+the time you create them". There is no shorter credential to request.
+
+So the implemented ceiling sat below the platform's floor. That is not a strict gate, it
+is an off switch: the broker rejected 100% of real mints. Nothing caught it because no
+test can mint a real token, and the single test covering the bound asserted *refusal* of a
+60-minute token - it encoded the defect as the expected behaviour.
+
+## Decision
+
+1. **`MAX_TTL_SECONDS` is 3600**, GitHub's documented lifetime, and AC-3 is corrected to
+   match FR-3's honest reading rather than the other way around.
+
+2. **The ceiling is retained rather than removed.** It no longer shortens anything, but it
+   still fails closed if a future API change or a misconfigured factory returns something
+   longer than the platform documents.
+
+3. **A five-minute skew grace sits above the ceiling.** GitHub stamps `expires_at` on
+   GitHub's clock; the Worker compares against Cloudflare's. A bound of exactly 3600
+   refuses a legitimate token whenever the Worker's clock is behind by more than the mint
+   round-trip. That would re-create the off switch *intermittently and only under drift* -
+   strictly worse than the original, because it would be unreproducible.
+
+4. **Exposure is bounded by handling, not by lifetime.** The accepted controls are: the
+   token is scoped to exactly one repository; it carries only the `review` profile and a
+   wider grant is refused; it is never written to disk, never logged, and never cached
+   (`no-store` on every response); and it is used immediately by the run that requested it.
+
+## Accepted risk, stated plainly
+
+**A broker-minted token is usable for up to an hour after the workflow that requested it
+finishes.** If one leaks - from a workflow log, a compromised runner, a malicious action in
+the same job - an attacker has the remainder of that hour to apply `ai-review:*` labels,
+post review comments, set check-runs and set commit statuses on that one repository.
+
+That is materially more than the ten minutes SPEC-034 assumed, and it cannot be reduced by
+configuration. It is accepted because the alternative is not a shorter token but no broker
+at all, and the fallback to "no broker" is every adopter holding the App private key -
+which is the catastrophic case DR-054 exists to prevent. **An hour of one repository's
+review scope is a far smaller exposure than a shared key with unlimited lifetime over
+every installation.**
+
+## Alternatives rejected (DR-086 §4)
+
+- **Keep 600 and advertise a 10-minute `expires_at` while the real token lives an hour.**
+  Rejected: the response would understate the credential's true scope, which is the exact
+  defect #1818's review blocked in `mint.ts` (a stated safeguard that does not exist). It
+  also makes the signpost lie, which this product cannot afford.
+- **Drop the ceiling entirely** since it no longer constrains anything. Rejected: it is the
+  only thing that would catch an API change handing back a longer credential, and it costs
+  one comparison.
+- **Proxy every review write through the Worker** so no token reaches CI at all. This
+  genuinely removes the exposure and is the strongest option. Rejected for now as a much
+  larger design - the Worker becomes a stateful API surface for labels, comments,
+  check-runs and statuses, and it inherits the availability requirement of the review gate
+  itself (NFR-3). Worth revisiting if token leakage is ever observed rather than theorised.
+- **Have the broker revoke the token when the run ends.** `DELETE /installation/token`
+  exists, so this is feasible and would cut the window to the run's duration. Rejected as
+  out of scope for slice 1 rather than on the merits: it needs a workflow `always()` step
+  and a revocation endpoint, and a revocation that silently fails would leave the
+  full-hour exposure while reading as mitigated. **This is the option most likely to be
+  right later** - recorded here so it is not re-derived from scratch.
+
+## Consequences
+
+- AC-3, `design.md` §API, the sequence diagram, and task 1.3's restatement are corrected in
+  place with reasoning, not silently edited.
+- NFR-4's pre-GA security review (task 6.2) should treat the one-hour window as a stated
+  input rather than discovering it.
+- Task 5.2's content-free audit record gains a reason to exist beyond compliance: with a
+  one-hour token, the audit trail is what distinguishes legitimate use from post-run use.
+
+## Follow-ups (tracked)
+
+- **Token revocation at run end** - the narrowest real reduction of the accepted risk.
+  Filed as a follow-up to this record rather than left as prose.
+- #1963 - the broker's `not_implemented` error code covers three unrelated conditions.
