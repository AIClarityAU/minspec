**Tier: T4 (complete ceremony).** The end state routes the credential that writes this
repo's required `ai-review` check through a vendor service. A defect there either blocks every
merge or forges a pass, and the workflow it changes ships byte-for-byte to every adopter.

## One-Sentence Scope

Exercise SPEC-034's broker on this repository in two stages: first a shadow probe that mints,
checks and revokes a broker token without touching the merge gate, then an operator-selected
broker arm of `ai-review.yml`. The direct key-as-secret path stays available as a manual,
never automatic, fallback.

## Context - what the code does today (read from this worktree's base, not inferred)

1. **This repo only takes the direct path, and the broker branch could never run here.**
   `ai-review.yml` refuses to run unless `MINSPEC_APP_ID` and `MINSPEC_APP_PRIVATE_KEY` are
   both set (`.github/workflows/ai-review.yml:204-217`). It then mints with
   `actions/create-github-app-token` from those secrets (`:221-227`). SPEC-034 OQ-4 (the
   override selection rule) picks the native path whenever a customer app-id secret is
   configured, so under that rule the broker arm can never execute in this repo. SPEC-034's
   own tasks already record this: task 1.4b, item (ii) (`specs/minspec/SPEC-034-oidc-review-broker/tasks.md:35`). **This is the
   central obstacle #697 has to resolve.** A spec that just says "point ai-review.yml at the
   broker" cannot be built as SPEC-034 currently specifies the selection.
2. **The same App identity sits on both arms.** The broker mints for App `4212099`
   (`packages/broker/wrangler.toml`, `MINSPEC_APP_ID`). The `main` ruleset pins the required
   `ai-review` check to integration 4212099 (DR-103, lines 241-245, measured 2026-10-06). So a
   broker-minted token satisfies the integration pin and the `AI_REVIEW_BOT_LOGINS` allowlist
   unchanged. It also means **`sender` cannot tell the two arms apart**: comparing them needs
   an explicit token-source marker (FR-13).
3. **The repo key is load-bearing beyond ai-review.** `approve-on-label.yml:146-148` and
   `main-red-watch.yml:54-56` also mint from `MINSPEC_APP_PRIVATE_KEY`. Moving ai-review to
   the broker therefore does **not** remove the private key from this repo, so the dogfood
   cannot demonstrate SPEC-034 FR-5's custody property here (see DQ-3).
4. **`ai-review.yml` ships to every adopter.** `packages/minspec/src/lib/ci-review-templates.ts`
   embeds it byte-exact (`AI_REVIEW_WORKFLOW`, line 35), and the `ci-stack-portability` test
   holds the copy equal to the file. Any edit made for this repo's dogfood reaches every
   MinSpec-initialized repo on its next harness refresh. Constitution invariant 3 (blast radius
   is the opted-in project) therefore bites on the live-gate stage, not on a repo-local probe.
5. **The broker is not deployed.** Wrangler login against the pinned account is a human step
   (#1869 broker deploy credential). SPEC-034 tasks still open include slices 2-5 (fail-closed
   workflow, provenance closure, GH-native approval, override, zero-config default and audit)
   and ops gates 6.1-6.3 (SLO, independent security review, privacy policy).
6. **The broker authorises on the `repository` claim only** (`packages/broker/src/decide.ts:98-108`).
   It does not check `ref`, `event_name` or `job_workflow_ref`. Any workflow run in this repo
   that can request an OIDC token can therefore mint a review token. Today, any workflow run
   that can read repo secrets can already mint one through the direct path, so this is
   equivalent exposure, not new exposure. It is the reason FR-4 keeps PR-triggered runs off
   the shadow probe.
7. **Broker tokens live one hour and are not revoked.** DR-094 records that GitHub issues no
   shorter installation token and bounds exposure by immediate use and non-storage. The
   direct arm's `create-github-app-token` action revokes its token in its post step by
   default. I believe it does so at the pinned v1.9.0, from the action's documented default;
   I have not verified that in this repo. A broker arm that skips revocation would be
   *weaker* than the arm it replaces (FR-7, FR-14).

## Functional Requirements

### Shadow stage - a repo-local probe, no change to the merge gate

- **FR-1 - Separate, unshipped workflow.** The shadow probe MUST live in its own workflow
  file. That file is not registered in `ci-review-templates.ts`, `template-registry.ts` or any
  other harness-generation source. No adopter repo ever receives it (constitution invariant 3).
- **FR-2 - Never a required check.** The probe MUST NOT be added to the `main` ruleset's
  required checks. It must not write `ai-review:*` labels, the `ai-review` check-run, the
  `ai-review/pass` status, or `ready-to-merge`. A broker outage during the shadow stage must
  not block any merge.
- **FR-3 - Least privilege.** Only the probe job holds `id-token: write`. The workflow-level
  `GITHUB_TOKEN` permission stays `contents: read`. The OIDC token is requested with the
  audience the broker pins (`BROKER_AUDIENCE`, currently `https://broker.minspec.dev`).
- **FR-4 - Trusted triggers only.** The probe runs on `schedule`, `push` to `main` and
  `workflow_dispatch`. It MUST NOT run on `pull_request` or `pull_request_target`, so a PR
  cannot edit the probe and run the edited version with a freshly minted bot token. This keeps
  the shadow stage from adding a per-PR, head-executed token path (Context item 6).
- **FR-5 - Broker endpoint is a literal.** The broker URL and audience MUST be literals in the
  workflow file. They must never be read from `vars`, `secrets`, `inputs`, an environment
  file or PR content. A configurable URL would let anyone who can change it redirect a live,
  audience-bound OIDC JWT to a host they control. That host could then replay the JWT to the
  real broker within its lifetime and mint a review token for this repo. The same rule binds
  the live-gate arm (FR-11).
- **FR-6 - Check what was minted (SPEC-034 AC-3 observed live).** On a 200 response, the probe
  MUST assert the following, failing the job on any mismatch:
  - `repositories` is exactly `["AIClarityAU/minspec"]`.
  - `permissions` equals the `review` profile exactly: issues, pull_requests, checks and
    statuses at write, nothing else.
  - `expires_at` is in the future and no more than 1h away.
  - The token actually works and is scoped as declared: `GET /installation/repositories`
    lists exactly this repository.
- **FR-7 - Revoke, always.** The probe MUST revoke the minted token (`DELETE
  /installation/token`) in a step that runs `if: always()` after any step that held it. It
  must treat a failed revocation as a job failure, not swallow it (constitution invariant 2).
  The token MUST NOT be written to a file, cache, artifact, job output or log. It is passed
  between steps only as a masked value.
- **FR-8 - Refusal is observed, not assumed (SPEC-034 AC-1, AC-2 live).** A
  `workflow_dispatch` input MUST select a refusal probe that sends a request the broker must
  reject. At minimum, a body `repository` that disagrees with the OIDC claim must get 403
  `repo_claim_mismatch`. The probe passes only if the broker refuses **and** returns no
  `token` field. A 200 on a refusal probe fails the job loudly. The token is revoked anyway
  if one came back.

### Live-gate stage - the broker arm of `ai-review.yml` (lands with SPEC-034 task 1.4b)

- **FR-9 - Explicit selector that outranks secret presence.** `ai-review.yml` MUST choose its
  token source from a single repo variable (name fixed in Plan; `AI_REVIEW_TOKEN_SOURCE` below):
  - `broker`: the broker arm, **even when** `MINSPEC_APP_ID` / `MINSPEC_APP_PRIVATE_KEY` are
    set.
  - `app`: the direct `create-github-app-token` arm.
  - Unset: exactly SPEC-034 OQ-4's rule, unchanged.

  This is what makes the broker arm reachable in a repo that also holds the key (Context
  item 1).
- **FR-10 - Adopters unchanged by default.** With the selector unset, the shipped
  `ai-review.yml` MUST behave identically to today for every adopter: same arm, same skip
  notice, same labels and checks. The dogfood MUST NOT be the change that flips adopters to
  the broker; that flip is SPEC-034 FR-11's (zero-config default) and is decided there.
- **FR-11 - Literal endpoint.** As FR-5. The selector chooses *whether* to call the broker,
  never *which* host to call.
- **FR-12 - No automatic cross-arm fallback.** When the selector says `broker` and the broker
  refuses, is unreachable, rate-limits or errors, the run MUST fail closed exactly as SPEC-034
  FR-9 / AC-9 requires: no token, no `ai-review:pass`, `ready-to-merge` red. The run surfaces
  "reviewer identity unavailable (broker)" visibly. It MUST NOT silently retry through the
  direct key. Returning to the direct arm is an operator act: set the selector to `app` and
  re-run. The issue's "keep the direct path as the fallback/comparison" is met by keeping
  that arm one variable away, not by wiring it in behind the broker (DQ-2).
- **FR-13 - Token source is recorded.** Every verdict comment and the `ai-review` check-run
  output MUST name the token source used (`broker` or `app`). Because both arms post as the
  same App (Context item 2), this is the only way to tell from the PR timeline which path
  produced a verdict. It is what makes the comparison #697 asks for possible.
- **FR-14 - Revoke on the broker arm.** As FR-7, applied to the token the broker arm holds in
  `ai-review.yml`. This is needed so the broker arm is not weaker than the direct arm it
  replaces.
- **FR-15 - `id-token: write` arrives with the feature, not ahead of it.** The permission is
  granted at job scope on the job that calls the broker. It lands in the same change as the
  broker arm, which ships to adopters (Context item 4). It MUST NOT be added in an earlier,
  standalone change (DQ-4).
- **FR-16 - Guard untouched.** `.github/scripts/ai-review-guard.js`, `AI_REVIEW_BOT_LOGINS`
  handling and the ruleset's integration pin are unchanged. The broker arm feeds the existing
  guard a token from the same App (SPEC-034 FR-8).

### Operational preconditions (not code, but blocking - each is a human act)

- **FR-17 - Order of enablement.** Each step needs the one before it to have been observed,
  not just declared:
  1. Deploy the broker (#1869).
  2. Run the shadow probe green on `main`, plus one refusal probe (FR-8).
  3. Clear SPEC-034 ops gate 6.2 (independent security review and key-rotation runbook).
     That review is required before any repo authenticates through the broker, this one
     included.
  4. Land the live-gate stage.
  5. Set the selector to `broker` on this repo.

## Acceptance Criteria

- **AC-1 (FR-1, invariant 3).** A test asserts the probe workflow's path appears in no
  harness template source. `ci-review-templates.ts` contains no `broker-dogfood` string.
- **AC-2 (FR-3, FR-4).** A static contract test parses the probe workflow and asserts:
  - `on:` contains no `pull_request` or `pull_request_target`.
  - Workflow-level `permissions` is `contents: read`.
  - `id-token: write` appears only on the probe job.
- **AC-3 (FR-5, FR-11).** A static test asserts the broker URL and audience in the probe
  workflow (and later `ai-review.yml`) are string literals. They are equal to
  `packages/broker/wrangler.toml`'s `BROKER_AUDIENCE`, and no `${{ vars.* }}`,
  `${{ secrets.* }}` or `${{ inputs.* }}` expression feeds the URL or audience.
- **AC-4 (FR-7, FR-14).** A static test asserts every job that obtains a broker token has a
  revoke step with `if: always()`. The revoke step has no `|| true` / `continue-on-error`.
- **AC-5 (FR-2).** The probe workflow contains no write to `ai-review:*` labels, the
  `ai-review` check-run, the `ai-review/pass` status or `ready-to-merge`.
- **AC-6 (FR-6, live).** After the broker deploy, a `main` run of the probe is green. Its job
  summary shows one repository, the exact `review` permission set, an `expires_at` within 1h,
  and a successful revocation. A follow-up `GET /installation/repositories` with the revoked
  token returns 401.
- **AC-7 (FR-8, live).** A `workflow_dispatch` refusal probe gets 403 `repo_claim_mismatch`
  with no `token` field, and the job is green. Pointing the probe at a deliberately accepting
  case fails it red. That case is a control run, not a shipped mode.
- **AC-8 (FR-9, FR-10).** A contract test over `ai-review.yml` covers all three selector
  values:
  - Selector unset with secrets set: the direct arm, byte-identical step behaviour to today.
  - `broker` with secrets set: the broker arm, with no `create-github-app-token` call.
  - `app`: the direct arm, with no broker call.
- **AC-9 (FR-12, live - SPEC-034 AC-9 observed here).** With the selector at `broker`, make
  the broker unavailable deliberately on a throwaway fixture PR (Plan picks how; the deploy
  owner does it). The run posts no `ai-review:pass`, `ready-to-merge` stays red, the failure
  text names the broker, and no direct-arm token was minted in that run.
- **AC-10 (FR-12, FR-13, FR-16 - SPEC-034 AC-7 observed here).** With the selector at
  `broker`, a normal PR gets `ai-review:pass` with `sender = minspec-sdd[bot]`, an `ai-review`
  check-run from integration 4212099, `ready-to-merge` green, and a verdict comment naming
  token source `broker`.
- **AC-11 (FR-13).** Setting the selector back to `app` and re-running the same PR produces a
  verdict naming token source `app`. This is the comparison #697 asks for.

## Invariants (must not break)

- **INV-1 - Constitution invariant 2 (no silent gate).** No step that mints, checks or revokes
  a broker token swallows an error. A broker failure on the live arm is a visible red, never a
  quiet fall-through to the key.
- **INV-2 - Constitution invariant 3 (blast radius).** No adopter repo's behaviour changes
  until it sets the selector or SPEC-034 FR-11 changes the default. The shadow probe never
  ships.
- **INV-3 - Constitution invariant 1 (offline).** Untouched: everything here runs in this
  repo's CI. The extension gains no network call, and the vsix gains no broker URL beyond what
  SPEC-034 FR-5 already permits.
- **INV-4 - SPEC-034 FR-6 (no artifact egress).** Neither stage sends the broker anything but
  the OIDC JWT (in `Authorization`) and `{repository, permissions_profile}`.
- **INV-5 - DR-033 §6 provenance.** `ai-review:pass` is honoured only from the allowlisted
  App. A human hand-applying it is still reverted.
- **INV-6 - SPEC-034 approval.** This spec does not edit SPEC-034's `requirements.md`. Where
  it needs SPEC-034 to behave differently (the selector of FR-9), it says so here and flags it
  for SPEC-034's owner (see Follow-ups).

## Decisions needed (Clarify)

- **DQ-1 - Which stages.**
  - (a) **(rec)** Shadow probe first, then the live gate. Cost: two machinery PRs instead of
    one, and the probe stays on as an unrequired workflow, using roughly one broker mint per
    `main` push plus the schedule.
  - (b) Shadow probe only. Cost: #697's real ask (verdicts posted via the broker) is never
    exercised here, and SPEC-034 AC-7 / AC-9 stay unobserved until a customer hits them.
  - (c) Live gate directly. Cost: the first ever live mint happens inside the required merge
    gate. A broker defect then reds every PR in this repo with no prior observation of the
    happy path.
- **DQ-2 - Fallback semantics.**
  - (a) **(rec)** Manual: the operator flips the selector to `app`. Cost: a broker outage
    blocks merges here until someone notices and flips the variable.
  - (b) Automatic retry through the key on broker failure. Rejected as the recommendation:
    it makes SPEC-034 AC-9 unobservable here, hides broker outages behind green runs
    (constitution invariant 2), and leaves the key as the effective gate credential.
- **DQ-3 - Key custody after cutover.**
  - (a) **(rec)** Keep `MINSPEC_APP_PRIVATE_KEY` as a repo secret. Cost: SPEC-034 FR-5's
    "key never in the repo" property is not demonstrated here, and the repo remains a place a
    leaked key could come from.
  - (b) Also move `approve-on-label.yml` and `main-red-watch.yml` to the broker and delete the
    secret. Cost: new scope. Those workflows may need permissions outside the `review`
    profile (unverified), which would mean a second broker profile, a SPEC-034 change. It
    should be its own issue, not this spec.
- **DQ-4 - When adopters get `id-token: write`.**
  - (a) **(rec)** Together with the broker arm, in the change that closes SPEC-034 task 1.4b
    (FR-15). Cost: the live-gate stage waits on SPEC-034's own progress, and adopters still
    receive the permission even though their selector stays unset.
  - (b) Hold the permission back from the shipped template until SPEC-034 FR-11 flips the
    default, running the broker arm here from a repo-local copy of `ai-review.yml`. Cost:
    this repo then runs a different gate from the one adopters get, which defeats the
    byte-exact portability test and the point of dogfooding.
- **DQ-5 - Does SPEC-034 absorb the selector?** FR-9 changes how the shipped workflow picks
  its arm, which is SPEC-034 OQ-4's territory.
  - (a) **(rec)** Keep it here and raise it against SPEC-034 at its next revision. Cost:
    SPEC-034's approved rule and the shipped behaviour diverge (in the additive direction only)
    until SPEC-034 is revised.
  - (b) Revise SPEC-034 now. Cost: it stales SPEC-034's approval and needs a fresh human read
    of a T4 spec.

## Why no new DR

Every choice here can be undone in under a day by deleting a workflow file or unsetting a
repo variable, which is under this dispatch's threshold for a decision record. The decisions it rests on already exist: shared App and
broker (DR-054), one-hour tokens (DR-094), and the provenance guard (DR-033). The alternatives
rejected are recorded in DQ-1 to DQ-5 and below, so they survive without a DR.

## Out of Scope

- Building or changing the broker itself (`packages/broker/`): SPEC-034.
- Flipping adopters' default to the broker: SPEC-034 FR-11 (zero-config default).
- Moving `approve-on-label.yml` / `main-red-watch.yml` off the repo key (DQ-3 option (b)).
- Claim pinning beyond `repository` (`job_workflow_ref` / `ref`) in the broker. This is
  worth raising against SPEC-034. For `pull_request` runs, `workflow_ref` points at the PR
  head, so pinning it would not close the head-workflow residual Context item 6 describes.
- Abuse monitoring (#639).

## Alternatives considered and rejected

- **Delete the repo secrets so SPEC-034 OQ-4 picks the broker.** Rejected: it breaks
  `approve-on-label` and `main-red-watch` (Context item 3). It also removes the comparison arm
  #697 asks to keep, and rolling back needs a human to re-enter a private key.
- **Run the probe on `pull_request` to exercise PR posting early.** Rejected: it adds a
  head-executed workflow holding a fresh bot token on every PR (FR-4). PR posting is observed
  in the live-gate stage instead, where the self-edit guard already governs the head-run
  workflow.
- **Dogfood on a separate repo (task 1.4b's suggestion of the voip-sms-inbox repo).** Not
  rejected for SPEC-034, but it does not answer #697, whose ask is "here".
