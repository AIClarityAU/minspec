## One-Sentence Scope

Add one step to the canonical approval hash, in all three copies of the canonicalizer, so
that a ticked and an unticked task-list item hash identically, and prove with pinned
fixtures and a standing corpus test that the twins agree and that no existing sign-off is
voided by the change.

## Functional Requirements

- **FR-1 (the step).** `canonicalizeSpec` MUST rewrite every *ticked task-list line* in the
  document **body** to its unticked form before hashing. A ticked task-list line is a line
  that matches, from its first character:

  1. zero or more spaces or tabs;
  2. zero or more block-quote prefixes, each `>` followed by zero or more spaces or tabs;
  3. a list marker: `-`, `*`, `+`, or one to nine ASCII digits followed by `.` or `)`;
  4. one or more spaces or tabs;
  5. `[x]` or `[X]`;
  6. then a space, a tab, or end of line.

  The rewrite replaces the `x` or `X` with one space and changes nothing else. As a single
  expression, applied to each line after the body is split on `\n`:

  ```
  ^([ \t]*(?:>[ \t]*)*(?:[-*+]|[0-9]{1,9}[.)])[ \t]+)\[[xX]\](?=[ \t]|$)    ->    $1[ ]
  ```

  The step runs on the body only: the text after the frontmatter block, or the whole
  document when there is none. Frontmatter lines are never rewritten. It runs after the
  frontmatter split (existing step 2) and before the relative-link collapse (existing step
  5), in the same position in both twins.

- **FR-2 (ASCII classes only).** The expression in both twins MUST use the explicit classes
  written in FR-1. `\s`, `\d`, `\w` and any Unicode-aware class are forbidden in it.
  Python's `\d` matches every Unicode decimal digit in a text pattern and JavaScript's
  matches ASCII digits only; the twins' `\s` is already reported to disagree on four code
  points (#1668, filed, not re-run for this spec). A test MUST fail if either source file's
  checkbox expression contains one of those classes.

- **FR-3 (three copies, one commit).** The Node twin, the Python twin and the generated
  embed in `ci-review-templates.ts` MUST change in the same commit. The embed is produced
  by running `node scripts/gen-ci-templates.mjs`, never edited by hand. `npm run validate`
  (Rule 12) MUST pass on that commit.

- **FR-4 (nothing else moves).** No hashing call site listed in Context changes. No field
  is added to the approval record. `resolveStatus`, the approval states and the gate's
  verdict logic are untouched. `getSpecBodyOnly` (`canonical.ts:144`), the body-only review
  baseline, is untouched, so a tick still appears in the "changed since approval" diff.

## Contract

The canonical form, restated as the single source both twins implement. New text in bold.

1. Normalize line endings to `\n`.
2. Split the frontmatter block from the body.
3. Remove the lifecycle keys `status` and `phases` (with indented children) from frontmatter.
4. **In the body only, per line, rewrite a ticked task-list marker to the unticked marker
   (FR-1).**
5. Rejoin frontmatter and body.
6. Collapse relative link targets to `](RELLINK)`.
7. Strip trailing whitespace per line; collapse the trailing newline run to one.
8. sha256 of the UTF-8 bytes, hex.

Properties the step guarantees, each checked by a requirement above:

- **Length-preserving.** The canonical form has the same number of lines, and each line the
  same number of characters, as it would without the step.
- **Idempotent.** Applying it twice equals applying it once (FR-6).
- **Tick-blind, text-sensitive.** Two documents that differ only in tick state hash equal;
  two that differ in any other byte the old hash saw still hash differently (FR-5, FR-6).
- **Identity on an unticked document.** Its hash is the hash it has today (FR-5 last row,
  FR-7).

Function signatures do not change: `canonicalizeSpec(raw: string): string`,
`specHash(raw: string): string`, `canonicalize_spec(raw: str) -> str`,
`spec_hash(raw: str) -> str`, and the CLI `canonical.py --hash <file>`.

## Decisions needed (Clarify)

Four questions. Each states a recommendation and what that recommendation costs.

### DQ-1 - Which checkboxes does the hash ignore?

- **Option A - every task-list line in the body, under any heading (rec).** One line
  pattern, no document structure. Covers acceptance criteria, task documents with arbitrary
  slice headings, and decision-record checklists alike. **Cost: tick state stops being
  approved content everywhere. A document that records a choice with ticks ("- [x] Option
  A / - [ ] Option B") can have that choice flipped with no re-approval.** No hashed
  document does this today (of 373 checkboxes in requirements, design, decision and epic
  documents, 371 are under an acceptance-criteria or checklist heading and 2 are a code
  sample), and FR-9's guidance says not to, but guidance is prose and nothing enforces it.
- **Option B - only lines under a heading that contains "Acceptance Criteria".** Closes the
  choice-by-tick hole. Cost: the hash now depends on heading text, so renaming or
  re-levelling a heading silently changes which lines are covered; both twins need a
  heading tracker, which is new parity surface; and ticks in an approved task document
  (arbitrary headings) still void its approval, which is the friction #224 opened on.
  Changes FR-1, FR-5 and the Contract.

### DQ-2 - Is a checkbox inside a code sample normalized?

- **Option A - yes; the rule is a line pattern and does not know about code blocks (rec).**
  **Cost: the tick state of a checkbox shown inside a fenced or indented code sample, or an
  HTML comment, in an approved document is not covered by approval.** Two such lines exist
  in the corpus, in one document.
- **Option B - skip fenced code blocks.** Cost: a fence state machine in two languages
  (backtick and tilde fences, fence length, indentation, nesting inside lists and quotes),
  and an unclosed fence changes the treatment of every later line in the file. Indented
  code blocks cannot be told from nested list items by a line rule, so they would still be
  normalized. Changes FR-1, FR-5 and the Contract.

### DQ-3 - What happens to an approval given over a document that was already ticked?

Such a record is `stale` once the change ships. This repository has none (FR-7 keeps it
that way until merge). Adopter repositories were not measured.

- **Option A - build no migration; say so in the changelog (rec).** If FR-7 finds a record
  here before merge, the human re-approves it. **Cost: an adopter who approved a ticked
  document sees it go `stale` once after refreshing harness files, with only a changelog
  line to explain why, and must re-approve it.**
- **Option B - build a re-stamp, on the pattern of SPEC-070 FR-9.** Classify every sidecar
  under both hashes, re-stamp those fresh under the old one with `rehashedAt` /
  `rehashedFrom`, and ship an adopter path. Cost: a second migration tool and, for
  adopters, a frozen pre-change hasher as a new managed file, for a population measured at
  zero here and unknown elsewhere. Adds requirements; turns FR-7 from a guard into a
  pre-flight.
- **Option C - hold this until SPEC-070's migration exists and ride on it.** Cost: #224
  waits on a T4 (complete ceremony) spec that is mid-Plan, and SPEC-070 must be edited,
  which voids its approval.

### DQ-4 - May a stale approval become fresh with no human act?

A record that is stale today **only** because a box was ticked after approval resolves
`approved` the moment the step ships, with no write. There are none today.

- **Option A - allow it, and report each one by path (rec; FR-8).** Every byte the new hash
  covers is a byte the human signed, so nothing unsigned is being accepted. **Cost: an
  approval's status improves with no human keystroke, which DR-088 (ownership leaves the
  hash) treated as something to quarantine in its own migration; here the only visible
  trace is a test's printed list.**
- **Option B - quarantine them: rewrite each such record to a non-approving state so the
  human re-approves.** Cost: this needs the sidecar rewrite machinery of SPEC-070 FR-9.4
  (the stored hash must move out of `specHash`, a new field, both readers updated), INV-7
  no longer holds, and the human re-reads documents in which nothing but a tick changed.

## Why a decision record

The change cannot be undone in under a day once it ships: reversing it voids every record
whose document has a ticked item at that time. DR-035 already recorded the choice but is
not in force (`status: superseded`, nothing superseding it), so the register had no live
record to rest this spec on. The new record supersedes DR-035 and sets its
`superseded_by:`.
