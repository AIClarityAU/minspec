## One-Sentence Scope

Consolidate MinSpec's scattered first-run surfaces — the setup-relevant per-activation bootstrap toasts ([auto-bootstrap.ts `BOOTSTRAP_STEPS`:528](../../../packages/minspec/src/lib/auto-bootstrap.ts#L528): init / harness-refresh / classify / epic-backfill), the one-off init advisories ([init.ts:707](../../../packages/minspec/src/commands/init.ts#L707)), and the SPEC-018 init prompts — into **one re-openable page** (Command Palette: **MinSpec: Getting Started**) with a single hero required action (Initialize SDD structure) above a tiered Required / Recommended / Optional settings sheet of standing-consent switches and per-action buttons, each naming its real `minspec.*` setting, built directly on the merged [#883] per-signature answer memory so nothing is a one-shot dismiss — all offline (Tier-0), with every network/external action gated on an explicit per-action click and **no progress meter**.

## Context

Grounded in the current codebase, with `file:line` evidence:

- **First-run guidance is a toast pile, evaluated one-at-a-time on every activation.** [`runBootstrap`](../../../packages/minspec/src/lib/auto-bootstrap.ts#L734) walks [`BOOTSTRAP_STEPS`:528](../../../packages/minspec/src/lib/auto-bootstrap.ts#L528) and offers **the first eligible step only** — a modal-ish info toast with `Primary` / `Always` / `Don't ask again` actions. Six distinct offers (init, harness-refresh via `minspec.initRefresh`, classify, epic-backfill, DESIGN.md-stub removal, tasks.md scaffold) compete for that one slot, so a user never sees the whole setup surface at once and cannot revisit a step they dismissed except by changing the underlying state. There is **no single, re-openable place** that shows "here is everything MinSpec can set up for you, and what you've chosen."
- **The re-openable foundation is already merged.** [#883] added `answeredSignatures` ([auto-bootstrap.ts:68](../../../packages/minspec/src/lib/auto-bootstrap.ts#L68)) — a per-`(prompt, state-signature)` memory persisted in `.minspec/preferences.json` ([loadPreferences:82](../../../packages/minspec/src/lib/auto-bootstrap.ts#L82), [savePreferences:101](../../../packages/minspec/src/lib/auto-bootstrap.ts#L101)). A dismissed step returns **only when its underlying state genuinely changes** (e.g. a fresh template bump moves [`harnessDriftSignature`:201](../../../packages/minspec/src/lib/auto-bootstrap.ts#L201)). This is the exact "not a one-shot dismiss" semantics the page needs — it consumes the same model rather than inventing a new one.
- **The authoritative settings already exist** in `contributes.configuration` ([package.json:462-530](../../../packages/minspec/package.json#L462)). Every switch the page surfaces is a real contributed setting — `scroogellmNudge.enabled` ([:472], default `true`), `autoBootstrap.enabled` ([:477], `true`), `autoClassifyOnCommit` ([:487], `false`), `commitOnApprove` ([:492], `true`), `autoBackfillUseAi` ([:497], `false`), `advancePhaseOnApprove` ([:502], **`false` today**), `approverEmail` ([:507], `""`, `scope: application`), `coverage.minimumPercentage` ([:524], `80`) — **except `silentRefresh`, which is planned ([#186]) and not contributed.**
- **Approver identity resolves offline today, and has a real DR-056-shaped gate.** [`resolveApproverEmail`:92](../../../packages/minspec/src/commands/approve.ts#L92) prefers `minspec.approverEmail` over ambient `git config user.email` — **purely local git config, no network** ([:96](../../../packages/minspec/src/commands/approve.ts#L96); its docstring notes "Tier-0/offline: gitConfigEmail reads local git config only") — and the approve path **refuses** an agent/bot/absent identity ([approve.ts:240](../../../packages/minspec/src/commands/approve.ts#L240)). A free-typed approver email is therefore *forgeable* — the very unverifiable-approval problem [DR-056] / [SPEC-037] exist for. Verifying an email against the GitHub login is a *net-new* external read this spec introduces (see FR-5), not part of the existing offline resolver.
- **Coverage is honestly non-enforced today.** [package.json:528](../../../packages/minspec/package.json#L528) states the setting "does **NOT** itself change an already-initialized project's enforced threshold" — it only seeds the onboarding prompt / `.minspec/config.json`. The page must preserve that honesty, not imply enforcement.
- **The GitHub PR extension offer is already a per-action, first-init-only advisory.** [`offerGitHubPrExtensionAdvisory`:707](../../../packages/minspec/src/commands/init.ts#L707) installs **only on the user's explicit "Install" click** — the network-touching action is gated. The page adopts, not weakens, that consent shape.

**Core gap (one sentence):** MinSpec's setup story is spread across six competing activation toasts and two one-off advisories with no single, re-openable, honestly-labelled surface — so a user cannot see the setup choices MinSpec offers, cannot revisit a dismissed choice, and is never shown which standing `minspec.*` consents are in effect.

## Design spine (Tier-0, no rubber-stamping)

The page is **offline UI over settings that already exist**. It renders with **zero network** and holds **no standing network authorization**: every network/external action (Backfill with AI, install the GitHub PR extension, verify the approver identity against GitHub) fires **only on an explicit per-action click** — the click *is* the consent moment (constitution invariant [offline:5](../../../.minspec/constitution.md#L5); [DR-004]). It deliberately has **no progress meter / "N of M set up" tally**: a completion score pressures the user toward 100% on items we explicitly call *optional* and promise not to nag about — that trains rubber-stamping, which the constitution forbids ([Principles:9-16](../../../.minspec/constitution.md#L9)). Re-openability, dismissal memory, and honest built-vs-planned labels are the load-bearing properties; the switches are just a faithful view onto `contributes.configuration` and `.minspec/preferences.json`.

## Functional Requirements

- **FR-1 (single re-openable page).** A new command **MinSpec: Getting Started** (`minspec.gettingStarted`) opens one page consolidating the **setup-relevant** [`BOOTSTRAP_STEPS`](../../../packages/minspec/src/lib/auto-bootstrap.ts#L528) offers it can honestly surface — **init** (hero, FR-2), **harness refresh** (FR-16), **classify** (FR-4, via `autoClassifyOnCommit`), and **epic-backfill** (FR-8) — together with the [init.ts:707](../../../packages/minspec/src/commands/init.ts#L707) GitHub-PR advisory (FR-17) and the SPEC-018 init prompts. The remaining two bootstrap steps — DESIGN.md-stub removal and tasks.md scaffold — are deliberately **not** surfaced here (they are narrow file-hygiene prompts, not standing setup choices — see Out of scope). It is re-openable at any time from the Command Palette — never a modal that appears once and is gone. *Rationale: one durable surface replaces the competing one-slot toasts for the setup choices a user actually revisits.*
- **FR-2 (hero + tiered sheet + mindset primer, no meter).** The page shows exactly one **hero required action** — *Initialize SDD structure* (`minspec.init`) — above a settings sheet grouped **Required / Recommended / Optional**, with a slim four-point "how MinSpec works" primer up top ([#156] framing: ceremony matches blast radius; verify signal not content; one-next-step signpost; deterministic decisions). It renders **no progress meter or completion tally**. *Rationale: a score over items we call optional trains the rubber-stamping the constitution forbids ([Principles:10-11](../../../.minspec/constitution.md#L10)).*
- **FR-3 (re-openable, builds on [#883], nothing one-shot).** Any dismissal or "not now" on the page persists through the **same** per-`(prompt, state-signature)` memory as [`answeredSignatures`](../../../packages/minspec/src/lib/auto-bootstrap.ts#L68) — a dismissed item reappears only when its underlying state genuinely changes; standing switches read/write their `minspec.*` setting directly. No item is a forever-gone one-shot dismiss. *Rationale: reuse the merged foundation instead of a second, divergent memory.*
- **FR-4 (standing-consent switches, each naming its setting).** The Recommended tier presents "Always" standing-consent switches, each labelled with its `minspec.*` id: `silentRefresh` (**Planned [#186]** — rendered disabled with a "Planned" tag, never as a live no-op), `autoClassifyOnCommit` ([:487]), `commitOnApprove` ([:492]), `advancePhaseOnApprove` ([:502]). *Rationale: the "Always" toast choices ([auto-bootstrap.ts:771](../../../packages/minspec/src/lib/auto-bootstrap.ts#L771)) become durable, visible switches instead of buried one-time prompts.*
- **FR-5 (approver identity — offline default, click-gated GitHub verification).** An editable email field bound to `minspec.approverEmail` ([:507]) is seeded **offline, on render**, from [`resolveApproverEmail`:92](../../../packages/minspec/src/commands/approve.ts#L92) — `minspec.approverEmail` if set, else `git config user.email` — with **zero network**. A **separate, explicitly-labelled "Verify against GitHub" action** performs a **click-gated** `gh api user` read (a *net-new* external capability this spec introduces — `resolveApproverEmail` itself never networks); when the entered value is a valid email but **differs from the verified `gh` login**, the page shows a **non-blocking amber flag** — *"differs from your GitHub login — approvals under this email can't be auto-verified."* The field validates email format and is **not hard-locked** (corporate-email ≠ `gh`-login stays possible). *Rationale: a free-typed approver email is forgeable — exactly the unverifiable-approval risk [DR-056]/[SPEC-037] address — but the render-time value must stay offline (INV-1); verification against GitHub is a distinct, informed-consent click, not a default that would fire a network read on render.*
- **FR-6 (`advancePhaseOnApprove` default ON).** This spec flips the contributed default of `minspec.advancePhaseOnApprove` from `false` ([package.json:504](../../../packages/minspec/package.json#L504)) to `true`, and the page presents it on. *Rationale: OFF never meant "never advance" — it meant "ask each time" ([approve.ts:99-112](../../../packages/minspec/src/commands/approve.ts#L99)); auto-advance is the right default, the per-approval prompt is the minority case. (A user's explicit prior setting is preserved — see INV-5.)*
- **FR-7 (unified auto-commit consent).** The page surfaces **one** "commit MinSpec's own changes (approvals + harness refreshes); never pushed automatically" switch bound to `minspec.commitOnApprove` ([:492]) — not two per-surface toggles. Harness-refresh coverage under that one setting is the [#758] unify target (the `commitHarnessRefresh` command exists separately today, [package.json:76](../../../packages/minspec/package.json#L76)). *Rationale: one consent for "commit MinSpec's own state," matching the single mental model the setting already describes.*
- **FR-8 (Backfill = per-click button, not a standing toggle).** Epic backfill is a **"Backfill with AI" button**, not an "always use AI" switch; clicking it dispatches `minspec.backfillEpics` with `{ aiConsent: true }` (mirroring [auto-bootstrap.ts:592](../../../packages/minspec/src/lib/auto-bootstrap.ts#L592)). `minspec.autoBackfillUseAi` ([:497]) is deliberately **not** shown as a page toggle. *Rationale: the per-click button IS the network-consent moment; a standing flag would silently pre-authorize network (Tier-0 win).*
- **FR-9 (keyboard shortcuts shown where they exist; setting ids hidden by default).** Any actionable row that **carries a keybinding** displays it inline/as a persistent tooltip at all times (RSI / keyboard-first preference — a preference, not a gate: a row without a binding is not required to invent one); raw `minspec.*` setting ids are hidden behind a **default-off "Show setting ids"** meta-toggle. *Rationale: shortcut visibility is a standing accessibility need wherever a shortcut exists (a user can't use a shortcut she can't see); mandating one per row would over-specify a preference. Setting ids are power-user detail that clutters the default view.*
- **FR-10 (whole-row click toggles single-toggle rows only).** A whole-row click flips a row **only** when the row is a single boolean toggle; text/number-field rows (approver email, coverage), the multi-control approvals row, and any row carrying a secondary control (e.g. the refresh row's "Refresh now" action — FR-16) are **excluded** from row-click. *Rationale: a11y — a stray row-click must never mutate a text field or fire a secondary action.*
- **FR-11 (coverage seed field, honestly framed).** A number field bound to `minspec.coverage.minimumPercentage` ([:524]) is framed as a **non-enforced seed/default** — it seeds `.minspec/config.json` / the CI gate at setup; the extension itself does not enforce it (verbatim to [package.json:528](../../../packages/minspec/package.json#L528)). *Rationale: never imply enforcement the code does not perform (evidence discipline).*
- **FR-12 (ScroogeLLM nudge shown-on, no off-switch here).** `minspec.scroogellmNudge.enabled` ([:472]) is shown **on** and is **not disable-able on this page** (G-5 acquisition funnel, [constitution G-5:40](../../../.minspec/constitution.md#L40)). The setting still exists and is toggleable in the standard VS Code Settings editor — so it is not an un-disable-able-anywhere dark pattern. *Rationale: protect the funnel on the acquisition surface while keeping a real off-switch reachable.*
- **FR-13 (footer master controls).** A footer carries `minspec.autoBootstrap.enabled` ([:477]) — "offer setup automatically on activation; off = this page opens only on demand" — and the "Show setting ids" toggle. *Rationale: the master on/off and the display toggle are meta-controls, separated from the setup items.*
- **FR-14 (Tier-0 offline; per-action consent).** The page renders with **zero network calls**. Every network/external/mutating action — Backfill with AI (FR-8), install the GitHub PR extension (FR-17, [init.ts:707](../../../packages/minspec/src/commands/init.ts#L707)), verifying the approver identity against GitHub (FR-5) — fires **only on an explicit click** and never on render. *Rationale: constitution invariant ([offline:5](../../../.minspec/constitution.md#L5)) / [DR-004]; the click is the consent.*
- **FR-15 (evidence-honesty cuts).** Reading-time estimates ([SPEC-017] — zero code; surfacing it would be a false signpost) and auto-export-traceability / conformance (`minspec.conformance.enabled` [:467] — niche, only meaningful with ScroogeLLM present) are **excluded** from this page. *Rationale: never render a setting whose behavior is unbuilt or belongs elsewhere.*
- **FR-16 (Refresh harness now = per-click action).** A **"Refresh now" action** dispatches the existing manual harness-refresh command `minspec.initRefresh` on an explicit click — giving the [`BOOTSTRAP_STEPS`](../../../packages/minspec/src/lib/auto-bootstrap.ts#L528) *refresh* offer a durable home on the page. It is **distinct** from the Planned `silentRefresh` switch (FR-4): this fires a refresh **now, on click**; `silentRefresh` (unbuilt, [#186]) would make refreshes automatic. Its row is excluded from whole-row click (FR-10). *Rationale: the refresh bootstrap offer would otherwise be dropped; a manual per-click action is the honest, built form while automatic silent refresh stays Planned.*
- **FR-17 (Install GitHub PR extension = per-click button, per-click consent).** An **"Install" button** reuses [`offerGitHubPrExtensionAdvisory`'s install path:707](../../../packages/minspec/src/commands/init.ts#L707), installing the GitHub PR extension **only on the user's explicit click** — never on render. It is optional and non-blocking. *Rationale: the network-touching install is a first-class design element and needs its own requirement + test, not incidental coverage folded under FR-14; the click is the consent (Tier-0). Parallel to FR-8/AC-6.*

## Invariants

- **INV-1 (Tier-0 offline).** The page renders and all standing switches read/write with **zero network**. Every network/external action is gated on an explicit per-action click; none runs on render (constitution [offline:5](../../../.minspec/constitution.md#L5)).
- **INV-2 (no rubber-stamping).** The page shows **no progress meter / completion tally**, and never nags on items it labels optional (constitution [Principles:10-11](../../../.minspec/constitution.md#L10)).
- **INV-3 (re-openable, not one-shot — builds on [#883]).** No page dismissal is a forever-gone one-shot; dismissal memory reuses the per-`(prompt, state-signature)` [`answeredSignatures`](../../../packages/minspec/src/lib/auto-bootstrap.ts#L68) model — an item returns when its state genuinely changes.
- **INV-4 (approver identity verifiability; never auto-forge a sign-off).** The approver field's render-time value is the **offline** `resolveApproverEmail` result (git config / `minspec.approverEmail`), with **zero network**; verification against the `gh` login is a **click-gated** action, and a valid-but-divergent email is **flagged, never silently trusted**. The page **never writes an approval record or mints a sign-off** — it only sets `minspec.approverEmail`, which the existing DR-056 gate ([approve.ts:240](../../../packages/minspec/src/commands/approve.ts#L240)) still adjudicates (never-wrong).
- **INV-5 (honest labeling; no live no-ops).** A planned/unbuilt setting (`silentRefresh`, [#186]) is rendered as **Planned**, never as an active toggle that does nothing; a default change (FR-6) preserves any value a user has **explicitly** set (evidence discipline / DR-003).
- **INV-6 (Phase-2 gating).** This is Phase-2 public-onboarding work; it must not displace an unmet Phase-1 item ([constitution Phases:60-97](../../../.minspec/constitution.md#L60)).

## Vertical slices (thinnest-first; ordering is load-bearing)

1. **Slice 1 — the page exists, read-only.** The `minspec.gettingStarted` command + webview: the mindset primer, the hero *Initialize SDD structure* action (`minspec.init`), and a **read-only** render of the current tiered settings (no writes yet). Shortcut-visibility (FR-9) rides the hero row here. Thinnest end-to-end: open → render current state → run init. Delivers the "one re-openable surface" (FR-1, FR-2, FR-14) immediately.
2. **Slice 2 — standing switches + meta-controls.** Wire the Recommended-tier switches to their `minspec.*` settings (write via config API), the row-click a11y rule (FR-10), the **"Show setting ids" meta-toggle (FR-9)**, and the footer master (FR-13). Includes the FR-6 default flip and the FR-7 unified consent label. `silentRefresh` renders Planned/disabled. Shortcut-visibility (FR-9) rides each switch row that has a binding.
3. **Slice 3 — identity + per-action buttons + seed.** The approver-identity field seeded **offline** with the click-gated **"Verify against GitHub"** action, validation, and the amber divergence flag (FR-5); the per-action buttons — Backfill with AI (FR-8), Install GitHub PR extension (FR-17), and Refresh harness now (FR-16) — each with per-click consent (FR-14); the coverage seed field (FR-11); the shown-on Scrooge nudge (FR-12). Shortcut-visibility (FR-9) rides these action rows.

- **FR-OQ2 → editable, offline-seeded, click-gated GitHub verification (FR-5 as written).** Not hard-locked to the `gh` identity: the corporate-email ≠ `gh`-login case is legitimate, seeding from `gh` on render would breach INV-1, and [DR-056] already adjudicates identity downstream ([approve.ts:240](../../../packages/minspec/src/commands/approve.ts#L240)). Divergence raises the **non-blocking amber flag** only after an explicit *Verify against GitHub* click.
- **FR-OQ3 → `silentRefresh` stays a dependency ([#186]); the page renders it Planned/disabled.** Its behavior is its own change with its own review; the **built** refresh path surfaced here is the manual per-click `minspec.initRefresh` action (FR-16), so no live no-op is rendered (INV-5).

## Acceptance Criteria

- **AC-1 (FR-1, FR-14).** `MinSpec: Getting Started` opens the page; a network-recording test asserts **zero** network/external calls occur on open/render (INV-1).
- **AC-2 (FR-2).** The page renders the hero *Initialize* action, the four-point primer, and Required/Recommended/Optional tiers — and contains **no** progress-meter / "N of M" element (INV-2).
- **AC-3 (FR-3, INV-3).** A dismissal persists via the [#883] `answeredSignatures` model; a test shows the dismissed item stays hidden until its state signature changes, then reappears.
- **AC-4 (FR-4, FR-6, FR-7).** Each standing switch reads/writes exactly its named `minspec.*` setting; `advancePhaseOnApprove` renders **on** by default; `commitOnApprove` is a **single** unified consent; `silentRefresh` renders **Planned/disabled**.
- **AC-5 (FR-5, INV-4).** The approver field renders seeded with the **offline** `resolveApproverEmail` value (git config / `minspec.approverEmail`) and **zero network**; entering a valid email writes **only** `minspec.approverEmail` and **no** approval record; entering an invalid string shows a format error.
- **AC-6 (FR-8, FR-14).** The Backfill-with-AI button dispatches `minspec.backfillEpics` with `{ aiConsent: true }` **only on click**; no epic backfill / AI pass runs on render.
- **AC-7 (FR-10).** A whole-row click flips a single-toggle row; a test asserts a row-click on the email row, the coverage row, the approvals row, and the refresh row (FR-16) does **not** mutate their field / fire their secondary control.
- **AC-8 (FR-9, FR-13).** "Show setting ids" defaults **off**; any row that carries a keybinding displays it (inline/tooltip); the footer exposes `autoBootstrap.enabled`.
- **AC-9 (FR-11).** The coverage field's helper text states it seeds config/CI and is **not** enforced by the extension (matches [package.json:528](../../../packages/minspec/package.json#L528)).
- **AC-10 (FR-12).** The Scrooge nudge is shown **on** with **no** off-control on this page; a test asserts the page never writes `scroogellmNudge.enabled = false`.
- **AC-11 (FR-15).** No reading-time or conformance control is present on the page.
- **AC-12 (FR-16, FR-14).** The "Refresh now" action dispatches `minspec.initRefresh` **only on click**; a render-only test asserts no harness refresh runs on render.
- **AC-13 (FR-17, FR-14).** The "Install" button invokes the GitHub-PR-extension install path (`offerGitHubPrExtensionAdvisory`) **only on click** and **never on render**; a render-only test asserts no install is triggered. An implementation that omitted the button would fail this AC.
- **AC-14 (FR-5, FR-14, INV-1/INV-4).** The `gh api user` read fires **only** on an explicit "Verify against GitHub" click — **never** on the identity row's first render; before that click the row shows the offline value with **zero network**; on an air-gapped host the page renders without hanging or networking; after a verify, a valid-but-divergent email shows the amber flag and is **not** rejected.

## Risks

| # | Risk | Mitigation |
|---|------|-----------|
| R1 | **Default flip (FR-6) silently changes behavior for existing users.** Flipping `advancePhaseOnApprove` to ON could auto-advance where a user relied on the ask-each-time prompt. | The flip changes only the **contributed default**; any explicitly-set value is preserved (INV-5). The primer + visible switch make the new default discoverable; per-approval advance was always reversible. |
| R2 | **Approver amber flag reads as a block.** Users may think a divergent email is rejected. | Copy is explicitly non-blocking ("can't be auto-verified"), the field stays editable, verification is a separate click, and the DR-056 gate — not this page — adjudicates at approve time (INV-4). |
| R3 | **Consolidation orphans a live toast path.** Keeping both the page and the activation toasts could double-surface. | The page and toasts share one memory model ([#883]); `autoBootstrap.enabled` (FR-13) governs whether toasts fire at all. Toast retirement/relationship is a design (HOW) decision — see design.md, not a new mechanism here. |
| R4 | **Phase-2 work crowds Phase-1.** Polishing onboarding could steal priority from the dogfood line. | INV-6 + the header banner mark it Phase-2; the resolver treats it as lower-rank until the Phase-1 line is met ([constitution Phases](../../../.minspec/constitution.md#L60)). |
