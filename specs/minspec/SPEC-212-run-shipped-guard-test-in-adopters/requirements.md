# SPEC-212: An adopter's CI runs the ai-review-guard test suite MinSpec ships to it

## In plain terms

MinSpec copies `.github/scripts/ai-review-guard.test.js` into every repo that adopts the
ai-review stack (#871). In MinSpec's own repo, `.github/workflows/ci.yml:113` runs it
(`node --test .github/scripts/ai-review-guard.test.js`). `ci.yml` is not a shipped template,
so an adopter gets the suite and nothing runs it. The guard that decides merges is then
unverified in exactly the repos that cannot see its tests fail. This spec makes one shipped
workflow run the suite, so the evidence travels with the file.

> **SPECIFICATION ONLY.** Nothing is built by the session that wrote this. A human reads it,
> answers **Decisions needed (Clarify)**, and approves it through the spec-approval gate.

Materializes **#2059** (named follow-up of #871; same class as #1186 section 2 fixed in

## One-Sentence Scope

Make a workflow that MinSpec already ships to adopters run `node --test` on the shipped
`ai-review-guard.test.js`, failing the check visibly when the suite fails or cannot run.

## Context (read from this worktree, not inferred)

- `.github/workflows/ci.yml:113` is the only invocation of the suite; `grep -n
  "ai-review-guard.test" .github/workflows/*.yml` returns that one line.
- `.github/workflows/ai-review.yml` is a shipped template: `scripts/gen-ci-templates.mjs:43`
  embeds its verbatim body, and the CI-review stack is in `SELF_HOSTED_TEMPLATE_NAMES`
  (`template-registry.ts:2753`), so this repo authors the file directly and the generator
  copies it into `ci-review-templates.ts`. The embedded copy must be regenerated, never
  hand-edited (`node scripts/gen-ci-templates.mjs`; staleness fails `npm run validate`).
  Consequence: editing the template body means editing `.github/workflows/ai-review.yml`.
- In `ai-review.yml` the runner job checks out the TRUSTED base (line ~284) and sets up Node 22
  (~290) before any review step, but every step after the guard step carries
  `if: steps.guard.outputs.configured == 'true'` - i.e. it runs only where the review secrets
  are configured. A step added with that condition would not run in an adopter that has not
  configured review.
- The App installation holds no `workflows: write` permission by design (host DR-079, as cited
  in the issue; not re-verified here), so any edit under `.github/workflows/` is a human push.
- `minspec-validate.yml`'s body is a string literal in `template-registry.ts`
  (agent-editable), but it is not in `SELF_HOSTED_TEMPLATE_NAMES`, so editing it makes this
  repo's own copy stale until a human pushes the refreshed file.

## Functional Requirements

- **FR-1 - The shipped suite is invoked in an adopter's CI.** After a Refresh Harness Files,
  an adopter repo contains a workflow step running `node --test` against the shipped
  `.github/scripts/ai-review-guard.test.js`, in the carrier workflow chosen under DQ-1.
- **FR-2 - Plain Node.** The step uses only the Node the stack already sets up; no package
  install, no network call beyond what the carrier job already makes (constitution invariant 1;
  the suite's no-dependency property is proved by `ai-review-guard-test-parity.test.ts`).
- **FR-3 - Fails visibly.** A failing, crashing or missing suite fails the step (non-zero
  exit); the step has no `continue-on-error` and no `|| true` (constitution invariant 2). A
  missing test file is a failure, not a skip.
- **FR-4 - Trusted source.** The suite and guard run from the base-ref checkout, never the PR
  head, matching how the carrier job already treats control scripts.
- **FR-5 - Carrier and template stay in step.** The embedded copy
  (`ci-review-templates.ts`) is regenerated by `node scripts/gen-ci-templates.mjs`; this
  repo's own file and the shipped template are the same bytes (existing freshness gate).
- **FR-6 - A gate that the step exists.** A test (placed by Plan) asserts the scaffolded
  carrier workflow contains the `node --test` invocation of the shipped suite path, so removing
  the step later fails `npm test`, not just a review. The test must be shown red on the tree
  without the step (red-then-green).
- **FR-7 - Dedupe with `ci.yml`.** `ci.yml:113` either stays (MinSpec-only, redundant) or is
  removed; see DQ-2. Whatever is chosen, the suite must still run on every MinSpec pull request.

## Decisions needed (Clarify)

### DQ-1 - Which workflow carries the step?

- **(a) `ai-review.yml` (rec).** Already shipped, already checks out base, already sets up
  Node, and is the workflow whose decisions the guard makes. Cost: a `.github/workflows/` edit,
  so it is human-push-only and waits on a founder keystroke; and as written its steps run only
  when review secrets are configured (see DQ-3).
- **(b) `minspec-validate.yml` template body.** Agent-editable. Cost: this repo's own copy goes
  stale until a human pushes it (same permission wall, one step later), and a guard-specific
  step lands in a corpus-validation workflow.
- **(c) A new standalone guard-test workflow template.** Cost: a fourth workflow in every
  adopter for one line, unless conditioned on the ai-review stack being present.

### DQ-2 - Keep `ci.yml:113`?

- **(a) Remove it once the carrier step runs on MinSpec PRs too (rec).** One invocation, no
  drift. Cost: `ci.yml` is a workflow edit (human push) and the suite then runs only where the
  carrier runs; if the carrier is secret-gated (DQ-3) MinSpec's own coverage must be confirmed.
- **(b) Keep both.** No coverage risk. Cost: the suite runs twice on MinSpec PRs.

### DQ-3 - Run the step in adopters that have not configured review?

- **(a) Unconditional (rec).** The guard file ships regardless, so its tests should run
  regardless; no silent skip. Cost: needs a step placed outside the `configured == 'true'`
  condition, with its own checkout/Node setup or an ordering change in the runner job.
- **(b) Same `configured` condition as sibling steps.** Minimal diff. Cost: an unconfigured
  adopter ships the guard and the suite with no witness - the gap this issue is about.

## Invariants (must not break)

- **INV-1 - No silent gate** (constitution invariant 2): FR-3.
- **INV-2 - Offline core** (constitution invariant 1): no new network call in MinSpec itself.
- **INV-3 - Blast radius** (constitution invariant 3): changes reach an adopter only via its
  own Refresh Harness Files; no adopter file is hand-edited. The step is part of the
  ai-review stack an adopter already opted into via `.minspec/`.
- **INV-4 - Guard behaviour unchanged**: the guard and suite files are not modified.

## Acceptance Criteria

- [ ] A scaffolded repo's carrier workflow contains `node --test .github/scripts/ai-review-guard.test.js`
      (FR-1, FR-6); the test is red without the step, green with it.
- [ ] Running the step command in a freshly scaffolded repo exits 0; with the test file deleted
      or one case forced to fail it exits non-zero (FR-3).
- [ ] `grep -nE "continue-on-error|\|\| true"` over the added step prints nothing (FR-3).
- [ ] `node scripts/gen-ci-templates.mjs --check` and `npm run validate` exit 0 (FR-5).
- [ ] The suite still runs on every MinSpec pull request after DQ-2 is applied (FR-7).
- [ ] `npm test`, `npm run lint` pass.

- Granting the App `workflows: write` (host decision, DR-079).
