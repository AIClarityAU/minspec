# SPEC-137: A DR never lands without its INDEX entry

> **SPECIFICATION ONLY.** Nothing is built by the dispatch that produced this. A human
> reads it, answers the questions under **Decisions needed (Clarify)**, and approves it
> through the normal spec-approval gate before any code changes.

Materializes **[#366](https://github.com/AIClarityAU/minspec/issues/366)** - *"DR-index
drift reds validate on EVERY PR - DRs land without atomic INDEX regen (3rd recurrence)."*

## Problem

`docs/decisions/INDEX.md` is a derived artifact. Rule 8 of `scripts/validate-frontmatter.ts`
(`:369-380`) fails fatally on a DR file with no INDEX entry, a status mismatch, or an
orphan entry. `npm run validate` scans the whole corpus, so once a DR reaches `main`
without its INDEX entry, **every open PR** fails `lint` until someone hand-adds the entry.
Three occurrences so far (DR-045/046 blocking #354; DR-047 blocking #361, fixed by #364),
each costing a fix PR and a CI round trip.

## What the code does today (verified by reading, `file:line`)

- Regeneration lives only in the extension: the DR-folder file watcher
  (`packages/minspec/src/extension.ts:550-575`, 300 ms debounce, opt-in gated, errors
  swallowed as "best-effort") and `applyStatus` (`commands/adr.ts:244-249`).
- Only the **Accept** path commits the INDEX with the DR (`commands/adr.ts:252-262`,
  SPEC-022 FR-1). **Create** does not: `createAdrCommand` (`commands/adr.ts:62-94`) calls
  `createAdr` and nothing stages or commits an INDEX. I found no `regenerateDrIndex` call
  there; the watcher is the only thing that can write it, after the fact and uncommitted.
- The pre-commit hook runs `npm run validate` when DR/INDEX files are staged
  (`.githooks/pre-commit:325-`), but the validator reads the **working tree**, not the
  staged index (the hook itself says so at its "Known limit" note). I believe, unverified,
  that this is the escape: the watcher (or any session) leaves a regenerated but
  **unstaged** `INDEX.md`; validate passes locally against it; the commit contains the DR
  and not the INDEX. Plan phase must reproduce this before it is relied on.
- Any DR written by a headless agent or `sed` has no watcher at all; the pre-commit hook
  is then the only local witness.

**Root cause (mechanism plus missing gate):** the INDEX is regenerated by a best-effort,
editor-only side effect that is not part of the commit, and the commit-time gate checks
the working tree rather than what is being committed. The fatal Rule 8 then converts the
one stale commit into a corpus-wide outage. Adding the entry by hand (#364) fixes an
instance, not the gate.

## Functional requirements

- **FR-1 (commit-time witness).** A pre-commit check, run when any `docs/decisions/DR-*.md`
  is staged, regenerates the INDEX content in memory from the **staged** DR blobs and
  compares it to the **staged** `INDEX.md` blob. Any difference blocks the commit with a
  message naming the DR ids and the one command that fixes it. It fails closed: if it
  cannot read the staged blobs or regenerate, the commit is blocked visibly, never skipped
  (constitution invariant 2).
- **FR-2 (atomic create).** `MinSpec: Create Architecture Decision Record` regenerates
  `INDEX.md` in the same operation that writes the new `DR-NNN.md`, so both files exist
  together on disk. Staging/committing remains the user's act unless Clarify DQ-1 says
  otherwise.
- **FR-3 (no unstaged regeneration trap).** Regeneration is deterministic and idempotent
  (the existing `regenerateDrIndex` already preserves CRLF, SPEC-095); the check in FR-1
  must give the same verdict whether the INDEX was produced by the watcher, the command,
  or by hand.
- **FR-4 (CI second witness).** CI runs the same comparison on the PR's merge result, so a
  commit made with the hook bypassed (`DR_INDEX_GATE_OFF=1`, a headless agent with no
  hooks) is still caught **on the PR that introduces it**, before it reaches `main`.
  This is an independent witness to FR-1 (invariant 2), not a replacement.
- **FR-5 (blast radius).** Nothing here changes behaviour in a repo without `.minspec/`
  (invariant 3): the hook check and the CI step are inert when `.minspec/` is absent.
- **FR-6 (offline).** The check is pure, local, and makes no network call (invariant 1).

## Out of scope

- Auto-committing from CI (issue option 3, "self-heal"): see DQ-2.
- Changing which DR statuses are valid, or the DR id collision gate.

## Acceptance criteria

- **AC-1.** Staging a new `DR-NNN.md` with no `INDEX.md` change: the pre-commit check
  blocks, naming `DR-NNN`. (Fails on today's hook if the working-tree INDEX is unstaged
  but regenerated.)
- **AC-2.** Staging the DR **and** a correct regenerated INDEX: passes.
- **AC-3.** Working tree has a correct INDEX but it is not staged: blocks (the staged blob
  is what is judged).
- **AC-4.** Unreadable staged blob or regeneration throws: blocks with the error shown,
  exit non-zero; never exits 0.
- **AC-5.** Create command on a fixture workspace leaves `DR-NNN.md` and an `INDEX.md`
  containing `DR-NNN` on disk after one invocation.
- **AC-6.** Repo with no `.minspec/`: the check and CI step do nothing.
- **AC-7.** A fixture PR adding a DR without INDEX fails the CI comparison on that PR.

## Invariants this must not break

1. Offline Tier-0 (invariant 1).
2. No silent gate (invariant 2): no `|| true` on the new check; a missing witness fails
   closed; the CI step is a second, independent witness to the hook.
3. Blast radius is the opted-in project (invariant 3).
4. DR-029: DRs are still born `proposed`; this spec does not touch acceptance.

## Decisions needed (Clarify)

**DQ-1. Should Create also stage (or commit) the INDEX with the DR?**
- (a) **Regenerate on disk only** (rec): least surprise; the FR-1 hook still guarantees both
  are committed together. Cost: the user must stage two files, and the failure is only
  caught at commit time.
- (b) Stage both files via git. Cost: the extension starts mutating the git index on
  Create, which it does not do today.
- (c) Commit both like Accept does. Cost: commits a just-drafted, unreviewed DR.

**DQ-2. Keep Rule 8 fatal, or downgrade it to a warning (issue option 2)?**
- (a) **Keep fatal** (rec): FR-1 and FR-4 move the failure to the PR that causes it, so
  the outage cannot recur through the normal path, and the gate stays a gate. Cost: a DR
  that arrives via a bypassed hook *and* a bypassed/absent CI step still reds everyone.
- (b) Downgrade to a warning. Cost: drift becomes visible-but-mergeable, which is the
  "weaponised stale index" fix traded for a silent-ish gate; contradicts invariant 2's
  spirit and lets a wrong status in the INDEX ship.
- (c) Fatal only for status mismatch and orphans, warning for a missing entry. Cost: a
  split rule that is harder to explain.

**DQ-3. CI self-heal (issue option 3)?**
- (a) **No** (rec): a bot commit to PR branches needs write credentials and workflow
  permissions this repo deliberately withholds from agents, and an auto-fix hides the
  defect it should report. Cost: the author must fix by hand (one command).
- (b) Yes, regenerate and push. Cost: new write-capable CI surface; machinery-review
  territory.

**DQ-4. Where does the shared comparison live?** (a) **a new `scripts/` file reused by both
hook and CI** (rec), cost: a second consumer of `adr-manager` from `scripts/`; (b) extend
`validate-frontmatter.ts` with a `--staged` mode, cost: grows an already large file.
