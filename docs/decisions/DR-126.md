# DR-126: App repos do not behave exactly as before

Triggered by: #4141

> **Born `proposed` per DR-029.** Acceptance is a separate human act (*MinSpec: Accept
> ADR*). This record makes no new choice. It writes down two consequences of choices already
> made in SPEC-268 and PR #4079, because accepted DR-115 contradicts them.
>
> **Amends DR-115** (App secrets optional; `GITHUB_TOKEN` fallback). It replaces only two
> sentences there: the plain-terms line "Repos that have the App secrets (this one) behave
> exactly as before", and the clause in Decision 1 "the App identity is used exactly as
> today". The rest of DR-115 stands. DR-115's accepted text is not edited. It carries a
> one-line forward pointer to this record (Rule 16, `scripts/validate-frontmatter.ts:552-597`).

## In plain terms

In a repo with the MinSpec App secrets, such as this one, review still posts as
`minspec-sdd[bot]` and the merge gate still reaches the same verdict. Two things change.
After every completed review, the merge gate runs once more and may post its status a second
time. Before the AI reviewers start, the review job now removes the git login that checkout
left on disk, and it stops with an error if it cannot. DR-115 said App repos "behave exactly
as before". That is no longer true. New repos still need only the Claude secret (PR #4079).

## Context

DR-115 Decision 1 kept the App arm "exactly as today". SPEC-268 then specified the no-App
fallback. Building it (PR #4079, branch `cos/noapp-secrets-1126`) changed the App arm in two
ways:

- **D2 option (b).** SPEC-268 D2 asked whether the new `workflow_run` re-evaluation also runs
  in the App arm. The agent pick under DR-123 was (a), exit early and post nothing. Planning
  found (a) unsound. The re-evaluation shares the per-PR concurrency group
  (`ready-to-merge-<PR>`, #1973). GitHub keeps one pending run per group and drops the older
  pending run when a newer one queues. So an App-arm run that exits without writing can
  replace a queued `labeled`/`synchronize` run and leave `ready-to-merge` unwritten (SPEC-268
  design R3). The founder chose option (b), re-evaluate in both arms, on 2026-11-26 at 21:56
  UTC (2026-11-27 in Sydney). Observed at branch tip `0b336ba0`:
  `.github/workflows/ready-to-merge.yml:124-136` (trigger, "re-evaluates in BOTH arms") and
  `:203-206` (no early exit for the App arm).
- **Persisted credential (security finding on #4079).** `actions/checkout` writes the job
  token into `.git/config` as an `http` extraheader. The voters can read that workspace, and
  FR4 widens the token's scopes. `ai-review.yml` now unsets the extraheader after the last
  head fetch. It fails the job if any extraheader remains, before any voter runs, in both
  arms. Observed at `0b336ba0`: `.github/workflows/ai-review.yml:575-585` (SPEC-268 design
  R5b).

**Build status (RCDD / DR-003).** Both behaviours exist on PR #4079's branch and **not on
main**. At this record's base `7322e031`, `ai-review.yml` has no `extraheader` handling and
`ready-to-merge.yml` has no `workflow_run` trigger. This record describes the behaviour
#4079 ships. If #4079 does not merge, this record has nothing to correct and should be
withdrawn.

**SPEC-268 text.** The amended D2 and AC2 (option (b), founder-chosen) were observed on
branch `cos/spec268-founder-1127` at `d63e2ce7`, not on main. The issue says SPEC-268's
plain terms also say this supersedes DR-115's line. No local ref has that sentence; I believe
it lands in the same founder-approved requirements change, unverified.

## Decision

1. **DR-115's "behave exactly as before" is replaced.** In a repo where both App secrets are
   set, the reviewer identity, labels, comments, check-runs, commit statuses and the
   `ready-to-merge` verdict rules are as DR-115 states, with two departures:
   - **Departure A: one more gate evaluation per completed review.** When an `ai-review`
     run completes, `ready-to-merge` re-evaluates the PR from fresh API state and writes
     what a gate run writes (the `ready-to-merge` status and the `awaiting-approval` /
     `blocked-by` label sync). It is still the single writer of that status (DR-115
     Decision 4 unchanged). In the common case the second post carries the verdict the
     `labeled`/`synchronize` run would have posted for the same head and base (SPEC-268
     AC2 as amended).
   - **Departure B: the persisted checkout credential is removed before the voters run.**
     In both arms, the job token that `actions/checkout` persisted is unset after the last
     fetch. A remaining extraheader fails the review job visibly (`::error::`, exit 1). It
     is never skipped (constitution invariant 2).
2. **Adopters still need only the Claude secret.** `CLAUDE_CODE_OAUTH_TOKEN` alone gates the
   scaffolded review (DR-115 Decision 1, unchanged; PR #4079).

## Residuals (accepted; tracked in #4140)

Departure A brings in four residuals, listed in SPEC-268 design R6 and tracked in #4140.
Each fails closed, red and never a false green:

- Label-timeline lag can turn a fresh `success` red. The re-evaluation reads pass
  provenance from the label timeline, and that can lag the `labeled` run.
- A run it replaces in the queue skips that run's provenance revert and stale-pass strip.
- A failed PR read posts `failure` on the reviewed head (`workflow_run.head_sha`), which may
  not be the PR's current head.
- A newer head whose queued run it replaced can have no status until that head's own review
  completes.

Departure B's residual: a review job whose workspace still holds a persisted credential after
the unset stops red. That job produces no verdict until the cause is fixed (by design, no
best-effort fallback). Its fetch path is unchanged, because every fetch runs before the unset.

## Alternatives considered

- **Amendment section inside DR-115:** rejected. It edits an accepted record's body, so
  DR-115's acceptance hash would no longer cover its own text. Readers also cannot see an
  in-record amendment as pending (#2613, SPEC-266). SPEC-268 D3 chose a separate record for
  this same topic for the same reason. The cost: the reviewer-identity story now spans three
  records (DR-054, DR-115 and this one). DR-115 still gets a one-line pointer, which Rule 16
  requires and which stales its sidecar (a warning only for decision records,
  `scripts/validate-frontmatter.ts:701-738`).
- **Leave DR-115 as is and rely on SPEC-268's text:** rejected. An accepted record that
  misdescribes shipped behaviour misinforms, which is the defect class Rule 16 exists for.
- **Keep the App arm identical (D2 option (a)):** rejected by the founder. It can leave
  `ready-to-merge` unwritten (SPEC-268 design R3).

## Reversibility

Reverting Departure A means restoring an App-arm early exit, which re-opens the
unwritten-status failure. Reverting Departure B re-exposes the write-scoped token to the
voters. Either one is a template change plus a scaffold refresh in every adopting repo, which
takes more than a day across adopters. Hence this record.
