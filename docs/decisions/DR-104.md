## In plain terms - what this changes for you

When you update a pull request from `main` and nothing in the pull request's own change
moved, the four reviewers no longer run again. The pass they already gave is carried to the
new commit. The comment, a label, the check and the status on that commit all say the
verdict was carried and name the commit the reviewers actually read. If what they would be
shown differs by even one byte, they run exactly as before. To get a fresh review of a
carried commit, re-run the job.

What you give up: on a carried commit nobody re-read your change against what `main`
gained. The build and tests on the updated commit are the only check for a change that is
fine alone and wrong next to the new `main`.

## Context

`main` requires a pull request to be up to date before it merges, and the staleness guard
(#359) voids `ai-review:pass` on any push. An update from `main` is a push, so the whole
four-voter panel re-runs on a change it has already passed (#1688). This record decides
that a pass is carried across a push when the text the voters would be given is
byte-identical and the reviewer is unchanged, and it records what that costs: on a carried
commit no voter reads the change against what `main` gained.

**It was proposed once and refused, and DR-097 is built beside that refusal.** #1840
proposed skipping the panel when the patch was unchanged. It was closed as not planned on a
measurement of 3 repeats in 41 fingerprinted runs, all three on one pull request and all
three base moves, with about a third of runs being machinery pull requests whose `neutral`
check could not be re-attested from at all. DR-097 (per-voter reuse on the same commit)
records that outcome in its Context and sets its own decision against it in a table: reuse
across commits "yes, that was the point", exposure to the #1394 semantic-conflict class
"yes, that is what closed it".

**What changed is the measurement, not the risk.** #2588 measured every round of the
review workflow across four repositories for the window 2026-10-01 17:00Z to
2026-10-06 22:23Z: 154 rounds, with the panel at about 26 percent of the weekly quota used
(range 20 to 34). The breakdown posted on #1688 on 2026-10-07 rebuilt the text the voters
were given for each round and compared it with the same pull request's previous round:

| What repeated | Rounds | Share of panel cost | Share of quota used |
|---|---|---|---|
| Whole review diff byte-identical to a round that had already passed | 18 | 9.2 percent | about 2.5 percent |
| Same added and removed lines, hunks or context moved because `main` touched the same files | 7 | 5.4 percent | about 1.4 percent |
| Both | 25 | 14.7 percent | about 3.9 percent |

All 25 followed a pass and all 25 passed again. So did the 6 other updates from `main` in
the window: 26 re-reviews after an update from `main`, no verdict changed. The costs are
modelled from round counts, and #2588 says to treat each percentage as good to within about
a third.

**Two of #1840's three objections are answered by that; the third is not.** The saving is
no longer three runs on one pull request. The machinery objection is answered in the
design: a completed round now records its verdict in a form that survives the `neutral`
conclusion (see Decision, 4). The #1394 exposure is exactly what it was. This record
accepts it, and says so here because the decision is being taken in an implementation pull
request, which is the outcome #1897 was filed to prevent.

## Decision

**1. What the `ai-review` check asserts.** One of two things, and the check, the comment, a
label and the commit status say which:

- *Fresh round:* the required voters reviewed this commit.
- *Carried round:* the required voters reviewed commit X and passed it; what they would be
  given at this commit is byte-identical to what they were given at X; and the reviewer
  itself is unchanged since X. The voters did not run on this commit.

**2. When a verdict is carried.** Only when all of these hold. Anything else runs the full
panel, and every refusal writes its reason to the run log: the gate fails closed and
visibly, as DR-066 requires of anything merge-gating.

1. The event is a push to an open pull request (`synchronize`), on the first attempt of
   the workflow run. A newly opened or reopened pull request is always reviewed. So is a
   re-run, which is the way out for a person who wants fresh eyes and is what
   `ai-review-retry` does to a blocked round.
2. The head the push replaced has an `ai-review` check run that is the latest on that
   commit, is completed, was posted by the allowlisted reviewer App, concluded `success` or
   `neutral`, and carries a readable round record naming a pass.
3. That check run was chosen from a listing shown to be the whole list. GitHub returns
   check runs a page at a time. A listing that is short of its own `total_count`, has no
   count, or is a full page is refused, so the newest run on one page of several can never
   stand in for a later round on a page nobody read.
4. The input hash recorded by that round equals the input hash at the new head.
5. The reviewer key recorded by that round equals the reviewer key at the new base.

**3. What "nothing changed" means.** Two sha256 hashes, computed by the trusted base
checkout from git objects. Never the event type, the actor, a label, a commit count or a
commit subject.

- *The input:* the exact bytes the voters are given, which is the defanged three-dot diff
  plus the approval-provenance block. `review-branch.sh --print-input` prints them and
  exits before any model call, so the comparison and the review read one definition.
  `git patch-id` was rejected as the identity because it ignores whitespace.
- *The reviewer:* the blobs, at the base commit, of the workflow, the guard, the review
  scripts and the four role prompts, plus the coverage setting. The workflow file carries
  the pinned CLI version and the voter set, so both are bound.

Not bound, and said so: project context the reviewer CLI loads by convention, and every
other file in the base checkout. That is the accepted risk in section 6, not an oversight.

**4. What is carried, and what never is.** Only a pass. A completed passing round writes
`review-round:v1:pass:<input>:<reviewer>:<reviewed commit>` into its check-run summary; no
other verdict is ever recorded, and a record naming any other verdict does not parse.

- `ai-review:changes` is never carried. A voter that dies without a verdict fails closed to
  `changes`, and carrying that would make an outage stick to the pull request.
- `ai-review:blocked` is never carried. It is the review not running.
- So a carry cannot upgrade a verdict. The one label it can write is the one already
  earned.
- A carried round records the commit the voters actually read, not itself, so a chain of
  base updates keeps pointing at the one real review.

**5. A carried verdict is visible.** The comment's heading says carried and that the
voters did not run; its first line says it is not a fresh review; it names both commits,
says why, says what a carried verdict does not cover, and says how to get a fresh one. The
pull request wears `ai-review:carried`, which is a disclosure label and not a verdict
label. The check run's title and summary and the commit status say the same. A missing or
left-over disclosure label fails the step. A carry whose comment cannot be rendered is not
a carry.

**6. The accepted risk.** A carried pass means no voter read the change against the newly
merged base. A defect that exists only in the interaction between an unchanged diff and new
base code is not looked for by the panel. The required build and tests on the updated
commit remain the check for that class; the panel no longer is. 26 re-reviews with no
changed verdict cannot rule out a miss rate below about 1 in 10.

**7. The staleness guard keeps its job.** `decideStalenessStrip` stands down in exactly one
case: the allowlisted reviewer App has already recorded a completed pass round on the very
head being pushed. Without that, a carried round that finishes before the push-time strip
runs would have its fresh label removed and nothing would put it back. In every other case
the strip is what it was, so a real change still voids the verdict.

**8. Default-on, no setting.** Once the workflow edit is applied this is how the reviewer
behaves in this repository and in any repository that takes the shipped templates. There is
no opt-in key.

## What would reverse this decision

Any one of:

- A carried round that, re-run, returns anything other than a pass. #2636 (measure the
  carry once live) proposes sampling carried rounds by re-running them, which is the only
  way to see one.
- A defect that reached `main` on a carried pass and that a voter reading the change
  against the new base would plausibly have caught.
- The measured saving, once live, falling well short of the 18 rounds in 154 it is sized
  on. The risk is paid on every carry whether or not the saving is there.

Reversing is cheap: take the carry step out of `ai-review.yml`. The guard functions go
inert with no caller, which is the state they are in today.

## What this record changes in DR-097, and what it leaves alone

This record amends DR-097 in one place and no other.

- **Changes.** DR-097's section "Why this is safe where whole-panel reuse was not"
  describes whole-panel reuse across a base move as refused. If this record is accepted,
  that refusal no longer holds for the case defined in Decision, 2: a pass, on
  byte-identical input, under an unchanged reviewer. DR-097's Context sentence that #1840
  "was closed not-planned on measurement" stays true as history; the measurement it cites
  is the one this record sets a larger one beside.
- **Leaves alone.** DR-097's own decision. Per-voter reuse stays bound to one head SHA, and
  nothing here relaxes `selectVotersToRun`. The reasoning that a single voter's block must
  not be reused across commits is unaffected: this record carries a completed panel's pass,
  never one voter's block, and never a round that did not pass.

DR-097 carries a note at that section pointing here, written on this record's own pull
request and worded to be true while this record is still proposed. The note names this
record by its title, and this record's id was added to DR-097's `relates_to:`, because
prose there cannot spell the id out either.

## Alternatives rejected

Recorded per DR-086 section 4: under `autonomy: act` nobody sees these live.

- **Keep reviewing every push.** Zero added risk. Costs about 2.5 percent of the weekly
  quota for the byte-identical rounds alone, every week.
- **Turn off the up-to-date requirement.** Removes the pushes altogether, and removes the
  only guarantee that a pull request was built and tested against the base it merges into.
  That guarantee is what this record leans on in Decision, 6.
- **`git patch-id` as the identity.** Ignores whitespace, which is content in Python, YAML
  and Makefiles.
- **Carry `changes` too.** Makes a crashed voter's fail-closed `changes` permanent across
  re-pushes.
- **A position-insensitive identity, to also catch the 7 moved-hunk rounds.** The context
  lines are part of what a voter reads, and a normaliser that ignores positions is a place
  a change can hide. Worth about 1.4 percent of quota on a sample of 7. Tracked as #2635.
- **Walk back past the previous head when its round never completed.** Needs the pull
  request's list of earlier heads, which is another network read and a new trust question.
  Also #2635.
- **Paginate the check-run listing instead of refusing a short one.** More code on a merge
  gate to serve a commit that already holds a hundred rounds. Refusing costs one full panel
  in that case and cannot be wrong.
- **Make it opt-in per repository.** A setting nobody turns on saves nothing, and one more
  configuration key is one more way for the reviewer to differ between repositories without
  it showing. The disclosure on every carried round is the control instead.

## Costly to Refactor

1. **The round record format** (`review-round:v1:...`). It is written on check runs that
   outlive the code that wrote them, and the guard that reads it comes from the base
   checkout, which can be older or newer than the writer. Check: the version segment is
   parsed strictly, and an unknown version is a refusal, never a guess.
2. **`ai-review:carried` as a label name.** Anything that reads labels learns it. Check:
   it is declared once in the guard (`CARRIED`) and is not in `VERDICT_LABELS`.
3. **What the reviewer key binds** (`PANEL_KEY_PATHS`). Adding a file the reviewer reads
   and not adding it here lets a changed reviewer carry an old verdict. Check: a test pins
   the list to the paths `review-branch.sh` names.
4. **The meaning of the `ai-review` check itself** (Decision, 1). Low to change in code,
   high to change in what people have learned the green check to mean.

## Consequences

- About 18 rounds in 154 stop paying for the panel, on the #2588 sample: 9.2 percent of
  panel cost, about 2.5 percent of quota used. The 7 moved-hunk rounds still pay.
- The green check stops meaning one thing. It is honest about which of the two it means,
  but a reader has to look.
- A pull request updated from `main` can go green in seconds. Anything that treated "the
  panel is still running" as a pause now has less of one.
- On a commit that holds a full page of review rounds the verdict is never carried.
- The reviewer changing (a role prompt, a script, the workflow, the coverage setting)
  forces one full review of every open pull request on its next push. Those files changed
  in 7 of 232 merges to `main` over the 30 days to 2026-10-09.
- `scripts/review-churn-report.sh` counts completed `ai-review` check runs, so once this is
  live it would count carried rounds as repeat reviews. #2636.
