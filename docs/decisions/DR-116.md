# MinSpec has a machine-facing command line; a person is never told to type it

> **Born `proposed` per DR-029.** Acceptance is a separate human act (*MinSpec: Accept
> ADR*). This record is `kind: direction`: it changes what MinSpec is allowed to ship as a
> surface, so no delegation covers it, and an agent never mints the sign-off. It records
> an answer the founder already gave (SPEC-136, 2026-10-13); it does not claim that he has
> accepted this record.

Triggered by: #3296 (SPEC-136 task 1.1; build issue #3261).

## In plain terms - what this changes for you

MinSpec gains a second way in that is not the editor: one Node file,
`minspec-core.cjs`, that runs the same checks (validate, hash, status, next action, hook
activation, and the approval act) from a command line or as a local tool server. It is
for git hooks, GitHub workflows and AI agents, including ZCode inside its VM. You keep
using the Command Palette exactly as now; nothing MinSpec writes will ever tell you to
type this command instead. The cost: a command line that other programs call is a
contract, so its output format is marked unstable (`minspec-core/0`) until it has been
used for real, and it can still change under a caller.

## Context

SPEC-136 (headless core, `status: planning`, T4) packages the checks MinSpec already has
into one editor-free program with two ways in: a command line (FR-9) and a stdio tool
server (FR-10), both generated from one table of operations (FR-11). The founder allowed
the command line on 2026-10-13, for hooks, workflows and agents only (FR-12); this record
writes that answer down before any code depends on it.

SPEC-136's *Costly to Refactor* item 2 says the command line existing at all is
expensive to reverse:

- the project's instructions say MinSpec is "a **VS Code extension, not a CLI**"
  (`CLAUDE.md`, *Commands and locations*) and tell agents to "never write, suggest, or
  attempt a `minspec` shell command";
- goal G-7 (`.minspec/constitution.md:79-80`) is "Methodology enforced *in the editor at
  write time*, not bolted on as a separate CLI or IDE";
- once shipped, adopters' workflows and agents will script against it.

The spec required the founder's answer to be recorded as a decision before Plan. The
answer, 2026-10-13, verbatim: "zcode: do as recommended, except for where approvals are
made. i should be able to approve specs for the current project in zcode." The
exception concerns where approvals are made (SPEC-136 section F), not the command line,
so the command line took the recommendation: "**A command line - answered: as
recommended.** Allowed, machine-facing only (FR-12)" (SPEC-136 requirements.md, *Open
questions*, *Answered 2026-10-13*).

Why a non-editor surface is needed at all: the founder moved ZCode into a VM and ruled
that the host editor must not read folders ZCode writes (SPEC-136, *The boundary*).
The editor therefore cannot run the checks there, and GitHub Actions and agents have no
editor either. Without a headless entry point the checks are unreachable in exactly the
places the founder now works.

## Decision

1. **A command line exists, and it is machine-facing.** The headless core
   (`packages/core`, bundled as `minspec-core.cjs`, SPEC-136 design.md *Architecture*)
   exposes every operation as a command that prints a machine-readable result and
   exits non-zero on a failed check, a refusal or any error (FR-9). Its callers are git
   hooks, CI workflows and agents (FR-12).
2. **No MinSpec text tells a person to type it.** No document, prompt, template or
   shipped rule may tell a person to run the core's command line in place of a Command
   Palette entry (FR-12). Where a person-facing text needs the same check, it names the
   palette command. The enforcement is a test, not this sentence: SPEC-136's
   `boundary.test.ts` checks that every occurrence of `minspec-core` in the strings
   `template-registry.ts` renders sits inside a workflow or hook template, never in
   prose meant for a person (design.md, *Tests*).
3. **The command line owns no rule.** Every operation calls the existing library
   function (FR-2). The command line is a transport for the methodology, never a second
   implementation of it, so there is still one rule set, enforced in the editor and
   reachable elsewhere.
4. **The result schema is unstable at version 0.** Every result carries
   `schema: 'minspec-core/0'` and `coreVersion` (FR-16, design.md *The result envelope*).
   Version `0` means unstable: names, fields and exit-code meanings may change in any
   release without a deprecation period, and callers outside this repository and its
   own shipped templates (SPEC-139, the plugin shell) depend on it at their own risk.
   Leaving `0` is a new decision record: it declares the envelope stable as
   `minspec-core/1`, and from then on a breaking change bumps the number and is called
   out in the release notes. A caller can tell the two apart from the `schema` field
   alone.
5. **Not published as a public package.** Delivery is a GitHub release asset and a copy
   the scaffold writes to `.minspec/bin/` (design.md, *Delivery*; answered 2026-10-13).
   A public npm name is a separate, later decision (#248) because it cannot be taken
   back.

### How this squares with goal G-7

G-7 rejects MinSpec being a *separate CLI or IDE* that the methodology is bolted onto,
the spec-kit / Kiro shape where the person drives SDD by typing commands. This decision
keeps that: the person's surface is still the editor, the enforcement still happens at
write time in the editor, and the command line is not a product a person uses. What it
adds is reach for the same rules into places with no editor - which is goal G-6
("the same rule fires across editor, commit, CI, and agent"). G-7 constrains the human
surface; G-6 requires the machine surfaces; this decision is what lets both hold. G-7's
wording is unchanged.

### How this squares with "a VS Code extension, not a CLI"

That `CLAUDE.md` sentence exists so that no reader, human or agent, invents a `minspec`
command for a person to run. It stays true for people: MinSpec remains a VS Code
extension, and FR-12 forbids pointing a person at the command line. It is no longer
literally true for agents once the core ships, since an agent in a hook, a workflow or
ZCode will call `node .minspec/bin/minspec-core.cjs validate`. The sentence's "never
... attempt a `minspec` shell command" clause therefore needs a narrow carve-out for
the core's documented machine entry point when the core lands; that edit is a
follow-up below, not part of this record.

## Accepted cost

- A second entry point is a second surface to keep correct. Mitigated, not removed, by
  FR-2 (no rule of its own) and FR-11 (one table drives both ways in).
- Adopters may script against `minspec-core/0` despite the label, and a later change
  will break them. The label and the `schema` field are the whole mitigation.
- The rule that no text tells a person to type the command is enforced only over the
  strings `template-registry.ts` renders. A doc or issue body written by hand can still
  break it, and only review catches that.

## Rejected alternatives (DR-086 section 4)

- **No command line; the tool server only.** Rejected: git hooks and CI workflow steps
  invoke programs and read exit codes; they do not speak JSON-RPC. FR-15 (the validate
  workflow uses the core) would need a client shim, which is a command line by another
  name.
- **A person-facing command line (spec-kit style).** Rejected: contradicts G-7 and the
  founder's answer ("machine-facing only").
- **Keep checks editor-only and run them over files the editor reads from the VM.**
  Rejected by the founder's boundary ruling: the host editor must not read folders ZCode
  writes (SPEC-136, *The boundary*).
- **Declare the result schema stable at first release.** Rejected: nothing has called it
  yet (SPEC-136 Risk 5); a stable label on an unused contract would make the first real
  correction a breaking change.

## Consequences

- SPEC-136 tasks 3 onward may build `packages/core/src/cli.ts`; this is the record its
  build order says must land first (design.md, *Build order*, item 1).
- `boundary.test.ts` (SPEC-136) carries FR-12's enforcement.
- The ZCode plugin shell (SPEC-139, #2702) may call the core's command line from hooks.
- Not implemented today: as of this record no `packages/core` exists; every statement
  above about the core describes what SPEC-136 specifies, not shipped code.
