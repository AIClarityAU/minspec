# DR-101: Walking-skeleton completion is a tie-break term, declared by an epic's `skeleton:` list

## In plain terms - what this changes for you

You can tell MinSpec which specs form the thinnest end-to-end path through a feature area
by adding one line to that epic's frontmatter:

```yaml
skeleton: [SPEC-012, SPEC-010, SPEC-014]
```

From then on, when two pending tasks are otherwise exactly tied, the next-task signpost
prefers the one that moves an unfinished stage of that path forward over one that adds to
something off the path. Nothing else about the ordering changes. A gate still beats
everything, your `order`, `goal` and `priority` settings still beat this, and a blocked
task still sits behind its blocker. If you never write a `skeleton:` line, the signpost
behaves exactly as it does today.

MinSpec never works out the path for itself and never asks a model to. It reads the list
you wrote.

## Context

Triggered by: #297 (vertical-slice completion as a priority signal).

DR-019 (deterministic next-task ordering) ranks pending human tasks by severity class and
then by a within-class order, which DR-039 (goals drive priority) widened to
`(epic.order, goal-rank, priority, artifact-id)`. The code is
`compareRanked` at `packages/shared/src/next-task.ts:996-1002`. Every term before
`artifact-id` is a human weight; `artifact-id` is an arbitrary deterministic pick.

That order has no notion of an end-to-end path. Two equally unblocked tasks, one that
wires the last untouched stage of a walking skeleton and one that adds a fourth variant to
a stage that already works, rank by id. Contract-Driven Development names building
horizontally before the skeleton walks as a root cause of debt, and MinSpec can recommend
exactly that.

Measured on `main` at `27661a68` (2026-10-01), the arbitrary pick is the common case
inside an epic rather than a rare one:

- 0 of 72 specs declare `goal:`, so goal-rank never separates two specs.
- `priority` is never read from disk: the adapter passes `priority: undefined` for every
  epic, spec and decision (`packages/minspec/src/lib/artifact-graph.ts:522`, `:546`,
  `:569`).
- All 10 epics carry a distinct `order`, so `epic.order` always separates two specs in
  different epics and never separates two in the same one. EPIC-002 (Signpost Integrity)
  alone holds 24 specs.

So today, any two same-class tasks inside one epic are ordered by id alone.

Two things in this change are costly to undo, which is why it is recorded: a new
frontmatter key that authors will write across the corpus, and a change to the
within-class order that two accepted decisions state.

## Decision

### 1. The skeleton is declared on the epic, as an inline list of spec ids

An epic file MAY carry `skeleton: [SPEC-NNN, ...]` in its frontmatter. Each entry is a
spec id; each named spec is a **stage** of that epic's walking skeleton. The list is
human-authored. The engine reads it and never infers, extends, reorders or suggests it at
resolve time, which is the same rule DR-019 section 3 applies to `epic.order` and DR-039
section 2 applies to `goal:`.

The value uses the same inline-array grammar as the `depends_on` / `supersedes` /
`relates_to` edge keys (`parseEdgeArray`, `artifact-graph.ts:114-124`), so no new parser
shape is introduced. List order is documentation for the human reader. Sequencing between
stages stays the job of `depends_on`.

A stage may belong to any epic, because an end-to-end path can cross feature areas. Only
specs can be stages: a decision or an epic is not something that gets built, and one that
blocks a stage is already reached through `depends_on` (section 4).

### 2. A stage's state is read from the spec's `status`

| Stage state | Spec `status` | Effect |
|---|---|---|
| walked | `done` | the stage is proven; no preference |
| withdrawn | `archived`, `superseded` | no longer part of the path; no preference |
| unwalked | anything else | work on it advances the skeleton |

A skeleton declared by an `abandoned` epic is inert.

### 3. One new term, last before the arbitrary pick

The within-class order becomes

`(epic.order, goal-rank, priority, skeleton-advance, artifact-id)`.

`skeleton-advance` is binary: a node that advances a skeleton sorts before one that does
not. This amends DR-019 section 2 as already amended by DR-039 section 3. The severity
classes are untouched, and so is every existing term.

Placing it last means it only ever replaces the arbitrary id pick. It cannot override a
gate (a different class), a human weight (an earlier term), or a dependency (the flooring
pass at `next-task.ts:1072` runs after the sort and is unchanged).

### 4. A stage's blockers advance the skeleton too

A node advances a skeleton when its artifact is an unwalked stage, **or** is an uncleared
artifact that an unwalked stage reaches through one or more uncleared `depends_on` edges.

Without this the term is defeated in exactly the case it exists for. Measured against the
shipped resolver: four unapproved specs under one active epic, called W, X, Y and Z in
ascending id order, with W depending on the uncleared Z, produce the pipeline X, Y, Z, W.
If W is a stage, it sinks to the bottom and its blocker ranks behind unrelated work, so the signpost recommends two off-path tasks before the one
that unblocks the skeleton.

Only the skeleton term is inherited. The stage's `order`, `goal` and `priority` are not,
so a blocker in a lower-ordered epic still ranks by its own weights.

### 5. A bad marker is a validation failure, never a signpost failure

A `skeleton:` entry that does not resolve, is not a spec id, is repeated, or a `skeleton:`
value that is not an inline array, is reported by deterministic validation and fails
`npm run validate`. It is **not** resolver corruption and never becomes a "state unclear"
task.

This follows the rule the resolver already applies to `relates_to`
(`next-task.ts:332-341`): a broken soft link, one that only influences ties, is at most a
lint, and promoting it to a top gate violation buries every real task. A bad entry cannot
make the signpost wrong, because the term depends only on stages that exist and are
unwalked; it can only make the preference weaker than the author intended, and validation
says so.

## Alternatives rejected

- **A per-spec `slice: <name>` key.** Membership would travel with the member, and a spec
  could name any slice. Rejected for two reasons read from the code. A free-text name has
  no registry, so a typo silently creates a new one-member slice and nothing can detect it.
  And the approval hash covers every frontmatter key except `status` and `phases`
  (`packages/shared/src/canonical.ts:14-15`), so adding the key to an approved spec stales
  its approval, which makes the resolver emit an approve task for it and withhold its
  implement task (`next-task.ts:749`, `:841`). Marking a five-stage skeleton would cost
  five re-approvals and five signpost detours. The epic-level list costs one edit to one
  file and stales nothing: stored approval records exist only for specs (all 70 files
  under `.minspec/approvals/` sit in its `specs/` tree at `27661a68`), and the resolver
  carries no approval state for epics (`next-task.ts:78-84`).
- **A registered `SLICE-NNN` artifact kind.** Solves the typo problem by adding an id
  namespace, a status lifecycle and an index. SPEC-012 (next-task resolver) already
  specified one such kind, `MILESTONE-NNN`, and its own frontmatter records that it was
  never built. A second new artifact kind for a tie-break is disproportionate.
- **Treating a `relates_to` cluster as the path.** The issue floats this. Rejected because
  `relates_to` already means "loosely kindred, keep adjacent" and is written across the
  corpus for that purpose, including references to another register that deliberately do
  not resolve. Reading every existing cluster as a skeleton would be the engine inferring a
  path from data nobody authored as one, which DR-019 section 3 forbids.
- **Inferring the skeleton from the `depends_on` graph** (longest chain, most dependents).
  Rejected outright: it is inferred weight, and which path is the thinnest end-to-end one
  is a human judgement.
- **Placing the term above the human weights.** It would let structure outrank an explicit
  `order` or `goal`. DR-019 section 3 says the human sets weight; a structural hint should
  yield to it.
- **A new severity class for skeleton work.** Rejected: the class count and order is the
  costliest contract in SPEC-012 (its "Costly to Refactor" item 3), and a class would let
  the signal outrank `pending` gates, which the issue rules out.
- **A graded term** (fewer stages remaining sorts first). Rejected for v1: it makes the
  order depend on how many stages the author chose to list, so a carefully itemised
  skeleton loses to a coarse one. Binary is enough to replace an arbitrary pick.
- **Treating a bad entry as resolver corruption**, like a dangling `depends_on`. Rejected
  per section 5: one typo in a tie-break hint would replace the whole signpost with
  "state unclear".

## Costly to Refactor

The engine change is one compared field and one closure over existing edges, in a pure
function: cheap to revert. The cost is the data. Once authors have written `skeleton:`
lists, renaming the key, moving it off the epic, or changing which statuses count as
walked means migrating every epic that adopted it. **Reversibility filter: trivially
reversible until the first list is authored, more than a day once several are.** It is
recorded now because no list exists yet, which is the cheap moment.

The key is also optional and additive: an unread `skeleton:` line is inert YAML, so
removing the engine support never corrupts an artifact.

## Consequences

**Positive**

- Inside an epic, same-class ties stop being settled by id and start being settled by
  whether the work advances the declared end-to-end path.
- The signal stays inside DR-019's frame: explicit data in, pure function, reproducible,
  testable.
- A project that never writes the key sees no change at all.

**Negative**

- One more human-maintained frontmatter field. A stale list (a stage that should have been
  added, or a finished path nobody declared) mis-ranks silently, the same residual
  `epic.order` and `goal:` carry.
- Two accepted records must be amended when this ships: DR-019 section 2 and SPEC-012
  FR-2 state the within-class order. An existing gate (`validateDrAmendments`,
  `packages/minspec/src/lib/adr-manager.ts:262`) reports this decision once it is accepted
  until DR-019 mentions it. SPEC-012 has a stored approval record
  (`.minspec/approvals/specs/minspec/SPEC-012-next-task-resolver/requirements.md.json`),
  so editing its body stales that approval and costs one re-approval.
- The term never fires across epics while every epic has a distinct `order`. That is the
  intended conservative behaviour, but it means the signal is local to an epic.

## Risks

| # | Risk | Likelihood, impact | Mitigation |
|---|---|---|---|
| R1 | The term floats a task above a gate or its blocker, and the signpost lies. | Low, high | Section 3: it is the last term before the id pick, inside a class, before the unchanged flooring pass. SPEC-091 pins each precedence with a fixture that has a control. |
| R2 | A forgotten or stale `skeleton:` list mis-ranks. | Medium, low | Same class as DR-019's `epic.order` residual. The effect is bounded to which of several already-tied tasks comes first. Evidence on the task names the skeleton and its progress, so a wrong preference is diagnosable. |
| R3 | Every spec in an epic gets listed, and the term means nothing. | Medium, low | A degenerate list collapses the term to a no-op and costs nothing structurally, as DR-039 R4 notes for goals. |
| R4 | A block-style YAML list is silently unread. | Medium, medium | Section 5: a `skeleton:` key whose value is not an inline array fails validation rather than being dropped. |
