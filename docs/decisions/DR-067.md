# DR-067: Coordinated self-completing sessions — claim under a lease, shepherd your own PR, wrap up on exit; the drain reclaims only orphans

> **Born `proposed` per DR-029** (acceptance is a separate human act — *MinSpec: Accept
> Architecture Decision Record*). Materialized in
> [SPEC-044](../../specs/minspec/SPEC-044-coordinated-self-completing-sessions/requirements.md).
> This DR is the coordination sibling of [DR-065](DR-065.md) (which gave the
> [SPEC-026](../../specs/minspec/SPEC-026-session-presence/requirements.md) presence layer
> its *second* consumer, the sync gate); DR-067 gives it a *third* — the work-item claim —
> and reframes all three around one primitive already in the tree: **an expiring lease.**
> A prior draft of "DR-067" attached to the stalled, unmerged PR
> [#900](https://github.com/AIClarityAU/minspec/issues/900) is superseded — this is the
> local-register DR-067 authored on `main`.

## Context

The autonomous pipeline (triage → dispatch → build → review → merge) is live
([DR-060](DR-060.md)/[DR-061](DR-061.md)), but its **work-assignment model is a single
shared drain that both dispatches AND fixes everything**, with no atomic notion of "who
owns this item right now." Four founder requests on 2026-07-25 name the same missing
primitive from four angles:

1. **Claim-before-work.** The FIRST step of processing an issue must be *check-then-claim*
   so no two sessions double-work it. Today, `dispatch-issue.sh` flips
   `agent-ready → agent-running` ([dispatch-issue.sh:218-221](../../scripts/dispatch-issue.sh#L218))
   — a *de-facto* running-marker, but with **no check-before-claim** (nothing reads the
   label first and refuses if already claimed) and it is **drain-only** (a human session
   editing files never claims). A label flip is a last-write-wins attribute, not an atomic
   compare-and-swap, so two drainers (or a drain + a hand-run dispatch) can both read
   `agent-ready`, both flip, and both build the same issue.

2. **Creator-owned PR shepherding.** The session/agent that OPENS a PR has the change's
   intent in hand; it should drive that PR to merge — poll CI + ai-review, fix failures,
   ff a behind-base branch, land the auto-merge — instead of opening the PR
   ([dispatch-issue.sh:423-464](../../scripts/dispatch-issue.sh#L423)) and **exiting**,
   handing every open PR to a *fresh* drain remediator that has to **re-derive** the intent
   from the diff. That re-derivation is exactly what went wrong in
   [#912](https://github.com/AIClarityAU/minspec/issues/912): the drain's PR sweep
   (`remediate-pr.sh` via [drain-inbox.sh:471-496](../../scripts/drain-inbox.sh#L471))
   dispatched build agents that started near the context limit and crash-thrashed the whole
   `agent-ready` queue to zero PRs. The creator already has the worktree, the branch, and
   the reasoning — it is the cheapest and most-correct fixer.

3. **Auto-wrapup.** A session should run the `/wrapup` flow *on the way out* — commit and
   push chat-only work, file follow-up issues, save memory, prune merged branches/worktrees
   — so nothing that exists only in a dying session is lost and the tree is left tidy. Today
   wrapup is a manual, human-invoked skill; an autonomous session that dies mid-flight
   leaves loose work and leftover worktrees.

4. **Drain = orphan fallback only.** The drain must stop being the *primary* fixer. It
   should adopt a work item **only** when the item's owning session is **gone** — a
   safety-net reaper, not the default execution path.

**The unifying insight (the reason this is one decision, not four):** all four describe an
**advisory lock that EXPIRES unless a heartbeat renews it, whose reaper reclaims the stale
ones** — i.e. a **lease**. And the project already ships that primitive. SPEC-026's presence
layer *is* a lease: each live session heartbeats `.minspec/sessions/<uuid>.session.json`
every `HEARTBEAT_SECS=30` ([presence.ts:32](../../packages/minspec/src/lib/presence.ts#L32)),
a record is *held* iff `lastSeen` is within `STALE_SECS=120` **and** `process.kill(pid,0)`
proves the PID alive ([presence.ts:86-91](../../packages/minspec/src/lib/presence.ts#L86)),
and a dead record is reaped on read ([presence.ts:431-452](../../packages/minspec/src/lib/presence.ts#L431)).
DR-065 already made the sync gate a *consumer* of that lease
([presence.ts:202-224](../../packages/minspec/src/lib/presence.ts#L202)). So:

- **issue-claim / PR-claim = a new consumer of the same lease semantics.**
- **"drain reclaims orphans" = lease expiry** (heartbeat older than TTL ⇒ reclaimable), the
  exact reaper that already prunes dead presence records.
- **arbitration under contention = the FR-13 key already defined** — `startedAt`
  (fixed-width ISO-8601 ms, lexical == chronological), `sessionId` as the secondary
  tie-break ([presence.ts:53](../../packages/minspec/src/lib/presence.ts#L53), SPEC-026 FR-13).

No new lock store, no new coordination bus — the lease already exists; this DR gives it two
more consumers and a rule for who reclaims an expired one.

**The atomicity gap this DR must close honestly.** SPEC-026's lease is **single-machine** —
`process.kill(pid,0)` is meaningless for a PID on another host (DR-065 records this as a
known limitation). Issue/PR ownership, by contrast, is **cross-machine**: two developers, a
CI runner, and a laptop drain can all reach for the same open issue. There is no shared
process table across machines, and **a GitHub label is not a compare-and-swap** — so the
cross-machine claim needs an explicit optimistic-concurrency protocol (read-modify-write +
a deterministic tie-break) layered over a substrate that IS atomic, not over the label. That
substrate is the crux of the design (below) and the one part a human must ratify at Accept.

## Decision

Introduce **coordinated self-completing sessions**: a work item (issue or PR) is processed
by exactly one session at a time, under an **expiring lease**; the session that owns an item
drives it to completion and **wraps up on exit**; the drain reclaims an item **only** when
its lease has expired (owner gone). Concretely:

### 1. Claim-before-work (issue-claim as a lease consumer)

The **first** step of `dispatch-issue.sh` (before the worktree, before any edit) is
*check-then-claim*: read the item's current claim; if a **live** claim exists that this
session does not own, **stand down** (do not build); otherwise acquire the claim, then
**re-read and verify** this session is the deterministic winner before proceeding. The
`agent-running` label is retained only as a **human-visible mirror** of the claim, never the
authority (a label alone is a single, overwritable, non-atomic producer — precisely the
"single disableable producer" DR-066 forbids for anything load-bearing).

**The claim substrate — optimistic concurrency over atomic backstops.** Because a label is
not a CAS, exactly-one-owner rests on a **soft** optimization layer plus **hard** backstops,
and the correctness of the costly outcomes rests on the *hard* layers, never on the soft one:
the at-most-one-*merge* guarantee is the server-side PR-per-head CAS (concurrent) plus an
open-issue + shipped-marker gate (sequential), and same-host double-build corruption is closed
by a per-item `flock` + claim-unique worktree path. The soft claim only dedups *wasted work*:

- **Soft layer (dedup / avoid wasted work): a claim record with a deterministic winner.**
  The claim is an append-only, server-ordered record — a structured claim *comment* (or, as
  the hardening option in OQ-1, a claim *ref* `refs/minspec/claims/issue-N`) carrying
  `{claimant sessionId, host, worktreeRoot, pid, claimedAt, lastRenewed}`. Acquisition is
  *check → post → re-read → verify-winner*: after posting, the racer re-reads **all** claim
  records and keeps the claim **only if it is the earliest live claim**, where the winner is
  the earliest **server-assigned monotonic id** (the total order a label cannot give), with
  `sessionId` as a final deterministic tiebreak for the degenerate equal-id case. The
  client-clock `claimedAt` is **not** a deciding key (cross-machine clock-skew-unsafe; carried
  only as metadata) — the server id decides; for the claim-*ref* substrate there is **no**
  tiebreak at all, since `--force-with-lease` expecting-absent means at most one claim ref ever
  exists and the git-server CAS *is* the winner. The verify-read MUST enumerate every competing
  claim **to exhaustion** (paginate fully; compare against the served count; detect truncation);
  an incomplete, paginated-short, rate-limited, or failed read can never prove `own`, so it
  forces a **stand-down** (INV-6). A racer that is not the winner retracts (best-effort) and
  stands down. This dedups concurrent claimants *before* the expensive build, so the common
  case wastes no work.
- **Hard layer (concurrent correctness backstop): GitHub's one-open-PR-per-head-branch.** The
  dispatch branch is deterministic (`agent/issue-N`), and GitHub permits **exactly one open PR
  per head branch** and rejects a duplicate `gh pr create` atomically at the server. So while
  that PR/head is **open**, even if the soft layer ever admitted a false double-winner (a
  transient inconsistent comment-list read), the two racers collapse to **one** PR — two
  *concurrent* merges of the same change are impossible by a genuine server-side CAS, not by
  our optimism. **But this CAS window closes on merge:** once the first PR merges and
  `agent/issue-N` is auto-deleted, a later claimant (a stale drain cycle, a reopened issue, a
  soft-claim miss) could push a fresh `agent/issue-N` and `gh pr create` would succeed —
  merging the *same change a second time*. So the **sequential** at-most-one-merge guard is
  **separate and explicit**: any (re-)claim or dispatch is gated on the **issue being OPEN**
  *and* on a persisted **already-shipped marker** (the merged-PR number / a commit trailer /
  the closed-issue check), verified **before** re-claim — a shipped item is never re-dispatched.
  PR-per-head is the *concurrent* guarantee; the open-issue + shipped-marker check is the
  *sequential* one.
- **Same-machine hard layer (local-FS mutual exclusion).** PR-per-head is a *server* CAS; it
  gives **zero** protection against two racers on **one host** (the DR's own "a drain + a
  hand-run dispatch", both seeing only their own claim on a machine-independent stale read) that
  derive the **same** deterministic worktree path and both `git worktree remove --force` +
  `git branch -D` it ([dispatch-issue.sh:225-231](../../scripts/dispatch-issue.sh#L225)) before
  any push — racer B clobbering racer A's live worktree mid-build, a corruption the server CAS
  never sees. Two same-host guards close this, **complementary to** (not the rejected global
  singleton lock): **(a)** the per-item worktree path is **claim-unique**
  (`…/issue-N-<sessionId>`) so two racers never share a directory, and **(b)** an OS-level
  **`flock`** on a per-item lockfile (`.minspec/locks/issue-N.lock`) — a genuine same-host
  compare-and-swap the label cannot provide, self-releasing on process death — is held before
  any worktree/branch mutation for that item. A worktree owned by a **live** claim is **never**
  force-removed by another racer.

A claim is **live** iff `lastRenewed` is within the lease TTL **and** (same-machine) the pid
is alive — the SPEC-026 liveness predicate, extended cross-machine by the TTL alone (a
foreign host's pid is unobservable, so a foreign claim is judged *purely* by its heartbeat
age, degrading to the safe side: an un-renewed foreign claim expires and becomes
reclaimable). The owner **renews** on a wall-clock timer while working; on normal completion it
**releases**. Two honesty caveats the predicate forces:

- **The predicate can misjudge a suspended-but-alive owner as dead** — a stale heartbeat
  *alone* marks a claim reclaimable *before* the pid is even consulted
  ([drain-inbox.sh:196-197](../../scripts/drain-inbox.sh#L196)), so an owner whose heartbeat
  merely lapsed (laptop sleep past TTL, renew-HTTP failures over TTL, `SIGSTOP`/load starving
  the renew timer — all *unbounded*, so no TTL sizing solves them) is reclaimable *on the same
  machine too*. Reclamation is therefore **two-phase with a grace interval**: the reaper posts
  "reclaiming in one renew interval unless renewed", waits one renew interval, re-reads, and
  **backs off** if the owner re-asserts; complementarily the owner **re-verifies it still holds
  the claim before *every* credentialed op** (push, pr-create, arm-auto-merge, label-mirror) and
  stands down if it was reclaimed. The grace/re-verify handshake — **not** TTL sizing — is what
  keeps a still-alive owner from being overridden.
- **A live-but-hung owner must not hold forever.** Because renew is a wall-clock timer
  independent of build progress (§D10), a wedged `claude -p` build with a live parent + live
  renewer would keep its claim live indefinitely and never be reaped — self-healing-via-expiry
  (INV-2) failing precisely for a live zombie. An **absolute max-claim-lifetime** (independent
  of renew, sized ~2× expected-build-max) caps this: on expiry the owner self-releases to
  `needs-human-review`, or the claim is force-expired despite a live pid, so even a hung owner
  eventually becomes reclaimable. The bounded shepherd caps (§2) cover only the *post-PR* phase;
  the absolute lifetime is what bounds the *build* phase (claim → commit → push → pr-open).

### 2. Creator-owned PR shepherding

The session that opens a PR **claims it** (a PR-claim, same lease shape) and drives it to
merge instead of exiting: poll CI + the independent ai-review, address `ai-review:changes`
and failing checks **in its own worktree** — it **reuses the preserved worktree/branch (no
re-clone, no rebuild from scratch) and dispatches a fresh fix agent that is not
context-exhausted**, rather than the #912 fresh drain remediator that started near the context
limit. (The build agent's in-context reasoning does *not* persist across invocations; what
carries over is the *warm worktree + branch* and a *non-exhausted* fix agent that still reads
the PR feedback and diff — so the honest benefit is "no re-clone / no near-limit agent", not
"holds the intent".) It then ffs a behind-base branch and confirms the DR-061 native
auto-merge lands. Shepherding is **bounded and heartbeated** (a wall-clock cap and an attempt
cap, mirroring `remediate-pr.sh`'s `MINSPEC_REMEDIATE_MAX_ATTEMPTS`
[remediate-pr.sh:51](../../scripts/remediate-pr.sh#L51)); merge **conflicts are surfaced to a
human, never LLM-resolved** (unchanged from
[remediate-pr.sh:79-81](../../scripts/remediate-pr.sh#L79)). Credential model is **unchanged
and load-bearing**: the build/fix agent stays credential-free (no `gh`/push/network); the
**parent** dispatch process — the "creator" — performs every credentialed op, exactly as
today. The `ai-review:*` labels remain **CI-bot-owned** (never mutated by the shepherd —
[dispatch-issue.sh:466-487](../../scripts/dispatch-issue.sh#L466), the #600 provenance rule).

### 3. Auto-wrapup on session exit

A session tidies up on the way out, but the cheap must-happen op and the expensive fragile one
are **split and ordered** — a single trap that bundled them would let a hung wrapup strand a
lease. The parent's `EXIT` trap runs **mechanical teardown FIRST and unconditionally**:
`issue-lease.sh release-all` (a cheap `gh`/ref op that must **never** be gated on wrapup),
prune merged branches/worktrees, push already-committed work. Only **after** release does it
attempt the **cognitive** `/wrapup` best-effort — filing `inbox` follow-ups and saving durable
memory are an LLM/agent act (a fresh multi-minute `claude -p`), so on a **clean** exit they run
as the live agent's **last act before** the parent trap fires; a headless dispatch has no chat
to save, so its "wrapup" is effectively *release + worktree-prune*. Phase 1 wires the trap on
the same `resolve_session_pid`/`session_alive` the continuous drain already uses
([drain-inbox.sh:134](../../scripts/drain-inbox.sh#L134),
[:258](../../scripts/drain-inbox.sh#L258)). A **killed** session (SIGKILL) fires **no** trap at
all — its leases fall to the §1 TTL / absolute-lifetime expiry path, mechanical-only, no
cognition; that is the case orphan-fallback (§4) exists for.

### 4. Drain demoted to orphan-fallback

The drain stops being the primary fixer. Its dispatch loop and PR sweep become
**claim-aware**: it adopts an issue only if unclaimed-or-expired, and remediates a PR only if
its creator-claim is **absent or stale** (owner gone). `classify_pr`
([remediate-pr.sh:71-95](../../scripts/remediate-pr.sh#L71)) gains a new terminal token —
`skip-live-owned` — returned when a **live, non-self** creator-claim exists, so a PR under
active shepherding is left alone. The drain becomes the **reaper**: it reclaims **only** a
claim the liveness predicate deems expired — and even then via the **two-phase grace-interval
handshake** above (post-notice → wait one renew interval → re-read → back off if the owner
re-asserts), so a merely-suspended owner whose heartbeat lapsed is not overridden. This is
exactly SPEC-026's dead-record prune generalized from presence records to work-item claims. The
DR-065 gated fast-forward is unaffected (a different lease consumer).

### 5. Tier-0 split (constitution invariant #1 — offline)

The **offline lease primitive stays in core; every networked consumer stays out of it.**

- **Tier-0 (core, ships in the MinSpec ext):** the lease *semantics* already in
  `presence.ts` — heartbeat record, the `isRecordLive` validity predicate
  ([:86-91](../../packages/minspec/src/lib/presence.ts#L86)), reap-on-read, and the FR-13
  arbitration key. This module imports only `fs/path/crypto/child_process(git,local)` and
  makes **zero** network calls; the Tier-0 import-ban gate (`tier0-import-ban.test.ts`)
  keeps it that way. This DR's core contribution is **naming and documenting** these as *the
  lease primitive* (and, optionally, extracting the pure **liveness** predicate the networked
  consumers must mirror byte-for-byte, the DR-065 §4 parity discipline — note the *winner*
  function is **not** part of that byte-parity: it is substrate-specific and `presence.ts`
  exports none, §Decision-1). The host-equality the liveness predicate needs (`sameMachine`)
  is **decided outside core and passed in as a parameter** — resolved only by a local
  `os.hostname()` syscall, **never** a DNS/network lookup — so answering "same host?" never
  pulls the network into core. **No network enters core.**
- **Tier-1 (out of the MinSpec ext):** the networked consumers — GitHub issue/PR claim
  (poll, claim, verify-winner), the shepherd loop (CI/review polling, merge), the orphan
  reaper, and the `/wrapup` push. These do `gh`/git-network and therefore **cannot** ship in
  the air-gapped product ext (invariant #1). They live in Tier-1 dispatch tooling — the same
  home DR-065 §5 uses for the drain's `fetch`/ff and DR-004 bounds.

### 6. Phased rollout ("both, phased" — founder's choice)

- **Phase 1 — dev-time machinery in the minspec repo `scripts/`.** `dispatch-issue.sh`
  gains the claim-check first-step + the creator-shepherd loop; `remediate-pr.sh` gains the
  `skip-live-owned` orphan gate; `drain-inbox.sh` becomes claim-aware + adds the reaper;
  auto-wrapup is wired into the session-lifetime trap; the claim protocol lives in a new
  `scripts/lib/issue-lease.sh` with a pure, unit-testable seam (the `--classify`-style seam
  `remediate-pr.sh` already models). Core gains only the lease-primitive naming/doc.
- **Phase 2 — productize in the agent-execute "Execute" extension** (`aiclarity.agent-execute`,
  sealbox, EPIC-007, Tier-1), **cross-repo**. This is where autonomous claim/shepherd/wrapup
  becomes a shipped capability of the separate execution plane, not repo-local scripts.
  **Deliberately not fully specified here** — filed as a follow-up spec in the sealbox repo
  (see Follow-ups); this DR only fixes the split and the primitive so Phase 2 inherits them.

## Consequences

**Positive:**
- Double-work is prevented at the *first* step, not discovered at a clobber. The
  `agent-ready → agent-running` de-facto marker becomes a real, checked, expiring lease with
  a deterministic winner — and a hard PR-per-head backstop against the one costly failure.
- The #912 class (a fresh drain remediator re-deriving intent and crash-thrashing the queue)
  is closed by construction: the creator, holding the intent, shepherds; the drain touches a
  PR only once its owner is gone.
- Presence (SPEC-026) earns its **third** consumer, further validating the lease framing
  DR-065 introduced — one primitive, three uses (edit-guard, sync-gate, work-claim).
- No session leaves loose work or leftover worktrees behind (auto-wrapup), and leases are
  released promptly on clean exit.
- The offline core is untouched in capability and stays air-gapped; all new network lives
  behind the tier boundary, ready for Phase-2 productization without re-architecting.

**Negative:**
- **A new distributed-coordination protocol** (claim/renew/verify-winner/reclaim) is real
  surface with its own failure modes; the honest correctness argument leans on the atomic
  PR-per-head backstop, *not* on GitHub read-after-write linearizability (which the API does
  not formally promise). Recorded as OQ-1 for the human at Accept.
- **The lease *liveness* predicate now exists in three places** (TS core, the drain's bash
  reader, and the new claim script) — a standing drift risk, mitigated by the DR-065 §4
  parity-test discipline but not eliminated. (The *winner* function is deliberately **not**
  in that byte-parity: it is substrate-specific — comment `serverOrder`, or nothing for the
  ref CAS — and `presence.ts` uses a *different* arbitration key (`startedAt`), so it gets its
  own substrate-specific test, not a cross-reader byte-comparison.)
- **A same-machine `flock` + claim-unique worktree path** are a second, local hard layer the
  cross-machine soft claim cannot provide — extra machinery, but the only thing that closes the
  same-host double-`worktree-remove --force` corruption the server CAS never sees.
- **A shepherd that hangs** ties up its parent longer than a fire-and-forget dispatch; bounded
  by the wall-clock/attempt caps, and a killed shepherd's PR falls to orphan-fallback — but the
  throughput/latency trade (creator holds the item vs. drain fans out) is a genuine change.
- **Cross-machine claims degrade to TTL-only liveness** (a foreign pid is unobservable), so a
  crashed remote owner's item is stranded for up to one TTL before reclamation. Accepted:
  the failure lands on the safe side (stale ⇒ reclaimable), same as DR-065's foreign-record case.

## Alternatives considered

- **Keep the drain as primary fixer (status quo).** Rejected — it is the #912 failure mode:
  a fresh remediator re-derives intent it never had and thrashes. The creator is the correct
  owner.
- **Make `agent-running` the claim (a plain label).** Rejected — a label is last-write-wins,
  not a CAS, and has no expiry or heartbeat; two racers both flip it. It survives only as a
  cosmetic mirror of the real claim (and even that is a "single disableable producer" per
  DR-066 if trusted alone).
- **A singleton lock (one global lock, or one designated drainer) as the cross-machine
  authority.** Rejected — a singleton needs manual release and strands work when its holder
  dies; a *lease* self-heals via expiry. SPEC-026 FR-2 already ruled out a separate lock store;
  DR-065 reaffirmed it. Reuse the heartbeat as the live claim. *This rejection is about a
  **global/singleton** lock as the authority — it does **not** preclude the **per-item,
  auto-releasing** same-host `flock` of §Decision-1, which is a local-FS mutual-exclusion layer
  **under** the lease (self-releasing on process death, one lockfile per item), not a manually
  released global store.*
- **Trust GitHub comment-list read-after-write as the sole atomicity source.** Rejected as the
  *sole* source — the API offers no linearizability guarantee across replicas. Retained as the
  *soft* dedup layer, with PR-per-head as the hard backstop; the stronger claim-ref CAS is
  offered as OQ-1's hardening option.
- **Put the claim/shepherd/wrapup in the MinSpec core ext.** Rejected — networked by
  definition; violates invariant #1 (offline core). The offline *primitive* stays in core; the
  networked *consumers* are Tier-1 (Phase 1 scripts, Phase 2 Execute ext).
- **Fully spec the Phase-2 Execute-ext productization here.** Rejected — cross-repo (sealbox),
  and premature before Phase-1 dogfoods the primitive. Filed as a follow-up spec.

## Costly to Refactor

**Costly:** the **claim substrate choice** and the **exactly-one-owner semantics**. Once
sessions and CI trust a claim to mean "mine, do not touch," weakening the winner-determinism
or the reclamation TTL re-opens double-work and (absent the PR-per-head backstop) double-merge
— a distributed race that no after-the-fact test reliably reproduces. That is the DR-359 (mmo-platform parent register) ADR
filter (parent register, mmo-platform) tripping: hard to reverse once other actors depend on it.

**Cheaper to reverse:** the shepherd's caps and poll cadence; the `skip-live-owned` token and
where the drain consumes it; the lease TTL value and the absolute max-claim-lifetime (named
once per language, the *liveness* half parity-tested); the grace-interval length; and *which*
claim substrate (comment vs. ref) is used — the shared **liveness** predicate is parity-tested,
while the **winner** function is substrate-specific (comment `serverOrder`; the ref CAS needs no
tiebreak at all), so swapping substrate re-tests only that substrate's winner, not the liveness
gate.
