# An agent's environment is built from a list of names, and an issue reaches one only when listed accounts wrote all of it

> **Born `proposed` per DR-029.** Acceptance is a separate human act
> (*MinSpec: Accept ADR*), and DR-086 keeps DR acceptance on the stop list (section 2,
> class 2). An agent never mints the sign-off. This record's live status is its
> frontmatter `status:` field, not this note.

> **Whose decision this is.** Nobody has made it yet. The code was written to replace the
> environment scrub that #1203 (the dispatch-thrash investigation) led to, and to close
> what its review found. This record was written afterwards, because the
> architect voter on #2686 blocked on there being none. That voter was right by this
> repository's own rule: the change sets a trust boundary and cannot be undone in a day.
> Accepting this record is the founder's act. Until then it is a proposal with code
> behind it.

> **On this record's number.** The id was taken from the collision gate
> (`scripts/check-dr-id-collision.ts`), which on #2686 at 08:42 UTC on 2026-10-10 reported
> it as the next free one across `main` and every open pull request. The parent-register
> gate (`packages/minspec/tests/parent-register-refs.test.ts`) reads any decision id of one
> hundred or more, written in prose, as a reference into the parent register, so this body
> does not spell out its own id. It is in the frontmatter.

> **Where the code is, and that none of it is live.** All of it is on #2686:
> `scripts/lib/agent-context.sh` (the environment), `scripts/lib/dispatch-author-gate.sh`
> (whose text), `scripts/lib/agent-worktree.sh` (what a launcher runs in an agent's
> worktree), `scripts/dispatch-ready-check.sh` (the readiness check), and the tests named
> under each decision below. Nothing here is in force until that pull request merges. To
> see whether it is, look for `scripts/lib/dispatch-author-gate.sh` on `main`.

## In plain terms - what this changes for you

An agent the automation starts no longer gets a copy of the shell it was started from. It
gets a short list of ordinary variables and nothing else. A token or key that happens to
be exported where the drain runs is not handed to it.

That is a statement about the agent's own process, and no more. The agent still runs as
your user. Other processes of that user may hold the token, and what a process holds its
own user can read, an agent or a reviewer included. Closing that takes a user of its own
for the agent (#2691) and a narrower token for the launcher (#2693). Neither is done
here.

An issue is picked up for triage or dispatch only when every word of its title and body
was written by an account on a list of two: yours, and the pipeline's own App. Anybody
else's issue is refused and waits. So is an issue of yours that somebody else has edited.
Editing a stranger's issue yourself does not make it yours; filing it again does.

Pull request remediation is not held to that list. It asks who wrote each comment, and
takes the pull request itself (its title, its branch, its commits) from whoever can push
to the repository. And push access is, in effect, enough to write as the App. So the list
keeps out everybody who cannot push. It does not keep out somebody you later let push
(#2698).

What you give up: adding a person whose issues agents may work on is a code change and a
review, never a setting. A tool an agent's build relied on finding in an inherited
variable may now need that variable added to the list, with a reason. And issues filed
by the GitHub Actions account, which used to go to triage, now wait for you (#2694).

## Context

`scripts/` holds the dev-time automation that starts headless agents: issue dispatch,
triage, the review scripts, pull request remediation and the tooling radar. DR-008
(dispatch security) decided, for that automation, that credentials are kept out of the
agent's reach, and that unattended runs are for issues whose text is trusted. Neither was
held by code. This record decides how far each is now held, and names what is not.

Triggered by: #1203 (the dispatch-thrash investigation). The scrub described below was
that investigation's fix for one variable; this record is about what the scrub left open.

**The environment.** Every launch sat behind a scrub that removed one named variable from
the launcher's environment and passed every other exported variable through. So an agent
held whatever its launcher held, which is not what DR-008 says an agent holds. The test
beside it read the launcher's source text and never the environment a started agent
actually had, so it stayed green.

A list of names to remove could not have held, however long it grew. It contains the
names somebody thought of. A variable nobody thought of is passed, and nothing fails when
it is: the gap is silent by construction.

**Whose text.** No launcher asked who wrote an issue. The gates between a label and a
launch each judged something else: that triage had run, that no other run held the
issue, that there was quota. The repository is public and an issue form applies the
queue's label for whoever fills it in. An agent that is started runs the project's own
build, which DR-008 itself calls executing arbitrary code by definition.

**The launcher, afterwards.** Keeping a token from the agent says nothing about the
launcher, which still holds it and goes back into the agent's worktree to push, rebase,
run the checks and ask for a review. What it executes there, it executes as itself, in a
directory the agent could write to.

## Decision

**1. An agent's environment is built from a list of names.** A variable reaches an agent
because it is on the list in `scripts/lib/agent-context.sh`, and for no other reason.
Every launcher under `scripts/` starts the CLI through that file. The model's own login
is handed over only when a launch asks for it by name, one login at a time, and a
capability probe is handed none.

The list checks itself before every launch and starts nothing if it holds a name with one
of three endings (`_API_KEY`, `_TOKEN`, `_SECRET`), one of the named GitHub token
variables, or anything else of GitHub's (`GH_*`, `GITHUB_*`). That check knows those
shapes and no others, and it reads names, never values. What holds the rest is a test
that writes the list out name by name, so adding a name or taking one away is an edit to
that test in the same review.

The list is deliberately narrow. It does not carry `npm_config_*`, and it does not carry
`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*` or `GIT_CONFIG_VALUE_*`; a test holds both
families off it. A build that relied on configuration arriving in such a variable, and
not from a file under the home directory, behaves differently. That direction is the safe
one, and a name a run needs is added at the list with the reason beside it.

Held by `agent-launch-sites.test.ts` and `dispatch-env-allowlist.test.ts`, which run the
real launchers against a stand-in for the CLI that records what it was started with, and
by a gate that reads every file under `scripts/` and fails on a line that names the CLI
and does not start it through the list. That gate is a tripwire for the ordinary ways of
writing a start, not a proof that there is no other: it cannot see a program held in a
variable that is given its value somewhere it does not read, or a start from outside
`scripts/` (#2698).

**2. Whose issue may start an agent, and whose comments reach one.** An issue is triaged
or dispatched only when the account that opened it, every account that has edited its
body, and every account that has changed its title are all on a list in
`scripts/lib/dispatch-author-gate.sh`. Comment text reaches a prompt only from a listed
commenter, and only when everyone who edited the comment is listed too.

That is the whole of what the list judges: an issue's title and body, and comments. It
does not judge these, and each is under Residual risk:

- **A pull request.** Remediation (`scripts/remediate-pr.sh`) asks who wrote each comment
  and nobody else. Who opened the pull request, who wrote its title and who pushed its
  commits are not asked. It takes any branch of this repository whose name fits, so it
  trusts push access where issue dispatch trusts the list.
- **A label.** The role an agent runs under comes from a `role:` label. A label counts
  only when it is a plain name, so it selects only among the files in `scripts/roles` and
  puts no text in a prompt. Who applied it is not asked.

How the list itself is held:

- An entry is an account's kind and its number, never its login. A login can be changed
  and then taken by somebody else.
- The list is two literals in a function body: the pipeline's own App, and the founder.
  There is no variable that adds to it and none that turns the gate off.
- Being a collaborator, or having write access, does not put an account on the list.
  Both can be granted later for an unrelated reason. This is a statement about the list
  and not about what such an account can bring about: push access is, in effect, enough
  to write as the App, which is on it. See Residual risk.
- The text judged must equal, exactly, the text the prompt is built from. An issue edited
  between the two reads is refused and offered again on the next cycle.
- Whatever cannot be read is a refusal that says so, never a pass.

Held by `dispatch-author-gate.test.ts`. The exact comparison was also measured against
GitHub on 2026-10-10, because a difference between the two reads would refuse every issue
for ever: eight issues in this repository (filed by the App, by the founder and by the
GitHub Actions account; edited; with code blocks; with text outside ASCII; with trailing
whitespace; up to 42,000 characters) and one from another public repository whose body
has carriage returns. Title and body were equal in all nine. No issue in this repository
has a carriage return in its body (1,531 read), which is why that one came from
elsewhere.

**3. What a launcher runs inside an agent's worktree is pinned.** Git operations there
take their hooks from the launcher's own tree and use the git directory recorded when the
worktree was made, before any agent ran in it. The worktree's own code (its tests, its
build) is run the way the agent was, through the list in 1. A tool the launcher needs
there is named by a path in the launcher's own tree, and the helper that runs one refuses
a program that is inside the worktree, however the path to it is written. Hooks are
pinned, not turned off: the push gate still runs.

One tool is an exception. The auto-merge gate (`scripts/auto-merge-gate.ts`) is started
through the list in 1, so the pin cannot reach it, and it asks git about the worktree for
itself. Its answer leads to a merge only when auto-merge has been opted into, which it is
not by default, and a merge then also waits on the `ready-to-merge` status of the pull
request's own head commit, read from GitHub (#2698).

Held by `agent-worktree-trust.test.ts`, and by a second half of the gate in
`agent-launch-sites.test.ts` that allows a launcher only a closed set of shapes for a
line that names the worktree. One of those shapes is any line that begins with one of the
launcher's own functions, so what such a line runs is held by the function it calls and
not by that gate.

**4. The readiness check may read GitHub.** `scripts/dispatch-ready-check.sh` was a
classifier that read only what it was given. Its `--trusted-comment-bodies` mode used to
take a login to trust. It now takes none, and identifies the account behind a comment
from the list in 2. A comment that reaches it with only a login is looked up, which is a
live read, and the one read the check makes: given comments that already carry their
account, it makes none.

It keeps a comment whose account is on the list. It also still keeps one whose author
GitHub shows as an owner, member or collaborator, as it did before this change. So an
account with that standing that is not on the list can write the record that makes an
issue dispatchable (#1105, open, and pinned by a test that is named as open). The text an
agent reads is not widened by that: the issue itself is judged by the list alone.

When the read cannot be completed the mode prints nothing, says why, and leaves with a
status of its own, so a caller can tell "could not ask" from "asked, and no trusted
comment holds a record". Its caller picks the newest record among what it is given, so
some of the comments would be worse than none. The dispatcher treats "could not ask" as a
fault of the machine: it starts nothing, writes nothing to the issue, and the issue is
offered again on the next cycle. The two approval scripts stop with an error and write
nothing.

**5. One asserted exception.** `scripts/verify-sealed-claude-start.ts` starts the CLI
without the list, twice. A person runs it by hand to re-check the one start the extension
makes itself, so it has to start the CLI the way the extension does. By design its start
is handed the whole environment of whoever runs it. That is accepted because the start
loads no tool and no MCP server, the prompt is the script's own, and no workflow, git
hook, package script, Claude Code hook or other script in the repository names the
script. `agent-launch-sites.test.ts` lists the two starts by their whole lines, in that
one file, and asserts each of those three things. A third exception is a new decision.

## How this relates to DR-008 and DR-004

**DR-008 (dispatch security): extended. Not amended, not superseded.**

- Its "Layer 1" section (applied now; defence in depth, not a boundary) says credentialed
  operations are removed from the agent and that the token is never in the agent's reach. Decision 1 here is what makes
  the environment half of that sentence true, and a test now holds it. The other half,
  reach, is not delivered: see Residual risk. Decision 3 extends the same layer to the
  launcher's own steps in the agent's worktree, which DR-008 does not mention.
- The closing paragraph of its "Layer 2" section (required before unattended dispatch),
  and its interim update of 2026-06-05, allow unattended runs on issues whose body is
  trusted, which it glosses as self-authored. Decision 2 is that condition in code, for
  triage and issue dispatch. It is not applied to pull request remediation. It also
  defines "trusted" more widely than "self-authored": the pipeline's own App is on the
  list. See Residual risk.
- Layer 2 itself is **not** delivered. An agent's code still runs as the launcher's own
  user. DR-008 calls Layer 1 defence in depth and not a boundary, and everything here is
  Layer 1.

**DR-004 (tiered network consent): applied as it stands.** None of amended, extended or
superseded. Its section "Tier 1: Local Tool Delegation" places agent dispatch, and the
`scripts/` tooling, in Tier 1, where reads go through `gh`. Decision 4 moves one mode of
one script from reading nothing to reading through `gh`, inside that tier. Tier 0 is
untouched: the one file this work changes under `packages/minspec/src` is the regenerated
copy of the review scripts that ship to adopters, and neither the author gate nor the
readiness check is among what ships.

DR-033 (auto-triage and auto-build) is what lets this path run unattended at all. It is
unchanged.

## What would reverse this decision

- The list in 1 turning out to break ordinary builds often enough that names are added
  without reasons. A list that grows by habit is the old scrub again.
- The exact comparison in 2 refusing the pipeline's own issues. Measured not to, on the
  shapes above. The symptom would be issues from listed accounts refused in the drain's
  log as changed while being checked. A quiet queue is not that symptom: the drain was
  dispatching nothing when this was reviewed, for unrelated reasons, so quiet says
  nothing either way.
- Text the pipeline relayed, under the App's identity, starting an agent it should not
  have (#2692). The cheap answer is to take the App off the list and file by hand until
  the writing side can tell the two apart.

Reversing 1 or 2 is cheap in code: both are one library and its call sites. Reversing
them once adopters run the shipped copy of `agent-context.sh` is not; see Costly to
Refactor.

## Alternatives rejected

Recorded per DR-086 section 4: under `autonomy: act` nobody sees these live.

- **Keep extending the list of names to remove.** It holds only the names somebody
  thought of, and it fails silently on the next one. This is what was in place.
- **Trust by repository permission** (collaborator, or write access). A permission is
  granted for other reasons, to review or to push, and it says nothing about whose text
  may start an agent. It also cannot see that an issue's body was edited by somebody
  other than its author.
- **Make the list of accounts configurable from the environment.** A gate with a switch
  is switched off on the first urgent morning, and whatever can set a variable where the
  launcher runs could then add an account. Adding one is meant to be a reviewed edit.
- **Rely on GitHub's interaction limit alone.** It is a repository setting, not code: no
  test holds it and no review sees it change. It is also believed to lapse after a set
  period and need renewing, which was not checked for this record. And it does nothing
  about an edit by somebody with access, or about text the pipeline relays.
- **Build the sandbox now and skip these.** The sandbox is the real boundary, and DR-008
  already says it is unscoped work. The gap here was open on every run. These controls
  are small, and each is still wanted behind a sandbox: an agent inside one should not be
  handed credentials or a stranger's text either. Tracked as #2691.

## Residual risk

- **The agent's code runs as the launcher's user.** A list of variables and pinned hooks
  narrow what it is handed. They are not a boundary. What the agent's own process is not
  handed, other processes of the same user may still hold, and what a process holds its
  own user can read, reviewers included. The author gate is the primary control until
  there is a boundary (#2691).
- **Trusting the App trusts every path that makes it write.** Some of those paths carry
  text the pipeline did not write. The gate sees the account, not where the words came
  from. The paths are listed where the list is defined; nothing here closes it (#2692).
- **Push access is, in effect, on the list.** An account that can push to this repository
  can cause writes under the App's identity, and the gate accepts those. This was
  established by reading how the repository is set up, not by doing it. Today the one
  account with access is the founder. Granting push access to anybody else is granting
  what the list grants (#2698).
- **Pull request remediation trusts push access.** It checks commenters against the list
  and nobody else: not who opened the pull request, wrote its title or pushed its
  commits. The agent it starts runs the branch's own build (#2698).
- **The launcher's own token is not narrowed.** What it is allowed to do is operator
  configuration, and is the size of what is at stake if the rest fails (#2693).
- **A verdict record still counts from an owner, member or collaborator who is not on the
  list.** See decision 4 (#1105).
- **Who applied a role label is not checked.** Whoever may label an issue chooses among
  the roles that exist (#2698).
- **The dispatcher finds its pull request by branch name alone,** at four lookups. A
  branch name does not say which repository a pull request came from. No text reaches a
  prompt this way; it decides which pull request the dispatcher shepherds (#2698).
- **The auto-merge gate is not pinned.** See decision 3 (#2698).
- **The gate that reads `scripts/` is a tripwire.** See decision 1 (#2698).
- **Prompts are passed as one argument.** Five starts hand the CLI its whole prompt as a
  single argument, and the auto-merge summary hands text an agent wrote to `jq` the same
  way. One argument has a size limit set by the system. The two places where comment text
  met that limit were fixed; these were left (#2698).
- **A lookup that never completes is quiet.** An issue whose comment authors cannot be
  read is skipped each cycle with a line in the drain's log and nothing else. Nothing
  counts the skips (#2698).
- **The shared-checkout sync is slower.** Its cost now grows with the square of the
  number of recorded worktrees: the second review measured 14 to 20 seconds a cycle at 90
  worktrees, and it was not measured again for this record. Slower, not wrong (#2698).
- **The exception in 5 holds an inherited environment on purpose.** What keeps that
  acceptable is asserted by a test that reads text. Whether the installed CLI still
  honours "no tools" is the very thing that script is run to find out.
- **Not verified:** the system bash on macOS, and a real drain cycle end to end. The
  first real launch after this merges is the check (#2698).

## Costly to Refactor

1. **`bash "$AGENT_LAUNCH_ENV" <command>` as the way a launch is written.** It is in the
   review scripts that ship to adopters, so changing its shape changes files in other
   people's repositories. Check: the generator's `--check` and the template tests fail on
   a shipped copy that has drifted.
2. **The entry format, `<kind>:<id>`.** Every comparison is made on that string, in one
   place. Check: one table of namesakes and near-misses (a person holding the App's login,
   an App holding the founder's, a number one digit off, the right number under another
   kind) is tried as the author, as somebody who edited the body and as somebody who
   changed the title, and every row is refused on each. The comment paths have namesake
   rows of their own.
3. **What the list in 1 means to a build.** Each name removed later can break a run that
   had come to rely on it. Check: a test writes the list out name by name, so a removal
   is a visible edit. That a value still arrives is asserted only for the handful of
   names the launch tests set, not for each.
4. **Refusing the GitHub Actions account.** Low to change in code, and a decision about
   what the list means (#2694).

## Consequences

- An agent started by this automation is handed no credential in its environment except
  the model login a launch asks for by name. What else its user can reach is unchanged.
- Issues from any account not on the list wait for a person, and say so only where the
  drain prints. That includes the GitHub Actions account (#2694).
- Comments from accounts not on the list are left out of a prompt, visibly.
- The readiness check can now fail for a network reason in one mode. Nothing is started
  on that run, nothing is written to the issue, and it is offered again.
- A `role:` label that is not a plain name is passed over, and the log says how many were.
- Adding a trusted account is a code change.
- One file under `scripts/` starts the CLI with an inherited environment, on a list, with
  its reasons asserted.
