# An agent is started holding only what is listed, and only on text a listed account wrote

> (*MinSpec: Accept ADR*), and DR-086 keeps DR acceptance on the stop list (section 2,
> class 2). An agent never mints the sign-off. This record's live status is its
> frontmatter `status:` field, not this note.

> does not spell out its own id. It is in the frontmatter.

> **Where the code is, and that none of it is live.** All of it is on #2686:

## In plain terms - what this changes for you

An agent the automation starts no longer gets a copy of the shell it was started from. It
gets a short list of ordinary variables and nothing else. A token or key that happens to
be exported where the drain runs does not reach it.

An issue is picked up for triage or dispatch only when every word of it was written by an
account on a list of two: yours, and the pipeline's own App. Anybody else's issue is
refused and waits. So is an issue of yours that somebody else has edited. Editing a
stranger's issue yourself does not make it yours; filing it again does.

What you give up: adding a person whose issues agents may work on is a code change and a
review, never a setting. A tool an agent's build relied on finding in an inherited
variable may now need that variable added to the list, with a reason. And issues filed
by the GitHub Actions account, which used to go to triage, now wait for you (#2694).

## Context

`scripts/` holds the dev-time automation that starts headless agents: issue dispatch,
triage, the review scripts, pull request remediation and the tooling radar. DR-008
(dispatch security) decided, for that automation, that credentials are kept out of the
agent's reach, and that unattended runs are for issues whose text is trusted. Neither was
held by code. This record decides how each is held, and names the one exception.

Triggered by: #1203 (the dispatch-thrash investigation). The scrub described below was
that investigation's fix for one variable; this record is about what the scrub left open.

**The environment.** Every launch sat behind a scrub that removed one named variable from
the launcher's environment and passed every other exported variable through. So an agent
held whatever its launcher held, which is not what DR-008 says an agent holds. The test
beside it read the launcher's source text and never the environment a started agent
actually had, so it stayed green.

A list of names to remove could not have held, however long it grew. It contains the
names somebody thought of. A variable nobody thought of is passed, and nothing fails when
it is: the gap is silent by construction.

**Whose text.** No launcher asked who wrote an issue. The gates between a label and a
launch each judged something else: that triage had run, that no other run held the
issue, that there was quota. The repository is public and an issue form applies the
queue's label for whoever fills it in. An agent that is started runs the project's own
build, which DR-008 itself calls executing arbitrary code by definition.

**The launcher, afterwards.** Keeping a token from the agent says nothing about the
launcher, which still holds it and goes back into the agent's worktree to push, rebase,
run the checks and ask for a review. What it executes there, it executes as itself, in a
directory the agent could write to.

## Decision

**1. An agent's environment is built from a list of names.** A variable reaches an agent
because it is on the list in `scripts/lib/agent-context.sh`, and for no other reason.
Every launcher under `scripts/` starts the CLI through that file. The model's own login
is handed over only when a launch asks for it by name, one login at a time, and a
capability probe is handed none. The list refuses to work if a name shaped like a
credential is ever put on it.

The list is deliberately narrow. It does not carry `npm_config_*`, and it does not carry
`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*` or `GIT_CONFIG_VALUE_*`. A build that relied on
configuration arriving in such a variable, and not from a file under the home directory,
behaves differently. That direction is the safe one, and a name a run needs is added at
the list with the reason beside it.

Held by `agent-launch-sites.test.ts` and `dispatch-env-allowlist.test.ts`, which run the
real launchers against a stand-in for the CLI that records what it was started with, and
by a gate that reads every file under `scripts/` and fails on a start that goes round the
list.

**2. Whose text may start an agent.** An issue is triaged or dispatched only when the
account that opened it, every account that has edited its body, and every account that
has changed its title are all on a list in `scripts/lib/dispatch-author-gate.sh`. Comment
text reaches a prompt only from a listed commenter, and only when everyone who edited the
comment is listed too.

- An entry is an account's kind and its number, never its login. A login can be changed
  and then taken by somebody else.
- The list is two literals in a function body: the pipeline's own App, and the founder.
  There is no variable that adds to it and none that turns the gate off.
- Being a collaborator, or having write access, does not put an account on it. Both can
  be granted later for an unrelated reason.
- The text judged must equal, exactly, the text the prompt is built from. An issue edited
  between the two reads is refused and offered again on the next cycle.
- Whatever cannot be read is a refusal that says so, never a pass.

Held by `dispatch-author-gate.test.ts`. The exact comparison was also measured against
GitHub on 2026-10-10, because a difference between the two reads would refuse every issue
for ever: eight issues in this repository (filed by the App, by the founder and by the
GitHub Actions account; edited; with code blocks; with text outside ASCII; with trailing
whitespace; up to 42,000 characters) and one from another public repository whose body
has carriage returns. Title and body were equal in all nine. No issue in this repository
has a carriage return in its body (1,531 read), which is why that one came from
elsewhere.

**3. What a launcher runs inside an agent's worktree is pinned.** Git operations there
take their hooks from the launcher's own tree and use the git directory recorded when the
worktree was made, before any agent ran in it. The worktree's own code (its tests, its
build) is run the way the agent was, through the list in 1. A tool the launcher needs
there is named by a path in the launcher's own tree. Hooks are pinned, not turned off:
the push gate still runs.

Held by `agent-worktree-trust.test.ts`, and by a second half of the gate in
`agent-launch-sites.test.ts` that allows a launcher only a closed set of shapes for a
line that names the worktree.

**4. The readiness check may read GitHub.** `scripts/dispatch-ready-check.sh` was a
classifier that read only what it was given. Its `--trusted-comment-bodies` mode used to
take a login to trust. It now takes none, and identifies the account behind a comment
from the list in 2. A comment that reaches it with only a login is looked up, which is a
live read, and the one read the check makes: given comments that already carry their
account, it makes none. When that read fails the mode prints nothing and says why. Its
caller picks the newest record among what it is given, so some of the comments would be
worse than none.

**5. One asserted exception.** `scripts/verify-sealed-claude-start.ts` starts the CLI
without the list, twice. A person runs it by hand to re-check the one start the extension
makes itself, so it has to start the CLI the way the extension does. By design its start
is handed the whole environment of whoever runs it. That is accepted because the start
loads no tool and no MCP server, the prompt is the script's own, and nothing in the
repository runs the script. `agent-launch-sites.test.ts` lists the two starts by their
whole lines, in that one file, and asserts each of those three things. A third exception
is a new decision.

## How this relates to DR-008 and DR-004

**DR-008 (dispatch security): extended. Not amended, not superseded.**

- Its "Layer 1" section (applied now; defence in depth, not a boundary) says credentialed
  operations are removed from the agent and that the token is never in the agent's reach. Decision 1 here is what makes
  the environment half of that sentence true, and a test now holds it. Decision 3 extends
  the same layer to the launcher's own steps in the agent's worktree, which DR-008 does
  not mention.
- The closing paragraph of its "Layer 2" section (required before unattended dispatch),
  and its interim update of 2026-06-05, allow unattended runs on issues whose body is
  trusted, which it glosses as self-authored. Decision 2 is that condition in code. It
  also defines "trusted" more widely than "self-authored": the pipeline's own App is on
  the list. See Residual risk.
- Layer 2 itself is **not** delivered. An agent's code still runs as the launcher's own
  user. DR-008 calls Layer 1 defence in depth and not a boundary, and everything here is
  Layer 1.

**DR-004 (tiered network consent): applied as it stands.** None of amended, extended or
superseded. Its section "Tier 1: Local Tool Delegation" places agent dispatch, and the
`scripts/` tooling, in Tier 1, where reads go through `gh`. Decision 4 moves one mode of
one script from reading nothing to reading through `gh`, inside that tier. Tier 0 is
untouched: the one file this work changes under `packages/minspec/src` is the regenerated
copy of the review scripts that ship to adopters, and neither the author gate nor the
readiness check is among what ships.

DR-033 (auto-triage and auto-build) is what lets this path run unattended at all. It is
unchanged.

## What would reverse this decision

- The list in 1 turning out to break ordinary builds often enough that names are added
  without reasons. A list that grows by habit is the old scrub again.
- The exact comparison in 2 refusing the pipeline's own issues. Measured not to, on the
  shapes above. A quiet queue after this merges is the symptom to look for.
- Text the pipeline relayed, under the App's identity, starting an agent it should not
  have (#2692). The cheap answer is to take the App off the list and file by hand until
  the writing side can tell the two apart.

Reversing 1 or 2 is cheap in code: both are one library and its call sites. Reversing
them once adopters run the shipped copy of `agent-context.sh` is not; see Costly to
Refactor.

## Alternatives rejected

Recorded per DR-086 section 4: under `autonomy: act` nobody sees these live.

- **Keep extending the list of names to remove.** It holds only the names somebody
  thought of, and it fails silently on the next one. This is what was in place.
- **Trust by repository permission** (collaborator, or write access). A permission is
  granted for other reasons, to review or to push, and it says nothing about whose text
  may start an agent. It also cannot see that an issue's body was edited by somebody
  other than its author.
- **Make the list of accounts configurable from the environment.** A gate with a switch
  is switched off on the first urgent morning, and whatever can set a variable where the
  launcher runs could then add an account. Adding one is meant to be a reviewed edit.
- **Rely on GitHub's interaction limit alone.** It is a repository setting, not code: no
  test holds it and no review sees it change. It is also believed to lapse after a set
  period and need renewing, which was not checked for this record. And it does nothing
  about an edit by somebody with access, or about text the pipeline relays.
- **Build the sandbox now and skip these.** The sandbox is the real boundary, and DR-008
  already says it is unscoped work. The gap here was open on every run. These controls
  are small, and each is still wanted behind a sandbox: an agent inside one should not be
  handed credentials or a stranger's text either. Tracked as #2691.

## Residual risk

- **The agent's code runs as the launcher's user.** A list of variables and pinned hooks
  narrow what it is handed. They are not a boundary. The author gate is the primary
  control until there is one (#2691).
- **Trusting the App trusts every path that makes it write.** Some of those paths carry
  text the pipeline did not write. The gate sees the account, not where the words came
  from. The paths are listed where the list is defined; nothing here closes it (#2692).
- **The launcher's own token is not narrowed.** What it is allowed to do is operator
  configuration, and is the size of what is at stake if the rest fails (#2693).
- **The exception in 5 holds an inherited environment on purpose.** What keeps that
  acceptable is asserted by a test that reads text. Whether the installed CLI still
  honours "no tools" is the very thing that script is run to find out.
- **Not verified:** the system bash on macOS, and a real drain cycle end to end.

## Costly to Refactor

1. **`bash "$AGENT_LAUNCH_ENV" <command>` as the way a launch is written.** It is in the
   review scripts that ship to adopters, so changing its shape changes files in other
   people's repositories. Check: the generator's `--check` and the template tests fail on
   a shipped copy that has drifted.
2. **The entry format, `<kind>:<id>`.** Every comparison is made on that string, in one
   place. Check: a test holds the file to one comparison and no second spelling.
3. **What the list in 1 means to a build.** Each name removed later can break a run that
   had come to rely on it. Check: the tests assert the values a run needs still arrive.
4. **Refusing the GitHub Actions account.** Low to change in code, and a decision about
   what the list means (#2694).

## Consequences

- An agent started by this automation holds no credential it was not explicitly given.
- Issues from any account not on the list wait for a person, and say so only where the
  drain prints. That includes the GitHub Actions account (#2694).
- Comments from accounts not on the list are left out of a prompt, visibly.
- The readiness check can now fail for a network reason in one mode. It fails closed.
- Adding a trusted account is a code change.
- One file under `scripts/` starts the CLI with an inherited environment, on a list, with
  its reasons asserted.
