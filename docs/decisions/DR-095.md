# DR-095: Mount the broker socket's directory, not the socket

> **Born `proposed` per DR-029** (born-gate: a record is authored `proposed` and
> promoted by a human). This record's live status is its frontmatter `status:`
> field, not this note.

> **On the number.** `main` holds up to DR-093, so `max + 1` looks like DR-094.
> It is taken: **#1956** is open and creates `docs/decisions/DR-094.md`. Following
> DR-093's precedent, this record takes the lowest number no open pull request
> claims, which is DR-095. Open pull requests were enumerated and their changed

> discussed here is the **host** register's DR-079, at

## In plain terms

The container reaches the GitHub App token broker through a Unix socket that is
bind-mounted in from the host. It is mounted as a **file**, and a file mount pins
exactly one inode for the life of the container. When the broker restarts, the old
socket is removed and a new one is created, so the container is left holding a
pointer to something that no longer exists. Every connection is refused.

The trap is that the obvious remedy causes the fault. A token problem looks like a
broker problem, so the broker gets restarted, and the restart is precisely what
severs the mount. The symptom then changes from "the token is rejected" to "there is
no token at all", which reads as an authentication failure rather than a plumbing
one. On 2026-09-23 that inversion cost the fleet, around fifteen concurrent sessions,
**47 hours of GitHub writes**, with the broker restarted twice more before the real
cause was found.

## Context

### The mount, and where it actually points

[`/etc/nixos/home.nix:95`](/etc/nixos/home.nix) declares it:

```nix
{ host = "$XDG_RUNTIME_DIR/gh-app-token.sock"; target = "/tmp/gh-app-token.sock"; mode = "rw"; }
```

The host side is **`$XDG_RUNTIME_DIR`**, which for a user manager is `/run/user/1000`.
It is not `/tmp`; `/tmp/gh-app-token.sock` is only the path the socket is presented at
*inside* the container. This matters for the proposal below, because "mount the
directory" means mounting the systemd user runtime directory, which is a very
different object from a purpose-built socket directory.

The socket unit agrees with the mount, via the `%t` specifier:

```nix
# /etc/nixos/home.nix:1457
ListenStream = "%t/gh-app-token.sock";
SocketMode   = "0600";
Accept       = true;
```

`%t` resolves to `$XDG_RUNTIME_DIR` for user managers
([systemd.unit(5), specifier table](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)),
so both sides name `/run/user/1000/gh-app-token.sock`.

### The severance, as the kernel sees it

Observed in `/proc/self/mountinfo` during the outage, with the `//deleted` tag the
kernel appends to an unlinked bind source:

```
984 971 0:63 /gh-app-token.sock//deleted /tmp/gh-app-token.sock rw,nosuid,nodev,relatime - tmpfs ...
```

Measured consequences, from **#2043** (the stale bind mount kills every agent GitHub
write): `connect()` returns `ECONNREFUSED`; the host journal records **zero** new
socket-activated instances, because the connection never reaches the live socket and
so never triggers activation; and there is no in-container remedy, since the container
has no `CAP_SYS_ADMIN` and cannot re-bind. Only a container restart re-establishes the
path. #2043 measured **0 of 10** mints over roughly 20 minutes while severed, and
**10 of 10** after a restart.

### An operational trap next to this one

Recorded because anyone debugging the broker hits it first and can wrongly conclude the
unit is misconfigured. The service is a systemd **template**
(`gh-app-token-proxy@`, `/etc/nixos/home.nix:1464`) because the socket sets `Accept = true`
and so instantiates one service per connection. Only the `.socket` unit
(`/etc/nixos/home.nix:1454`) can be restarted; restarting the service by unit name fails
with `Unit name is missing the instance name`.

That measurement is **#2110's**, not this record's - `systemctl --user` has no bus in the
agent container, so it could not be re-run here. The structural half is verifiable from the
configuration: the `@` in the unit name at line 1464 is what makes it a template.

### Why no amount of care with the broker avoids this

A pathname `AF_UNIX` socket cannot be re-bound in place. Measured in this container on
2026-09-25:

| Step | Result |
|---|---|
| `bind()` a fresh socket at a path | inode `6699029` |
| `bind()` a second socket at the **same existing** path | **`EADDRINUSE` (errno 98)** |
| `unlink()`, then `bind()` again | inode `6699115`, **different** |

So any listener that returns to the same path must unlink first, and unlink-then-bind
always yields a new inode. This is a property of `bind(2)` on `AF_UNIX`, not a systemd
configuration choice, which closes off the whole family of "make the broker keep its
inode" answers before they are tried.

`RemoveOnStop=` does not rescue it either. It
[defaults to off](https://www.freedesktop.org/software/systemd/man/latest/systemd.socket.html),
so stopping the unit already leaves the node in place. The unlink happens on the way
**in**, because starting requires binding, and binding requires the path to be free.

### The register already held the premise and did not carry it across

This framing, and the citation under it, are taken from the parallel record on **#2110**
(see the credit note at the end). `/etc/nixos/docs/decisions/DR-079.md` already wrote the
mechanism down, about the *other* file mounts in the same list:

> The client and helper are bind-mounted files, which keep the inode they were created
> with, so they reach the container at the next `agent-restart`, not at the switch.

For a static script that inode-pinning is a benign latency property: the file changes only
when a human rebuilds. It was never carried across to the one mount in the same list whose
producer **replaces the inode by design**. That is the root cause in one line: not an
unknown mechanism, an un-transferred one. It is also why this record proposes a change to
the mount rather than to the broker, which is behaving correctly.

### The pattern is already in the same file, one line down

Eight lines below the broker mount, the Postgres socket is mounted the other way, and
the comment says why:

```nix
# /etc/nixos/home.nix:103
# rslave so a PG restart's new socket propagates in.
{ host = "/run/postgresql"; target = "/run/postgresql"; mode = "rw,rslave"; }
```

Postgres survives a restart because its **directory** is mounted, so the container
re-resolves the path on every `connect()` and finds whatever socket currently lives
there. The broker is the one socket in the list that did not get that treatment. The
load-bearing part is the directory, not `rslave`: mount propagation governs mount
events, and no mount event occurs when a file inside an already-mounted filesystem is
unlinked and recreated.

## Decision

**Mount the broker socket's containing directory rather than the socket file, and make
that directory dedicated and read-only.** All three adjectives are load-bearing:

1. **Directory**, so the path is resolved fresh on each `connect()` and follows the
   inode through a broker restart.
2. **Dedicated**, because the directory the socket sits in today is
   `$XDG_RUNTIME_DIR`, and mounting that is not an option (see below).
3. **Read-only**, because a writable directory mount lets the container `unlink` the
   live socket, or replace it with a listener of its own.

### Why the existing directory cannot be mounted as-is

`$XDG_RUNTIME_DIR` is the founder's whole systemd user runtime directory. The host
register's own record at `/etc/nixos/docs/decisions/DR-079.md` states what the
container split deleted:

> Nothing mounts `/run/user/1000/bus`, `$SSH_AUTH_SOCK`, the X cookie, `~/.cache` or
> `~/.config/VSCodium` any more, in any container, so there is no conditional to
> invert.

`/run/user/1000/bus` is **inside** `$XDG_RUNTIME_DIR`. Mounting that directory would
re-grant, as a side effect, the precise mount that record removed on purpose. It would
also carry in a second broker socket already living there
(`ListenStream = "%t/xdg-open-proxy.sock"`, `/etc/nixos/home.nix:1342`) and, by the
ordinary layout of a systemd user manager's runtime directory, `systemd/private` (the
manager's control socket, and so arbitrary host execution as `jason`, which reaches the
App private key at `~/.claude/.secrets/minspec-sdd.pem` that the mount list deliberately
excludes) along with the keyring and the rest of the session's sockets.

**What the bus is worth is measured, not speculated.** `/etc/nixos/docs/decisions/DR-079.md:133`
records that a read-only `SearchItems` from inside the container returned **50 unlocked
items**, including LUKS passphrases, WireGuard keys, the restic repository password, the
browser `os_crypt` keys and a Marketplace publisher token. Host DR-077 and host DR-079
between them spent two decisions removing that path. An availability fix that restores it
as a side effect would be the worst change in this record. (This measurement was surfaced
by the parallel record on **#2110**; it is cited here because it converts the strongest
argument against a naive directory mount from an assertion into a number.)

> **One epistemic note**, because the difference matters to a reviewer deciding how hard to
> spot-check. The bus, the second socket, the token cache below and the 50-item figure are
> each **cited from a file**. `systemd/private` and the keyring are **inferred** from the
> standard layout of a user runtime directory and were not observed, because the host's
> `/run/user/1000` is not mounted into this container and so could not be listed from where
> this record was written. Nothing rests on the inferred half.

It would also hand over the token cache. `/etc/nixos/home.nix:1399` puts it at
`$XDG_RUNTIME_DIR/gh-app-token.cache`, a **plaintext installation token on disk** with
a 50-minute TTL. The whole point of the broker is that the container receives a token
by asking and never holds the means to mint one; a mount that includes the cache hands
over a credential file directly.

**So the dedicated directory is part of the change, not a refinement of it.** A
proposal that stops at "mount the directory" is a proposal to undo the host record's
containment.

### Why read-only is safe, and what it buys

A writable directory mount would let any agent session delete the live socket, denying
the broker to the whole fleet until a human restarts the unit, or replace it with its
own listener. Read-only removes that.

The obvious worry is that connecting to a Unix socket requires write permission, so a
read-only mount might refuse `connect()`. Read from kernel source, it does not:

- `net/unix/af_unix.c:1225` performs `path_permission(&path, MAY_WRITE)` when
  connecting to a pathname socket, so `MAY_WRITE` is indeed required on the socket
  inode.
- `sb_permission()` in `fs/namei.c` refuses `MAY_WRITE` on a read-only filesystem for
  `S_ISREG`, `S_ISDIR` and `S_ISLNK` only. **`S_ISSOCK` is not in that list**, so a
  socket is not covered.
- `MNT_READONLY` appears **nowhere** in `fs/namei.c`'s permission path. Mount-level
  read-only is enforced at each mutating call site through `mnt_want_write(path.mnt)`,
  which is what blocks `unlink`, `rename` and create.

That is the exact split wanted: `connect()` permitted, mutation denied. The socket
itself keeps `SocketMode = 0600` and the container runs as the same uid (1000), so the
permission bits are unchanged.

The in-container client only connects. It never writes into the directory
(`/etc/nixos/home.nix:1497` onward: an `[ -S ]` test, then a `socket.connect()` in
Python), so nothing in the current path needs write access.

> **This claim is reasoned from kernel source and has NOT been executed - it is
> unverified, and it is tracked as #2104 (verify a read-only socket directory mount
> permits `connect()`).** A read-only bind mount needs `CAP_SYS_ADMIN`, which the agent
> container does not have, so it could not be demonstrated from where this record was
> written. It is stated here rather than only in the pull request because the record is
> what outlives the thread, and an unmarked claim in a decision record is the false
> signpost this project exists to prevent.
>
> It is a condition on the diff below, not a detail: **do not apply the `ro` mode until
> #2104 reports.** If `connect()` turns out to be refused, the fallback is `rw` on the
> dedicated directory, which keeps the whole availability fix and loses only the
> anti-tamper property.

### The proposed diff

Four sites, all in `/etc/nixos/home.nix`. **Applying it is the founder's keystroke**;
this record does not edit the host, and nothing under `/etc/nixos/` was modified in
producing it.

```diff
@@ line 95 - the mount
-    { host = "$XDG_RUNTIME_DIR/gh-app-token.sock"; target = "/tmp/gh-app-token.sock"; mode = "rw"; }
+    # A DIRECTORY, so a broker restart's new socket is picked up without a container
+    # restart: a file mount pins one inode and dies with it (DR-095). Dedicated, so
+    # this is not a mount of $XDG_RUNTIME_DIR, which holds the session bus, the user
+    # manager's control socket and the plaintext token cache. ro, so a session cannot
+    # unlink the live socket or shadow it; connect() to a socket is unaffected by a
+    # read-only mount (S_ISSOCK is outside sb_permission's EROFS set).
+    { host = "$XDG_RUNTIME_DIR/gh-app-token"; target = "/tmp/gh-app-token"; mode = "ro"; }

@@ lines 851-854 - the launcher's pre-mount liveness check
-      if [ ! -S "$_RUNDIR/gh-app-token.sock" ]; then
+      if [ ! -S "$_RUNDIR/gh-app-token/gh-app-token.sock" ]; then
           systemctl --user start gh-app-token-proxy.socket 2>/dev/null || true
           for _i in 1 2 3 4 5; do
-              [ -S "$_RUNDIR/gh-app-token.sock" ] && break
+              [ -S "$_RUNDIR/gh-app-token/gh-app-token.sock" ] && break

@@ lines 1457-1458 - the socket unit
-      ListenStream = "%t/gh-app-token.sock";
+      ListenStream = "%t/gh-app-token/gh-app-token.sock";
       SocketMode = "0600";
+      # systemd creates the parent directory of a filesystem ListenStream itself;
+      # DirectoryMode governs its mode and defaults to 0755. Pinned to 0700 to match
+      # the 0700 that $XDG_RUNTIME_DIR already carries.
+      DirectoryMode = "0700";

@@ line 1497 - the in-container client
-      SOCK="/tmp/gh-app-token.sock"
+      SOCK="/tmp/gh-app-token/gh-app-token.sock"
```

No `tmpfiles` rule and no `RuntimeDirectory=` is needed. systemd.socket(5) states of
`DirectoryMode=`: *"If listening on a file system socket or FIFO, the parent
directories are automatically created if needed."* `RuntimeDirectory=` would actively
hurt here, since it is removed when the unit stops unless
`RuntimeDirectoryPreserve=yes` is also set, which would recreate this very bug one
level up: the **directory** would then be the thing that changes inode on restart.

The ordering the launcher already has is correct for this and needs no change: the
socket unit is started at line 851, which creates the directory, and only then does the
generated preflight at line 865 assert every mount source exists. The comment at line
859 explains why that order matters, and it applies unchanged to a directory source.

The token cache stays at `$XDG_RUNTIME_DIR/gh-app-token.cache`, a **sibling** of the new
directory and outside the mount. It must never be moved into it.

`/etc/nixos/home.nix:24` states that this list **is** the boundary: the launcher generates
every `--volume` from it and emits no other, and `tests/agent-container-no-user-credential.sh`
asserts it is the sole producer. A new mount line is therefore a change to the security
boundary and belongs in that list, never bolted on beside it. `agent-mounts.json`
(`/etc/nixos/home.nix:1482`) is generated from the same attribute, so the property test
follows automatically rather than needing a parallel edit.

### Applying it partially is the thing to be careful about

The four sites are **coupled**: the unit's `ListenStream`, the mount line, the launcher's
liveness path and the client's `SOCK` must all agree. Applying some but not all leaves the
socket live at a path the container does not mount.

The good news is that this fails loudly rather than silently, which is the opposite of the
defect being fixed. The generated preflight (`/etc/nixos/home.nix:113`, invoked at 865)
asserts every mount source exists before the container starts, so a half-applied change
**refuses to start the container** rather than starting it broken. The bad news is the
honest other half: that refusal stops every agent until the change is completed, so this is
a single-sitting edit plus rebuild, not something to leave half-landed overnight.

*(This risk analysis is adapted from the parallel record on **#2110**, which costed it more
carefully than the first draft of this one did.)*

### Residual risk: this narrows the trigger, it does not remove the class

The honest limit of the fix, and the most important thing folded in from **#2110**.

A directory mount pins the **directory's** inode by exactly the same rule that pins a
file's. If `$XDG_RUNTIME_DIR` itself is destroyed and recreated, the dedicated
subdirectory goes with it and the container is stale again. `systemd-logind` removes a
user's runtime directory when their last session ends unless lingering is enabled.

**This record does not establish which way lingering is set on this host.** Verified here:
the string `linger` appears exactly **once** in all of `/etc/nixos`, in an unrelated comment
at `home.nix:1715`, so no `enable-linger` is declared in configuration. But lingering can
also be set imperatively under `/var/lib/systemd/linger`, and that path is **not reachable
from the agent container** (checked: it does not resolve, and the only `/var/lib` entries in
this container's `mountinfo` are Docker's own `hosts`, `hostname` and `resolv.conf` files).
So the question is genuinely open from here rather than answered either way.

What changes is the **frequency and the coupling**, which is the whole value:

| | trigger today | trigger after |
|---|---|---|
| What severs the mount | restarting the broker | ending the host login session entirely |
| How often | frequent, and it is the documented remedy for unrelated token trouble | rare, and it already implies restarting everything |
| Relationship to the symptom | the remedy **causes** the fault | unrelated to token trouble |

The residual case is precisely why detect-and-alarm (#2046) is carried as a companion rather
than dropped: when the rare version does happen, the container should say so in one line
instead of costing another 47 hours.

## Alternatives rejected

Recorded because under `act` autonomy nobody sees them live (DR-086 §4, the autonomy
axis: an agent may act on its own recommendation, so the written record is the only
review path).

| Option | Why rejected |
|---|---|
| **Mount `$XDG_RUNTIME_DIR` itself** - the naive reading of "mount the directory" | Re-grants `/run/user/1000/bus`, which `/etc/nixos/docs/decisions/DR-079.md` records as deliberately deleted, plus `systemd/private` (host execution as `jason`, reaching the App key) and `gh-app-token.cache` (a plaintext token). It would trade a 47-hour availability fault for a standing containment breach. This is the reason the dedicated directory is part of the decision rather than a detail of it. |
| **Do nothing; document the runbook** | The container restart is a known fix now, so this is tempting and it is the status quo that produced the outage. Rejected on three measured grounds: the failure presents as an auth problem, not a mount problem, which is what cost the 47 hours; the natural response to an auth problem is to restart the broker, which **causes** the fault, so the runbook has to fight an instinct rather than inform one; and **the outage suppresses its own bug report**, since filing an issue about the broker requires the broker (#2043's own observation). A runbook nobody can reach the tracker to consult is a poor gate. |
| **Make the broker never unlink, or re-bind the same inode** | **Impossible, measured, not merely awkward.** `bind()` over an existing path returns `EADDRINUSE` (errno 98) and `unlink` + `bind` yields a different inode (6699029 then 6699115, this container, 2026-09-25). `RemoveOnStop=` already defaults to off, so the removal is not on the stop path to be disabled; the unlink is forced by the start path, because binding requires a free path. Checked before dismissing, as asked. |
| **Use an abstract-namespace socket** (`@gh-app-token`), which has no filesystem inode to go stale | Genuinely attractive, and it dissolves the problem rather than working around it. Fatal on scope: abstract sockets are scoped to the **network namespace**, and the container has its own. It would only work by sharing the host network namespace, which is a far larger grant than the single socket being replaced, and pushes against the same containment the first row protects. |
| **Move the broker to a TCP port on loopback** | Removes the inode class completely, since a port is resolved at connect time. Rejected on boundary: it makes the broker reachable by every process in the container's network namespace with **no filesystem gate at all**, trading a rare availability fault for a permanent widening of the identity boundary the host record exists to narrow. (Surfaced by the parallel record on #2110.) |
| **`rslave` or other propagation on the existing file mount** | Does not address it. Propagation governs mount events; unlinking and recreating a file inside an already-mounted filesystem generates none. The Postgres line's `rslave` is not what makes Postgres survive a restart; its directory mount is. |
| **Detect severance and restart the container automatically** | A self-heal on the right signal, but the remedy is disproportionate: a container restart kills every live session mid-work, around fifteen of them. Acceptable at most as a consented last resort, never as the primary fix, and it leaves the fault in place. |
| **Detect and alarm** - have the container notice `//deleted` and say so loudly | **Complementary, not an alternative**, and it is called out as such rather than listed to be dismissed. It shortens the outage; it does not prevent the severance, and on its own it leaves the trap intact, because the loud alarm still invites a broker restart. It is worth doing anyway and is already filed as **#2046** (the `-S` liveness test passes on a stale inode and the errno is discarded). Note that the directory mount **also** repairs that test's meaning: today `[ -S "$SOCK" ]` passes against the dead inode, which is why the client misreports a refusing socket as a missing one; under a directory mount, `-S` tests the socket that is actually there. |

## Consequences

- **Applying this costs exactly one more container restart, and it is the last one.**
  The client script is itself a file bind-mount of a Nix store path
  (`/etc/nixos/home.nix:93`), so a `home-manager switch` replaces the store path while
  running containers keep the old inode. The new socket path therefore does not reach a
  live container. This is the same defect class as the one being fixed, benign only
  because the cutover is planned. Worth knowing before applying it and expecting live
  sessions to heal.
- **A broker restart stops being a fleet-wide outage** and becomes a sub-second gap.
  That also makes the host record's operational advice safe to follow again: restarting
  the unit is currently the worst available response to a token fault.
- **The container gains the ability to enumerate the dedicated directory.** Read-only,
  and it will contain exactly one socket, but it is a new capability compared with a
  single-file mount and should be stated rather than glossed. It is the price of the
  path being resolved fresh.
- **One more moving part in the mount list**, and a directory source rather than a file
  source in the preflight. The preflight's `[ -e ]` is satisfied by either.
- **The severed state becomes rare, which makes it harder to recognise** if it ever
  recurs by another route. This is the ordinary cost of removing a fault's main cause,
  and it is an argument for doing #2046 as well rather than instead.

## Risks

| Risk | Likelihood · Impact | Mitigation |
|---|---|---|
| A read-only mount refuses `connect()`, so the fix breaks the broker outright | **Low** · **Critical** | Reasoned from `fs/namei.c` `sb_permission` (`S_ISSOCK` outside the `EROFS` set) and the absence of `MNT_READONLY` from the permission path, but **not executed** - no `CAP_SYS_ADMIN` in the container. **Blocking condition on the `ro` mode, tracked as #2104**; fallback is `rw` on the dedicated directory, which keeps the availability fix |
| The change is applied to some of the four sites but not all | Med · **High** | Fails loud, not silent: the generated preflight refuses to start the container on a missing mount source. Cost of that safety is that agents stop until the edit is completed, so it is a single-sitting change |
| `$XDG_RUNTIME_DIR` is itself recreated (session ends without lingering), taking the dedicated directory with it | Low · High | Not removed by this change, only made rare and decoupled from token trouble. Lingering state is undetermined from the container; #2046 is the companion that makes the rare case say so in one line |
| Someone later moves `gh-app-token.cache` into the dedicated directory for tidiness, handing the container a plaintext token | **Med** · **Critical** | Called out in the diff comment and above; the cache is a deliberate sibling. Wants a test asserting the mounted directory contains nothing but the socket (follow-up below) |
| A future edit "simplifies" the dedicated directory back to `$XDG_RUNTIME_DIR` | Low · **Critical** | The first row of the rejected-alternatives table exists to be found by that editor, and the diff carries the reason inline rather than only here |
| `RuntimeDirectory=` is added later for tidiness, recreating the bug at the directory level | Low · High | Stated explicitly in the decision; `DirectoryMode=` is the correct knob and systemd creates the parent itself |
| The cutover restart is skipped and live sessions silently keep the old path | **Med** · Med | First consequence above; the old socket path should also be removed from `$XDG_RUNTIME_DIR` so a stale node cannot answer |
