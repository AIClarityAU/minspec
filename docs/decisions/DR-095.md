## In plain terms

The container talks to the token broker through a single file on the host. That file is not
a name the container looks up each time it connects. It is one specific object, pinned at the
moment the container started. When the broker restarts, the host throws that object away and
creates a new one. The container is still holding the old one, and nothing on the host can
hand it the new one.

The cruel part is the remedy. When tokens stop working, the obvious thing to try is
restarting the broker. That is the exact action that severs the mount, and doing it again
severs it again. The only thing that reconnects the container is restarting the container.

## Context - what this already cost

On 2026-09-23 the founder restarted the broker to fix an unrelated token problem. That
restart severed the mount, and every agent session on the machine lost GitHub write access
for **47 hours**: roughly fifteen sessions, a dead autonomous drain, two finished fixes
stranded unpushed, and a backlog of issues that could not be filed.

Filing an issue about the broker also requires the broker, so the outage suppresses its own
bug report. That is recorded in **#2043 (stale socket bind mount kills agent GitHub
writes)**, which measured 0 of 10 consecutive mint attempts succeeding over roughly twenty
minutes, and 10 of 10 succeeding immediately after a container restart.

## The mechanism

**The mount.** `/etc/nixos/home.nix:95`, inside the `agentMounts` list:

```nix
{ host = "$XDG_RUNTIME_DIR/gh-app-token.sock"; target = "/tmp/gh-app-token.sock"; mode = "rw"; }
```

**The producer.** The broker is a systemd socket-activated user unit. The socket is declared
at `/etc/nixos/home.nix:1457` as `ListenStream = "%t/gh-app-token.sock"`, and systemd unlinks
and recreates that socket when the unit restarts.

**Why a file mount cannot follow it.** A bind mount of a *file* attaches the container's
mount entry to that file's inode. Unlink plus recreate leaves the mount on the orphaned
inode, and `/proc/self/mountinfo` names the condition outright - the `//deleted` suffix seen
during the outage:

```
984 971 0:63 /gh-app-token.sock//deleted /tmp/gh-app-token.sock rw,nosuid,nodev,relatime - tmpfs ...
```

A bind mount of a *directory* attaches to the directory, and the socket name inside it is
resolved at each `open()`. A replacement socket created in that directory is therefore
visible with no container restart.

**The host journal shows nothing, and that is diagnostic.** Socket activation fires when a
connection reaches the live socket. The container never reaches it, so zero new instances are
spawned and no journal entry can exist for a container-side attempt. The client shim's own
error text tells the reader to check `journalctl` (`/etc/nixos/home.nix:1519`), which sends
them to a guaranteed-empty log.

### The gates that answer "present" for a dead socket

Two checks stand between a broken mount and a working agent, and both pass:

1. **Start time.** The launcher preflight (`/etc/nixos/home.nix:862` onward, generated from
   `agentMounts`) asserts every mount source exists before the container starts. It runs on
   the host, where the socket is genuinely present and live. It has nothing to say about what
   the container is holding afterwards.
2. **Run time.** The in-container client tests the socket with `[ -S "$SOCK" ]`
   (`/etc/nixos/home.nix:1497` onward). `-S` interrogates the inode, and the orphaned inode is
   still a socket, so the test passes and the connection error is discarded. That is the
   separate defect tracked by **#2046 (the -S liveness test passes on a stale inode and the
   errno is discarded)**.

**Socket present is not socket live**, and no gate in the system currently distinguishes the
two. Per constitution invariant 2 and **DR-066 (no silent gate)**, an availability check that
cannot fail is not a check.

### The register already held the premise and did not carry it across

**Host DR-079 (agent-only container runtime)**, at
`/etc/nixos/docs/decisions/DR-079.md:127`, writes:

> The client and helper are bind-mounted files, which keep the inode they were created with,
> so they reach the container at the next `agent-restart`, not at the switch.

Inode pinning was understood and recorded. For a *static script* it is a benign latency
property. The reasoning was never carried to the one mount in the same list whose producer
replaces the inode **by design**. This is the whole root cause: not an unknown mechanism, an
un-transferred one.

### The precedent is three lines further down the same list

`/etc/nixos/home.nix:102-103` already solves this for Postgres, and says so:

```nix
# rslave so a PG restart's new socket propagates in.
{ host = "/run/postgresql"; target = "/run/postgresql"; mode = "rw,rslave"; }
```

Postgres is mounted as a **directory**, explicitly so that a producer restart survives. The
`rslave` flag there governs sub-mount propagation, which is a separate concern; the property
that makes a PG restart survivable is the directory shape. The pattern this record proposes is
already sanctioned in the same list, for the same reason.

### A second trap worth recording

The broker service is a systemd **template**. Restarting it by unit name fails:

```
$ systemctl --user restart gh-app-token-proxy@.service
Failed to restart gh-app-token-proxy@.service: Unit name is missing the instance name.
```

Only the `.socket` unit (`/etc/nixos/home.nix:1454`) can be restarted; the service
(`/etc/nixos/home.nix:1464`) is instantiated per connection. Anyone debugging this hits the
template error first and can easily conclude the broker is misconfigured.

## Options considered

### Option A - bind-mount a dedicated directory that contains only this socket (recommended)

**Mechanism.** Give the broker its own directory under the host runtime dir, point
`ListenStream` at a socket inside it, mount the **directory** into the container, and update
the client shim's path. A recreated socket is then found by name at connect time.

**Cost.** Three coupled edits in one file plus a rebuild, and one container restart to adopt
the new layout. The client shim is itself a read-only bind-mounted file, so per host DR-079
(agent-only container runtime) the new path reaches a running container only at the next
`agent-restart`. You pay one restart once, to stop paying it on every broker restart forever.

**Risk.** The three edits are coupled: the unit's `ListenStream`, the mount line, and the
client's `SOCK` must agree, and a partial application leaves the socket live at a path the
container does not mount. The launcher preflight fails closed on a missing mount source, so a
partial application refuses to start the container rather than starting it broken - loud, but
it does mean a half-applied change stops agents until it is completed. The launcher must also
`mkdir -p` the new directory before the preflight runs, exactly as it already does for the
directories it owns (`/etc/nixos/home.nix:841`).

### Option B - accept it, and document the container restart as the mandatory follow-up

**Mechanism.** Change nothing. Add a line to the broker's documentation saying that any
`systemctl --user restart gh-app-token-proxy.socket` must be followed by `agent-restart`.

**Cost.** Zero implementation, and the trap stays armed.

**Risk.** This is the option that already failed. The rule has to be remembered by whoever
restarts the broker, at the moment they are debugging something else, and the failure is
silent, delayed, and shaped like a different problem (it surfaced as a security alarm, not an
outage - see **#2044, the IDENTITY banner reports an availability failure as a possible
founder-credential leak**). It is prose where a gate belongs, which the constitution names as
the failure mode. The measured price of one such lapse is 47 hours.

### Option C - make the failure self-diagnosing (a backstop, not an alternative)

**Mechanism.** Have the client actually attempt the connection rather than stat the inode,
and on `ECONNREFUSED` print the true cause and the true remedy: the bind mount is stale, the
host is fine, restart the container. Drop the `journalctl` hint for the container case, where
no entry can exist. This is **#2046 (the -S liveness test passes on a stale inode)** already
filed.

**Cost.** Small, and it fixes none of the outage - the tokens still do not mint.

**Risk.** On its own it is a comfort, not a fix. Its value is that most of the 47 hours was
*diagnosis*, and it collapses that to one line of output for this cause and for any future
cause of a stale mount.

### Options rejected before costing

**Mounting `$XDG_RUNTIME_DIR` itself.** This is the naive form of Option A and it must not be
done. See the boundary section below.

**Moving the broker to a TCP port on loopback.** A port is resolved at connect time, so it
removes the inode class completely. It also makes the broker reachable by every process in the
container's network namespace with no filesystem gate at all, which trades a rare availability
fault for a permanent widening of the identity boundary that host DR-079 (agent-only container
runtime) exists to narrow. Not worth it.

## Decision

Adopt **Option A**, the dedicated-directory mount, and carry **Option C** as its backstop
under **#2046 (stale-inode liveness test)**. Option B is rejected: its only merit is costing
nothing to write, and it has already been run as the live experiment.

### The exact change

All three edits are in `/etc/nixos/home.nix`. They are the founder's to apply and they need a
rebuild; nothing here has been applied.

**1. The socket unit,** at line 1457 - move the socket into its own directory:

```nix
ListenStream = "%t/claude-agent/gh-app-token.sock";
```

**2. The mount,** replacing line 95 - mount the directory, not the file:

```nix
{ host = "$XDG_RUNTIME_DIR/claude-agent"; target = "/tmp/claude-agent"; mode = "rw"; }
```

**3. The client shim,** at line 1497 - follow the target:

```nix
SOCK="/tmp/claude-agent/gh-app-token.sock"
```

**4. The launcher** must create the directory before the preflight reads it. Extend the
existing `mkdir -p` block at line 841 with `"$_RUNDIR/claude-agent"`, and update the
socket-warmup test at line 851 to the new path.

Then rebuild and restart the agents:

```bash
cd /etc/nixos && sudo nixos-rebuild switch --flake .#k7
```

```bash
agent-restart
```

Verify the mount is a directory and carries no `//deleted` marker, from inside a fresh agent
session:

```bash
grep claude-agent /proc/self/mountinfo
```

### The boundary this decision does NOT cross

**The container must not mount `$XDG_RUNTIME_DIR` itself.** The obvious reading of "mount the
containing directory" is to mount `/run/user/1000`, and that would be the worst change in this
record. That directory holds the session D-Bus socket, and host DR-079 (agent-only container
runtime) measured what that socket yields: a read-only `SearchItems` from inside the container
returned **50 unlocked items**, including LUKS passphrases, WireGuard keys, the restic
repository password, the browser `os_crypt` keys, and a Marketplace publisher PAT. Host DR-077
and host DR-079 between them spent two decisions deleting that path. Mounting the parent
directory restores it silently, as a side effect of an availability fix.

The `agentMounts` list is itself the security boundary - `/etc/nixos/home.nix:24` states it,
and a property test asserts the generated block is the sole producer of `--volume`. A new
mount line is a change to the boundary and belongs in that list, never bolted on beside it.
The directory this record proposes is created for this purpose and contains exactly one
socket, which is what keeps the boundary the same width as it is today.

### Residual risk, stated plainly

Option A **narrows the trigger; it does not remove the class.** A directory mount pins the
*directory's* inode by the same rule that pins a file's. If `$XDG_RUNTIME_DIR` is destroyed
and recreated, the dedicated subdirectory's inode is replaced too and the container is stale
again. `systemd-logind` removes a user's runtime directory when their last session ends unless
lingering is enabled for that user; no `enable-linger` appears anywhere in `/etc/nixos`, but
lingering can also be set imperatively under `/var/lib/systemd/linger`, which the agent
container does not mount, so **this record does not establish which way it is set here.**

What changes is the frequency and the coupling. Today the trigger is "restart the broker",
which is frequent and is the documented remedy for unrelated token trouble. After this change
the trigger is "log out of the session entirely", which is rare and already implies restarting
everything. The residual case is precisely why Option C is carried rather than dropped: when
it does happen, the container should say so in one line instead of costing another 47 hours.
