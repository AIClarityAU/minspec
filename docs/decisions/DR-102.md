# Checkbox state leaves the canonical approval hash

> **Born `proposed` per DR-029 (decisions are born proposed).** Acceptance is a separate
> human act (*MinSpec: Accept ADR*); an agent never mints the sign-off. This record's live
> status is its frontmatter `status:` field, not this note.

> **On this record's number.** Taken as the highest decision id on any branch this checkout
> could see, plus one, on 2026-10-04: every remote-tracking ref (fetched the same day) and
> every local branch. That is an offline stand-in for the collision gate
> (`scripts/check-dr-id-collision.ts`), which also reads open pull requests and could not
> be run from the network-less dispatch that wrote this. If the gate reports a different
> next free id on the pull request, renumber. The id is not spelled out in this heading or
> body because `packages/minspec/tests/parent-register-refs.test.ts:43` reads a three-digit
> decision id in `docs/` prose as a reference to another register (#2148 decides the
> general rule); it is in the frontmatter and the file name.

## In plain terms - what this changes for you

Today, ticking an Acceptance Criteria box in a spec you approved throws your approval
away, because the `x` is inside the bytes you signed. So nobody ticks them: this
repository has 358 acceptance-criteria checkboxes in `requirements.md` files and not one
is ticked.

After this change, ticking or unticking a box does not touch your approval. Rewording a
criterion, adding one, or deleting one still does. The price is that the hash no longer
sees which boxes are ticked, so a document must never use a tick to record a *choice*.

## Context

DR-035 (normalize checkbox state before hashing) made this decision on 2026-06-19 and was
accepted. It was never built. It named `hashContent()` in `approval.ts` and `sha()` in
`spec-gate.py`; approval hashing shipped instead through DR-034 (approval foundation) and
SPEC-022 (its spec) as `canonicalizeSpec()` / `specHash()`, which has no checkbox step
(`packages/shared/src/canonical.ts:89-123`, `scripts/hooks/canonical.py:56-80`). On
2026-07-12 a documentation-honesty pass (commit `0e7b1d67`) changed DR-035's status from
`accepted` to `superseded` because its body claimed an implementation that did not exist.
No record superseded it. The register has therefore carried a decision that is neither in
force nor replaced, and the issue it answers, #224, is still open.

This record replaces DR-035 properly: the same decision, restated against the hasher that
actually exists, with the grammar pinned, the migration cost measured, and the parts
DR-035 got wrong corrected.

### The mechanism, observed

`canonicalizeSpec` normalizes line endings, strips the lifecycle keys `status` and
`phases` from frontmatter, collapses relative link targets, and strips trailing whitespace.
Nothing in it touches a `[x]`. Run on a five-line spec with one acceptance criterion at
commit `a482aee6`, `canonical.py`'s `spec_hash` returns a digest beginning `1ae52a5edef7`
unticked and `1fed027cf63b` ticked. One byte, different hash, approval `stale`.

### Measured at commit `a482aee6` (2026-10-04)

Computed by walking `.minspec/approvals/**`, `specs/**/*.md`, `docs/decisions/DR-*.md` and
`docs/epics/**/*.md` with the shipped Python canonicalizer and the grammar in Decision 2.

| Measurement | Value |
|---|---|

Two things follow. First, the friction #224 describes is visible as an absence: hundreds of
acceptance criteria, many in specs whose code shipped, none ticked. Second, **the new hash
equals the old hash for every record that is fresh today**, because normalization is the
identity on a document with no ticked box. At this commit the change voids no approval and
needs no re-stamp. DR-035 said the opposite ("existing stored hashes become stale on
deploy... all specs need one re-approval"); that was inferred, not measured, and it is
wrong for this corpus.

The issue's premise that `tasks.md` is body-only and so outside the gate is also no longer
uniformly true: all 21 `tasks.md` files under `specs/` now open with frontmatter, and 5 of
them contain a `tier:` line.

## Decision

### 1. Ticked and unticked task-list items hash identically

The canonical form gains one step: in the **body** of the document, every ticked task-list
marker is rewritten to the unticked marker before hashing. Frontmatter is not touched.

| Edit to an approved document | Hash | Approval |
|---|---|---|
| Tick or untick a task-list item | unchanged | holds |
| Change the text of an item | changes | void |
| Add or remove an item | changes | void |
| Change a marker to anything other than ticked or unticked (`[~]`, `[-]`) | changes | void |
| Any other edit | changes, as today | void |

### 2. The grammar is pinned here, in ASCII character classes only

A line is a ticked task-list line when it matches, from the start of the line:

1. zero or more spaces or tabs;
2. zero or more block-quote prefixes, each a `>` followed by zero or more spaces or tabs;
3. a list marker: one of `-`, `*`, `+`, or one to nine ASCII digits followed by `.` or `)`;
4. one or more spaces or tabs;
5. `[x]` or `[X]`;
6. then a space, a tab, or the end of the line.

Only the `x` changes, to a single space. The line keeps its length and every other byte.
As one expression, identical in both languages:

```
^([ \t]*(?:>[ \t]*)*(?:[-*+]|[0-9]{1,9}[.)])[ \t]+)\[[xX]\](?=[ \t]|$)    ->    $1[ ]
```

It is applied per line, after the document has been split on `\n`, so neither language's
multi-line anchor rules enter into it.

`\s` and `\d` are forbidden in this expression. Python's `\d` matches every Unicode
decimal digit in a text pattern and JavaScript's matches ASCII only, and the two
languages' `\s` already disagree on four code points in the existing trailing-whitespace
step (#1668, filed, not re-run here). An expression written with either would add a second
latent divergence to a function whose whole contract is byte-identical output.

This is deliberately **not** "whatever GitHub renders as a task list". It is a line
pattern. It does not know about fenced code blocks, indented code blocks or HTML comments,
so a `- [x]` inside a code sample is normalized like any other. The alternative is recorded
below and put to the human in the implementing spec.

### 3. One rule for every hashed document

`canonicalizeSpec` takes a string and no path. The step applies to whatever is hashed
through it: requirements, design and task documents today, and decision records and epics
once they carry hash-locked records under DR-062 (cross-artifact approval validity). No
per-file-type or per-heading switch.

### 4. No migration is built; a standing test guards the one way this could void a sign-off

A record minted under the old hash is void under the new one only when the document it
covers contained a ticked item when it was approved. That population is zero here
(measured above). So:

- No re-stamp tool, no new sidecar field, no record version.
- A standing test asserts that no sidecar is fresh under a frozen copy of the pre-change
  canonicalizer while stale under the shipped one. It is safe to leave running after the
  change lands: a record minted by the new hasher can only match the old one when its
  document has no ticked item, and then both hashes agree. If someone approves a ticked
  document before this lands, the test fails the build and names the record.
- A record that is stale today **only** because a box was ticked after approval becomes
  fresh the moment the step ships, with no write. That is this decision applied to the
  past, not a side effect: every byte the new hash covers is a byte the human signed. The
  population is zero at `a482aee6`. The implementing change reports the population by path
  when it lands.

### 5. All three copies change in one commit

The Node twin (`packages/shared/src/canonical.ts`), the Python twin
(`scripts/hooks/canonical.py`), and the generated copy of the Python twin embedded in
`packages/minspec/src/lib/ci-review-templates.ts` (regenerated by
`scripts/gen-ci-templates.mjs`, freshness gated by Rule 12 in
`scripts/validate-frontmatter.ts:533`). Parity is witnessed by new hand-pinned golden
pairs in `packages/minspec/tests/fixtures/canonical/`, the existing directory both twins
are already tested against.

## Alternatives rejected

| Option | Why not |
|---|---|
| **Ban checkboxes from hashed files; keep them in `tasks.md`** (the issue's Option B) | Acceptance criteria are contract. Moving them to a file outside approval lets a criterion be weakened with no re-approval. Also no longer a clean split: every `tasks.md` in the corpus now has frontmatter. |
| **A separate progress file beside `requirements.md`** | A second file to keep in step with the criteria it mirrors, for what one line pattern solves. |
| **Normalize only under an "Acceptance Criteria" heading** | Closes the choice-by-tick hole below, but makes the hash depend on heading text: renaming a heading silently changes which lines are covered, and task documents use arbitrary slice headings, so their ticks would still void. Adds a heading tracker to both twins. Offered as the alternative in the spec's first Clarify question. |
| **Skip fenced code blocks** | Needs a fence state machine in two languages (backtick and tilde fences, nesting, an unclosed fence that flips every later line). Two fenced checkbox lines exist in the whole corpus. Offered in the spec's second Clarify question. |
| **A hash-version field on the record** | DR-088 (ownership leaves the hash) rejected record versioning for the same contract; with a measured migration set of zero there is nothing for a version to distinguish. |
| **Fold this into SPEC-070 (ownership leaves the hash) so the basis changes once** | SPEC-070 is approved through Clarify and mid-Plan; adding to it voids that sign-off and couples a zero-migration change to the re-stamp SPEC-070 measures at 36 records. |

## Risks

| Risk | Likelihood · Impact | Mitigation |
|---|---|---|
| A document uses ticks to record a **choice** ("- [x] Option A"), and the choice changes with no re-approval | Low today (of 373 checkboxes in requirements, design, decision and epic documents, 371 sit under an acceptance-criteria or checklist heading and the other 2 are a fenced code sample) · High | This is the cost of the decision and is not engineered away. The spec's first Clarify question offers heading-scoped normalization; the shipped authoring guidance states that a tick is never a decision. That guidance is prose and will drift. |
| The twins diverge on an input no fixture contains | Low · High | ASCII-only classes (Decision 2); golden pairs for every branch of the grammar and its near misses; the existing whole-corpus parity test, which already walks 21 task documents holding 453 ticked items. |
| An adopter has approved a document that contained a ticked box | Unknown, unverified - no adopter corpus was measured · Low | That record reads `stale` once after the adopter refreshes harness files and re-approval clears it. Stated in the release notes. The spec's third Clarify question offers building a re-stamp instead. |
| This and SPEC-070 both change the same three files | Certain · Medium | Whichever lands second re-runs the measurement and re-vendors its frozen pre-change copy from `main` as it then stands. Required by the spec. |
| A ticked box now reads as "verified" to a human while nothing checks it | Medium · Low | Unchanged from today for task documents. A tick is a claim by whoever ticked it; the hash never vouched for it. |

## Costly to Refactor

**Yes.** The hash is a content contract held in 78 committed records here, mirrored across
two languages, and one of those twins is scaffolded into other repositories. Reversing the
step later voids every record whose document has a ticked box at that time, which after
this ships is expected to be most implemented specs. That is why this is a decision record
and not a patch.

## Consequences

- Ticking acceptance criteria during Implement stops costing a human re-read.
- The hash's meaning narrows from "this content" to "this content, with task-list state
  ignored". Every place that states the canonicalization steps must say so; the spec
  enumerates them.
- `scripts/approval-integrity.ts`, `scripts/approval-provenance.py`, `scripts/facts.ts` and
  the spec-gate all hash through the same two functions, so they follow without their own
  change. Believed from reading their call sites, not exercised.
- The body-only review baseline (`getSpecBodyOnly`, `canonical.ts:144`) is unchanged, so a
  tick still shows in the "changed since approval" diff. Intended: visible, not voiding.
