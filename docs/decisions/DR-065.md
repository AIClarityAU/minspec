# DR-065: Presence-gated fast-forward — the one sanctioned exception to "never move a shared HEAD"

> **Born `proposed` per DR-029** (acceptance is a separate human act — *MinSpec: Accept
> Architecture Decision Record*). Carves a **narrow, gated exception** into
> [DR-051](DR-051.md) §4a and rule #8 ([#168](https://github.com/AIClarityAU/minspec/issues/168)),
> and is the sync-side sibling of [DR-046](DR-046.md)'s base-freshness invariants.
> Materialized in [SPEC-026](../../specs/minspec/SPEC-026-session-presence/requirements.md).

## Context

Two rules the project already holds are, as written, in direct contradiction.

**Rule #8 / DR-051 §4a — never move a shared HEAD.** An agent never moves the HEAD of a
primary/shared checkout (`switch`/`checkout`/`reset --hard`/`rebase`/`merge`); all branch
work happens in a worktree. The rule exists because the failure it prevents is
*unrecoverable*: moving HEAD under a live session rewrites the working tree beneath it and
strands uncommitted work on the wrong branch. This has bitten repeatedly — it is the
originating incident behind #168, and DR-046 promoted the same concern to a T0 invariant
for SealBox dispatch.

**DR-051 §4c — on `main` is not the same as current with `origin/main`.** A shared checkout
can sit on `main` and be dozens of commits behind. Then the docs-on-`main` visibility win
*inverts*: the approvable "just there in the IDE" is a stale copy, and any gate that reads
the working tree (`validate`, the approve-hash) judges outdated content — a wrong verdict,
which in a never-wrong product is the worst defect class. Not hypothetical: §4c records a
SPEC-024 approval stranded because the acceptance criteria had merged to `origin` while the
35-behind local `main` still showed the pre-AC file.

So: staleness causes wrong verdicts, and the obvious remedy (advance the checkout) is
exactly what rule #8 forbids. The founder's 2026-07-16/17 ask ("keep the shared checkouts
current") is a request to resolve that tension, and ai-review
[#813](https://github.com/AIClarityAU/minspec/issues/813) flagged that a drain doing this
silently would be an **undocumented carve-out of a T0-grade rule** — the kind of exception
that, unrecorded, gets copied by the next author who sees the precedent but not the
reasoning.

What makes a resolution possible now is that **SPEC-026's presence layer makes occupancy
observable**. Each live session heartbeats a record every 30s carrying `worktreeRoot`
(`git rev-parse --show-toplevel` — the discriminator that differs per worktree even though
`.git` is shared) and `pid`; a record is live iff `lastSeen` is within 120s **and**
`process.kill(pid, 0)` does not throw (FR-2/FR-3/FR-4). "Is anyone in this tree?" stopped
being a guess and became a **query**.

The critical asymmetry — and the reason this DR exists rather than a code comment — is that
the two errors are not symmetric. A **skipped** fast-forward leaves a checkout stale:
harmless, self-correcting, retried on the next drain. A **wrongful** fast-forward mutates a
live tree: unrecoverable. The gate must therefore be biased, and its bias must be recorded
as a decision, because a future maintainer optimizing for "why is my checkout still stale?"
would otherwise loosen it without knowing which direction is the cliff.

## Decision

**A drain/loop MAY fast-forward a shared checkout to `origin/main` ONLY when the SPEC-026
presence layer positively confirms that NO live session claims that checkout's
`worktreeRoot` (heartbeat within 120s AND PID alive). Absence of proof means fetch-only.**

This is the **sole sanctioned exception** to DR-051 §4a / rule #8 / #168 "never move a
shared HEAD." It is justified because an **unoccupied checkout has no live tree to
disturb** — the rule protects live sessions, and a provably dormant checkout has none, so
advancing it violates the rule's *letter* while serving its *purpose*. Fail-safe toward
fetch-only preserves the invariant under any doubt.

### 1. Positive proof, not absence of evidence — the gate's fail direction

`isCheckoutOccupied` (`packages/minspec/src/lib/presence.ts:170`) returns `false`
(**dormant — ff permitted**) **only** on a conjunction of two positive facts:

- **(a) presence is demonstrably running** — at least one LIVE record exists *anywhere*, AND
- **(b) no live record's `worktreeRoot` resolves to this checkout**.

**"Anywhere" means every worktree's OWN sessions dir, not just the primary's.** Each
`SessionPresenceManager` writes its heartbeat into *its own* worktree's
`.minspec/sessions/` (a working-tree path), so both readers enumerate every worktree via
`git worktree list --porcelain` — always including `PRIMARY_ROOT`, deduped by canonical
path, git-failure falling back to the primary alone — and aggregate each worktree's own
records before applying (a)/(b). Reading only `PRIMARY_ROOT`'s dir was a real hole: a live
session in a *linked* on-`main` worktree would be invisible, its clean tree ff'd under it —
the exact rule-#8 corruption this DR forbids (fixed #846, security panel).

Condition (a) is the load-bearing subtlety and the easiest to mistake for redundancy. An
**empty / all-stale / all-corrupt** sessions directory is *indistinguishable* from "the
heartbeat isn't running" — a live session with presence disabled, crashed, or never
started looks exactly like no session at all. Treating "no records" as "nobody home" would
make the gate open **widest** precisely when its information is **worst**. So an empty dir
⇒ **occupied**. Every error path — missing dir, unreadable dir, corrupt record, `kill`
throw — returns `true` (occupied) (`presence.ts:175,179,183,186`).

This fail direction is deliberately **opposite** to SPEC-026 FR-12's pre-commit contention
backstop, which fails **open** (allow). The inversion is not an inconsistency: FR-12's
false-positive blocks a legitimate commit (visible, annoying, recoverable), whereas this
gate's false-negative corrupts a live tree (silent, unrecoverable). **Each gate fails toward
its own cheap error.** Recorded explicitly so the next reader does not "fix" the apparent
inconsistency by aligning them.

### 2. The exception is a conjunction of four guards, not presence alone

Presence-dormancy is *necessary but not sufficient*. `sync_shared_checkouts`
(`scripts/drain-inbox.sh:189`) fast-forwards only when **all four** hold; any failure ⇒
fetch-only:

| Guard | Condition | Protects against |
|---|---|---|
| **G1** | HEAD is the default branch (`main`) | Touching a feature-branch WIP tree |
| **G2** | Content-clean (`git status --porcelain` empty) | Stomping uncommitted WIP left by a session that exited |
| **G3** | Not presence-occupied (§1) | Mutating a live session's tree |
| **G4** | True fast-forward (`merge-base HEAD origin/main == HEAD`) | Losing local-only commits on a diverged checkout |

G2 and G4 are what make the exception safe **even if presence is wrong**. A dormant-but-
dirty checkout is skipped; a dormant-but-diverged checkout is skipped. The operation is
`merge --ff-only` — **never** `reset`, `rebase`, or a merge commit — so **no commit and no
WIP can be lost by construction**, not merely by policy. Presence is the *newest* guard,
not the *only* one; the pre-existing structural guards remain the floor.

### 3. Fetch is unconditional; only HEAD movement is gated

`git fetch` never moves HEAD and never touches the working tree, so it runs on **every**
checkout regardless of occupancy (`drain-inbox.sh:197`). This matters: even a checkout that
is never eligible for ff still gets current `origin/*` refs, which is what the extension's
**offline** staleness detection (DR-051 §4c / [#512](https://github.com/AIClarityAU/minspec/issues/512))
reads to warn a human that their tree is behind. The gated ff removes the stale-checkout
problem where it can do so provably; the fetch improves the *detection* everywhere else.
The exception is scoped to the one operation that carries the risk — **moving HEAD** — and
nothing more.

### 4. Bash and TypeScript must agree byte-for-byte

The gate exists **twice**: `isCheckoutOccupied` in TS (the extension's future callers) and a
jq-free `checkout_occupied()` in `drain-inbox.sh:148`. Two implementations of one predicate
is a drift class this project has already been bitten by, so the constants
(`HEARTBEAT_SECS=30` / `STALE_SECS=120`, **paired** as `STALE = 4 × HEARTBEAT`) are named in
one place per language with a tie-back comment, and a **golden-fixture parity test**
(`packages/minspec/tests/presence-sync-parity.test.ts`, SPEC-026 FR-14 family) fails on
divergence. Per the constitution's *enforce, don't trust the model* principle: the agreement
is a **gate**, not a comment asking future authors to remember.

### 5. Scope of the exception — deliberately minimal

This DR sanctions **exactly one** operation: `merge --ff-only` to `origin/<default>`, by a
drain/loop script, on a checkout passing G1–G4. It does **not** sanction, and must not be
cited to justify: any `switch`/`checkout` of a shared HEAD; any `reset`/`rebase`/merge-commit
on a shared checkout; ff of a **feature** branch (G1); ff of a checkout whose dormancy is
merely *assumed*; or the **extension** (Tier-0, offline core) doing any of this — DR-051 §4c
is explicit that the extension half offers a **consent-gated** sync, never a silent one. The
scripts may `fetch` because they are Tier-1 dispatch tooling (DR-004); the extension may not
(INV-1, offline core). Kill-switch: `MINSPEC_DRAIN_GATED_FF=0`.

## Amendment (2026-08-30) - WITHDRAWN, never accepted

> **Withdrawn 2026-10-17:** superseded by Amendment B (extension may move its own checkout)
> below, which reaches a clean checkout by staging identical files instead of discarding
> them. Text kept as written.

**Status: `proposed`.** This amendment widens §5's sanctioned operation set, so it is not
self-accepting. Implementation of the discard must not begin until a human accepts it.
Triggered by [minspec #1167].

**The deadlock it resolves.** G2 requires the checkout be content-clean. G2 is correct and
load-bearing - git cannot distinguish uncommitted WIP from anything else that is dirty. But
a MinSpec extension command writes to the **open workspace folder** (always the primary,
never a worktree), and nothing cleans up once the PR carrying those bytes lands. The
leftover copies are byte-identical to `origin/<default>`, so they carry **no information** -
yet they are still `git status` output. G2 therefore fails, `sync_shared_checkouts()` skips
the checkout every cycle, and the checkout can never become clean on its own.

Measured 2026-07-31: 8 dirty paths across the three workspace primaries, **7 byte-identical
to `origin/main`** - all three repos simultaneously dirty *and* behind. Measured again
2026-08-30 on `MinSpecPro`: **4 dirty paths, 4 byte-identical, 6 commits stranded behind**.
The guard works as designed; the outcome is a permanent staleness deadlock - and stale
shared checkouts stranding approvals is the exact defect DR-065 was written to eliminate.

**What this amendment authorises.** One additional operation: **discarding a working-tree
path that has been positively verified byte-identical to `origin/<default>`**, in order to
satisfy G2, on a checkout that already passes G1, G3 and G4.

**The bounds, all load-bearing.** These are conditions of the sanction, not optional
hardening:

1. **Byte-identity is proven per path, positively.** The content at `origin/<default>:<path>`
   must be read and compared byte-for-byte against the working-tree file. "Modified per
   `git status`", "differs from HEAD", or "appears already merged" are NOT sufficient - each
   is a proxy, and this operation deletes.
2. **Any doubt discards nothing.** A path that cannot be read, cannot be compared, is
   untracked-and-absent from `origin/<default>`, or differs by a single byte is left exactly
   as it is. The fail direction is toward keeping files, matching §1's "positive proof, not
   absence of evidence".
3. **G1, G3, G4 still hold.** Only G2 is repaired. In particular G3 (not presence-occupied)
   is unchanged: no discard on a checkout any live session claims.
4. **Scoped to the deadlock.** This authorises discarding redundant copies to reach a
   fast-forward. It does not sanction discarding uncommitted work, cleaning untracked files
   generally, or any path whose bytes are not already on the remote.
5. **The extension may not do this silently.** DR-051 4c stands - the extension half offers
   a consent-gated action, never an automatic one. The unattended path is drain/loop tooling
   only (Tier-1, DR-004).
6. **Kill-switch.** `MINSPEC_DRAIN_REDUNDANT_DISCARD=0` disables it independently of
   `MINSPEC_DRAIN_GATED_FF`.

**The residual risk, stated plainly.** The byte comparison is performed by the same system
requesting permission to delete. A defect in that comparison discards a file that was not
in fact redundant. Two things bound it rather than eliminate it: the discarded bytes are by
construction recoverable from `origin/<default>`, and G3's presence gate - which itself
failed OPEN until [minspec #1721] made it fail closed - keeps the operation off any
checkout a live session claims. This is a real risk accepted for a real deadlock, not an
argument that the risk is absent.

## Amendment B (2026-10-17) - PROPOSED, not accepted: the extension may move its own checkout

**Status: `proposed`.** It amends §5, which today bars the extension from moving a
checkout, so it is not self-accepting. Nothing it authorises may be built until a human
accepts it. Triggered by minspec issue 1167 (G2 deadlock) and the founder's answer `follow`
to queue item d1167 (2026-10-17). Materialized in
[SPEC-140](../../specs/minspec/SPEC-140-checkout-follows-approval/requirements.md)
(checkout follows approval).

**Why the drain cannot fix this.** The leftovers come from the editor's own approvals, and
the editor writes a live presence record for the checkout it has open
(`packages/minspec/src/extension.ts:114-126`). `isCheckoutOccupied` reads any live record
for the checkout as occupied, with no exception for the caller
(`packages/minspec/src/lib/presence.ts:381-407`). So G3 fails for as long as the window is
open, which is exactly when approvals are made. Widening G2, as the withdrawn 2026-08-30
amendment did, cannot reach that checkout.

**What this amendment authorises.** One additional actor and one additional index write:

1. **Actor.** The MinSpec extension, in the window that has the checkout open, MAY run
   `git merge --ff-only <pinned object id of the fetched origin/<default>>` on that
   checkout, and on no other.
2. **Consent, once.** Only while the user setting `minspec.followMergedApprovals` is `on`.
   The setting is asked once and never again; it is the explicit consent constitution
   invariant 1 requires for the fetch, and the standing consent DR-051 §4c requires for the
   move. This replaces, for this case only, §5's "consent-gated sync, never a silent one"
   per-move prompt and the Alternatives entry that kept a prompt per fast-forward for the
   extension path.
3. **Fetch.** §5's "the extension may not [fetch]" is lifted for this case only: the
   extension may fetch `origin`'s default branch while an approval it pushed is waiting to
   land and the setting is `on`. Never otherwise.
4. **The index write.** To satisfy G2 the extension may stage, by object id, a path whose
   working-tree bytes and mode it has positively verified equal to the target's, and only
   such a path. If the fast-forward then does not complete, every index entry it changed is
   put back exactly as found. No working-tree file is removed or rewritten.

**The guards, restated for this actor.** Each is checked before anything changes, and any
one failing means no change at all:

| Guard | For the drain (unchanged) | For the extension's own checkout |
|---|---|---|
| **G1** | HEAD is `main` | Unchanged |
| **G2** | `git status --porcelain` empty | Every reported path byte-identical (mode included) to the target, with no conversion attribute; staged as above |
| **G3** | No live session claims the checkout | **No live session other than this window claims it** |
| **G4** | True fast-forward | Unchanged |
| **G5** (new) | - | No SPEC-135 (self-installing build) consent record on the checkout: one mover per checkout |

**G3's fail direction is kept, not loosened.** "Other than this window" is a self-exception
by `sessionId`, and it holds only on positive proof:

- this window's own record exists, is live, is the only record carrying its `sessionId`,
  and carries this extension host's PID; that record is also §1's condition (a), presence
  demonstrably running;
- every record in every worktree's sessions directory is readable and well formed;
- no other live record resolves to this checkout.

Any unreadable, corrupt, missing or ambiguous record means no move, exactly as in §1.

**Why the self-exception is safe.** Rule #8 protects a live session from having its tree
moved by someone else. Here the actor is the session that claims the tree, acting on its own
human's standing consent, the same act as that human typing `git pull`. The structural floor
from §2 still holds: `--ff-only` cannot lose a commit, and G2 as restated means there is no
uncommitted work to strand, because every dirty path already equals what the move brings.

**The residual risk, stated plainly.** Terminal agent sessions write no presence record
(measured 2026-10-17: one record in the primary, the editor's), so G3 cannot see an agent
working in the checkout from a terminal. Its uncommitted edits are still protected by G2 as
restated, and git refuses a fast-forward over a change that races in after the check. A
read-only agent does see files change under it. Tracked as minspec issue 2843 (terminal
agent sessions write no presence record).

**Unchanged.** The drain, `sync_shared_checkouts`, G1 to G4 for the drain, the kill-switch
`MINSPEC_DRAIN_GATED_FF`, and everything else §5 refuses to sanction. This amendment does
not authorise the extension to switch, reset, rebase, stash, restore, clean, delete,
commit or push, nor to move any checkout but its own window's.

**Relation to the other pending amendment.** Minspec issue 2628 (DR-065 needs an amendment
for the consent-gated case) asks for a separate amendment for SPEC-135's host updater.
Accepting both makes §5's "sole sanctioned exception" plural; G5 keeps them from both
moving one checkout.

**Follow-ups (tracked).**

- SPEC-140 (checkout follows approval) - the materialization; built only after acceptance.

## Amendment C (2026-10-21) - PROPOSED, not accepted: the extension may retire its own just-pushed copies before the merge

**Status: `proposed`.** It widens what Amendment B lets the extension do to its own
checkout, and §5 bounds every such widening, so it is not self-accepting. Nothing it
authorises may be built until a human accepts it. Triggered by minspec issue 2992 (DR-065
needs an amendment sanctioning SPEC-140 FR-19's pre-merge restore), raised when the
AI-review architect blocked PR 2991 (SPEC-140 amendment for the pre-merge window, issue
2974: primary left dirty after an approval). Materialized in
[SPEC-140](../../specs/minspec/SPEC-140-checkout-follows-approval/requirements.md) FR-19
(`requirements.md:297-312`), built by PR 2990 (in-flight approval record).

**Why Amendment B does not cover it.** Amendment B reaches a clean checkout by staging
identical files and says "No working-tree file is removed or rewritten" (line 251 above).
Its closing paragraph says it "does not authorise the extension to switch, reset, rebase,
stash, restore, clean, delete, commit or push" (lines 289-291 above). FR-19 restores
working-tree files from the index and deletes a new sidecar, so it needs its own sanction.
The withdrawn 2026-08-30 amendment shows this repo treats discarding identical leftovers
on a shared checkout as a widening of §5, not as ordinary code.

**The gap it closes.** Between an approval's push and its merge, Amendment B's follow pass
has nothing to fast-forward to, so every path the approval transported sits dirty in the
shared primary for the whole life of the pull request. Each dirty path fails G2 for the
drain, reads as uncommitted work to every other session, and is the issue 2974 defect.
Those bytes are already on the remote, in the approval commit the extension itself just
pushed.

**What this amendment authorises.** One additional working-tree write, by one actor:

1. **Actor and checkout.** The MinSpec extension, in the window that made the approval,
   on the checkout whose git directory holds that approval's pending-approval record
   (SPEC-140 FR-4, `requirements.md:173-191`), and on no other checkout.
2. **The operation.** For each path the approval push transported: restore the
   working-tree file from the index, or, for an approval sidecar that is new to the
   branch, remove the working-tree file. Nothing else.

**The bounds, all load-bearing.** These are conditions of the sanction, not optional
hardening. Any one failing for a path means that path is not touched:

1. **Only the extension's own just-pushed output.** The path must be one the approval
   push wrote, as listed in the pending-approval record for that approval. No other path,
   however identical, is in scope; this is not a general clean-up of identical files.
2. **Proven per path, immediately before it is touched.** Both must hold, read at that
   moment, not carried over from an earlier check: the working-tree bytes
   (`git hash-object`) equal the blob for that path in the approval commit; and the
   path's index entry equals `HEAD`'s (for a new sidecar: absent from both). A staged
   change, an edit after the push, or any read or compare that fails means the path is
   kept.
3. **The approved document differs from `HEAD` only in lifecycle.** It must be tracked on
   `HEAD`, and the only differences allowed are frontmatter `status:` and `phases:` and
   the body's status word, compared in the approval hash's canonical form. A document
   edited beyond lifecycle is kept. An untracked document is never removed.
4. **Sidecar first, all or nothing for it.** The sidecar is proven and retired before any
   other path. If it cannot be proven or retired, nothing at all is touched, and the
   approval stays where it is in the working tree (SPEC-140 FR-19: "the approval is
   never recorded nowhere").
5. **Never the index or `HEAD`.** The step writes working-tree files only. It stages
   nothing, commits nothing, and moves no ref. This is what keeps it separate from
   Amendment B's index write and from §5's HEAD moves.
6. **No network.** Every check is a local read of objects and refs already present.
   Constitution invariant 1 is untouched; there is no fetch here to consent to.
7. **Only after the pending-approval record is written.** The record (SPEC-140 FR-4) is
   written first, so the overlay (SPEC-140 FR-20) keeps the item reading approved once its
   working-tree copy is gone. With no record, nothing is retired.
8. **Only once the pull request is open.** With no pull request open, nothing is retired:
   the dirty files are the visible prompt to open one (FR-19).
9. **Every kept path is reported.** Each path left in place is named with its reason, in
   the approval's completion message and the output channel (FR-19). No silent skip.

**Why no consent setting gates it.** FR-19 runs whatever `minspec.followMergedApprovals`
says (SPEC-140 rejected alternative 8, `requirements.md:446-448`). That setting is the
consent constitution invariant 1 requires for the fetch and DR-051 §4c requires for a
move of `HEAD`. This step does neither: it fetches nothing and moves nothing, and it only
takes back bytes the same extension wrote moments earlier, in the same user action, where
the remote already holds the same bytes. Gating it on the setting would leave the default
`ask` checkout dirty for the whole pull request, which is the issue 2974 problem. The
withdrawn 2026-08-30 amendment's bound 5 ("the extension may not do this silently")
applied to discarding leftovers of unknown origin on someone's checkout; here the origin is
proven to be this extension's own push, and every kept path is reported (bound 9).

**What is recoverable.** A retired document's body is `HEAD`'s, and the record stores the
pushed document's frontmatter and the hash of the restored bytes (FR-4). A retired
sidecar's contents are stored in the record. Every retired path's bytes are the approval
commit's blob, on the pushed branch while it exists.

**The residual risk, stated plainly.** The check and the write are two steps. A write that
lands on a path after its check and before its restore is overwritten, and those bytes are
lost; bound 2 narrows that window to one path at a time but cannot close it. Terminal agent
sessions write no presence record (issue 2843), so nothing tells the extension that an
agent is editing in the primary at that moment. The comparison is also performed by the
system asking to rewrite, as with the 2026-08-30 amendment; a defect there rewrites a file
that was not in fact a copy. This is a real risk accepted for a real, recurring defect, not
an argument that the risk is absent.

**Unchanged.** Amendment B and everything it bounds; the drain, G1 to G4 and
`MINSPEC_DRAIN_GATED_FF`; and everything else §5 refuses to sanction. This amendment does
not authorise the extension to restore or delete any path other than one bound 1 admits,
nor to switch, reset, rebase, stash, clean, commit or push, nor to touch any checkout but
the one holding its own pending-approval record.

**Alternatives considered.**

- **Leave the leftovers dirty until the merge, and let Amendment B's follow pass take
  them.** Rejected: that is the status quo issue 2974 reports. The primary stays dirty for
  the life of every pull request, G2 fails for the drain throughout, and other sessions
  see uncommitted work that is not theirs. With the default setting `ask`, the follow pass
  never runs at all, so the copies never go.
- **A new standalone decision record.** Rejected: the operation is one more write by
  Amendment B's actor, on Amendment B's checkout, bounded by the same §5. A separate record
  would split one exception's bounds across two documents that can drift, and §5's
  "deliberately minimal" list would no longer be readable in one place.
- **Widen §5 generally, so the extension may restore any working-tree file proven
  byte-identical to the remote.** Rejected: that is the withdrawn 2026-08-30 amendment's
  scope in the extension's hands, without its presence guard. Identity to the remote does
  not prove the file is the extension's own output; a file another session wrote that
  happens to match would be in scope. Bound 1 is what makes the rewrite safe without a
  consent prompt.
- **Gate the step on `minspec.followMergedApprovals`.** Rejected for the reason given
  above (SPEC-140 rejected alternative 8): the default checkout stays dirty.
- **Stage the copies (Amendment B's technique) instead of restoring them.** Rejected:
  before the merge, `HEAD` does not carry the approval, so staging it puts the approval in
  the index as an uncommitted change, which is the dirty state in a different place and
  breaks bound 5.

**Follow-ups (tracked).**

- SPEC-140 FR-19 to FR-21 (retire, overlay, record end) - the materialization; built by
  PR 2990 only after this amendment is accepted.
- Minspec issue 2992 (this amendment's ask) - closes on acceptance.
- Minspec issue 2843 (terminal agent sessions write no presence record) - the blind spot

## Consequences

**Positive:**
- The stale-shared-checkout defect class (DR-051 §4c — wrong verdicts from outdated content,
  the SPEC-024 stranding) is eliminated **for dormant checkouts** without weakening rule #8
  for live ones.
- Rule #8's exception surface becomes **explicit, enumerated, and gated** rather than
  precedent-by-example. A future author reading `sync_shared_checkouts` finds the reasoning,
  not just the code.
- Presence (SPEC-026 Layer 1) earns a second consumer beyond the status bar, validating the
  `worktreeRoot` discriminator as the "same working tree?" primitive DR-051 §4a assumed.
- The fail-safe bias is recorded, so "why is my dormant-looking checkout still stale?" is
  answered by a decision rather than re-litigated as a bug.

**Negative:**
- **Presence-off sessions never benefit.** A user who disables the heartbeat sees condition
  (a) fail forever, so their checkouts are always fetch-only. This is correct-by-design (they
  are indistinguishable from a live unclaimed tree) but will read as "the sync doesn't work."
  Accepted; the alternative is the unrecoverable error.
- **Two implementations of one predicate** (TS + bash) is a standing drift risk, mitigated by
  the parity test (§4) but not eliminated.
- **Presence is single-machine.** `process.kill(pid, 0)` is meaningless for a PID from another
  host; a shared checkout on network storage could in principle be claimed by an unobservable
  remote session. SPEC-026 puts cross-machine presence out of scope and relies on the 120s
  threshold to evict foreign records — which makes such a record *stale* ⇒ occupied ⇒
  fetch-only, so the failure lands on the **safe** side.
- The exception, however narrow, is a precedent. §5 exists to bound it.

## Alternatives considered

- **Do nothing — keep rule #8 absolute, accept staleness.** Rejected: DR-051 §4c documents
  this producing *wrong verdicts* (the stranded SPEC-024 approval), which is the never-wrong
  violation the project treats as its worst defect. "Never move a shared HEAD" was written to
  protect live trees; applying it to a provably empty tree serves the letter against the
  purpose.
- **Fast-forward whenever the tree is clean and on-main (no presence check).** Rejected: a
  live session frequently has a clean tree — between commits, mid-read, thinking. Clean is
  *not* evidence of dormancy, and this is precisely the reasoning that caused the original
  #168 incident.
- **Treat an empty sessions dir as "nobody home."** Rejected — this is the whole decision in
  miniature. It inverts the fail-safe exactly where information is weakest (§1) and would
  open the gate widest on a machine where presence never started.
- **Lock files instead of presence.** Rejected: a second source of truth for "who is in this
  tree," with its own staleness and cleanup problem. SPEC-026 FR-2 is explicit that the
  heartbeat **is** the live claim — no separate `.minspec/locks/` store.
- **`reset --hard origin/main` instead of `--ff-only`.** Rejected outright: it discards local
  commits and WIP. `--ff-only` makes loss structurally impossible, so G4 is enforced by git
  itself rather than only by our check.
- **Let the extension do the sync.** Rejected: Tier-0 offline core cannot `fetch` (INV-1), and
  a silent HEAD move in the user's IDE is the opposite of DR-051 §4c's consent-gated posture.
  The drain is Tier-1 tooling (DR-004) and is the right home.
- **Prompt a human for each ff.** Rejected for the *drain* (unattended by definition — a
  prompt nobody sees is a hang). Retained for the extension path (#512), where a human is
  present. Different actor, different answer.

## Costly to Refactor

**Costly:** the **fail-safe direction** (§1) and the **scope of the exception** (§5). Once a
drain is trusted to advance checkouts, loosening the gate — treating an empty presence dir as
dormant, dropping G2/G4, or extending the exception to `reset`/feature branches — re-opens an
**unrecoverable, silent** corruption path that no test observes after the fact and that no
gate downstream can catch. The cost is not the code change; it is that the failure destroys
the evidence. That is the DR-359 ADR filter (parent register, mmo-platform) tripping.

**Cheaper to reverse:** the constants' values (30s/120s — paired and named, one edit each
side, parity-tested); the bash-vs-TS duplication strategy (a future single implementation
could replace it); the kill-switch name; and *which* callers consume the gate.
