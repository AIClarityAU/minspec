# DR-077: Two implementations of the commit-destination rule, bound by a parity test

> **Born `proposed` per DR-029** — acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note.

## In plain terms — what this changes for you

One rule — *"you cannot commit an approval onto the push-protected default branch, because
that commit could never be pushed"* — is enforced in **two places**: a shell `pre-commit`
hook that fires on every `git commit` (even from a plain terminal), and a TypeScript guard
inside the extension that runs the instant you press Alt+A, *before* it stages anything.

The two are separate code, in different languages. That is on purpose. This DR writes down
**why** there are two, so the next person who edits one of them knows the other exists — and
knows that a test will fail loudly if the two ever disagree. Nothing about how the feature
behaves changes here; this record is the missing signpost over a coupling that already ships.

## Context

Since #1041, the scaffolded `pre-commit` hook refuses an authored commit on a project's
push-protected default branch: such a commit can never be pushed (the branch is gated on
pull-request-only checks), so it would strand the work in local history where recovering it
needs branch surgery. #1064 then found that **commit-on-approve** (Alt+A) hit exactly that
wall — it wrote the approval doc + sidecar, called `git commit`, the hook rejected it, and
the tree was left dirty with **no signal**: the stranding family (#1064 Accept-ADR, #1022
Alt+A, #874 advance). The fix was to make commit-on-approve refuse **up front**, before
staging, returning `'protected-branch'` so the command layer can offer a branch instead of
letting the raw hook rejection strand files.

That fix required the same "which commits may the default branch receive?" decision the hook
already makes — but reached from inside the extension, before anything is staged. There are
now **two implementations of one rule**:

| | where | language | when it runs |
|---|---|---|---|
| the hook | `template-registry.ts` → scaffolded to a project's `.minspec/hooks/pre-commit` | POSIX shell | at `git commit`, for everyone — terminal, other editor, AI agent |
| the guard | `approve-commit.ts` `resolveBranchDestination` | TypeScript | inside the extension, **before** anything is staged |

They must decide **every** commit identically, and the guard mirrors the hook's *whole*
contract, not just its default-branch resolution: the `MINSPEC_GATE_OFF` / `MINSPEC_ALLOW_MAIN`
bypasses, the `minspec.allowCommitOnDefaultBranch` opt-out, the merge / cherry-pick / revert /
rebase in-progress exemptions, the detached-HEAD skip, `origin/HEAD` as the authoritative
default, and the `minspec.protectedBranches` name-list fallback that *replaces* — not extends
— `main master trunk` (`approve-commit.ts:264-360`; hook body `template-registry.ts:663-725`).

The binding between them is **`approve-commit-hook-parity.test.ts`**: a T0 test that drives
one scenario table through *both* real implementations against real temp repositories and
asserts the outcomes agree —

```
hook blocks  ⟺  commitApproval returns 'protected-branch'
hook allows  ⟺  commitApproval returns 'committed'
```

The second half is what makes the test strong. When the TS guard *wrongly allows*, the real
hook fires during `commitApproval`'s own `git commit`, so the outcome is `'failed'`, not
`'committed'` — the divergence is observable without the test needing to know which side is
wrong. A source-text assertion ("both files contain string X") could not catch either failure
direction; it passes against a guard whose conditions are right and whose *logic* is wrong.

**A third copy exists, differently bound.** This repo sets `core.hooksPath=.githooks`, so the
*scaffolded* hook never runs here — the repo that ships the guard would be the one repo not
protected by it. So `.githooks/pre-commit` carries a hand-maintained shell **twin** of the
same guard, bound to the template by a *weaker* mechanism: a decisive-lines **substring**
test (`pre-commit-protected-branch.test.ts`, `DECISIVE[]`) asserting both texts contain the
guard's load-bearing lines. Shell-to-shell, kept textually near-identical, that substring
binding is proportionate; the shell-to-TS gap is the one that needs behavioral parity, and
gets it.

**Why this needs a DR, not a comment.** The reasoning above currently lives in a docstring
(`resolveBranchDestination`) and a test header.
The ADR filter (`DR-359` — parent register, mmo-platform) asks whether the choice can be undone in under a day: un-duplicating this —
collapsing to a single source — is *not* a one-day change once other call sites depend on
`resolveBranchDestination`, and the coupling is **cross-boundary** (a TS module bound to a
generated shell script by nothing but a test). That is precisely the class the register
exists for: the next person to touch either half needs to know the other exists and that a
test will fail if they diverge. It is also a **constitution invariant #2** ("no silent gate")
concern — see Risks.

## Decision

**1. Keep two implementations of the commit-destination rule, in shell and in TypeScript.**
The duplication is deliberate, not incidental, and is retained because the two forced
alternatives are worse for this one function (see *Alternatives considered*). The rule
enforced is: *refuse an authored commit whose current branch is the push-protected default
branch; allow everything else, and fail open on any unknown destination.*

**2. The behavioral parity test is the binding contract.**
`approve-commit-hook-parity.test.ts` is the authoritative binding between the hook and the TS
guard. It is a **T0 invariant test**: it must run one scenario table through both real
implementations and assert their outcomes agree in both directions (`hook blocks ⟺
'protected-branch'`, `hook allows ⟺ 'committed'`). It may not be weakened to a source-text
assertion, and new decision-affecting behavior in either half must arrive with a scenario
that exercises it.

**3. A change to either half must be mirrored in the other, in the same change.**
Editing the hook's guard clauses (`template-registry.ts`), the TS guard
(`resolveBranchDestination`), or the `.githooks` twin, obliges mirroring the others so the
parity and decisive-lines tests stay green. All three sites already carry rationale comments
that cross-reference each other (`approve-commit.ts:264-303` names `template-registry.ts` and
#1041; `.githooks/pre-commit:27-31` names the generated template and constitution invariant 2),
but **none of them names DR-077** — `grep -r DR-077` matches no source file as of this commit.
So the mirror obligation is stated here and nowhere the editor of either half will see it.
Adding those tie-backs is tracked at **[#1221](https://github.com/AIClarityAU/minspec/issues/1221)**
and deliberately left out of this docs-only PR.

**4. The guard mirrors the hook's *whole* contract, and the mirror is directional-asymmetric
by design.** The guard runs *before* the hook. Therefore:
- **TS refuses where the hook would allow → a false block** the user cannot escape by any
  documented means (their opt-out never reaches the hook). This is the strictly forbidden
  direction; the guard must never refuse *more* than the hook.
- **TS allows where the hook refuses → an inert guard**: the commit proceeds, the hook
  rejects it, and the result degrades to `'failed'` with files stranded — the exact #1064
  failure the guard exists to prevent.
Both directions are parity-test failures. Neither may be "fixed" by loosening the test.

**5. One sanctioned non-mirror is recorded, not a bug.** Mid-merge / mid-cherry-pick on the
default branch, the two halves agree on the **decision** (neither guard fires — a merge is how
a branch legitimately lands) yet diverge on the **outcome**: `git` itself forbids a *partial*
(pathspec) commit during a merge (`fatal: cannot do a partial commit during a merge`), and
commit-on-approve is pathspec-only by its invariant 1 (a bare commit would sweep another
session's staged files). So the TS outcome there is `'failed'`, declared per-scenario in the
parity table (`tsOutcome: 'failed'`), tracked at **#1112**. Asserting `'committed'` there
would assert something git forbids.

**6. The `.githooks` twin's weaker (substring) binding is accepted as proportionate.** A
shell-to-shell copy kept textually near-identical does not need full behavioral parity; the
decisive-lines substring test is the right cost. If that twin ever grows logic the substring
test cannot see drift in, upgrade it to behavioral parity (see Follow-ups) — but this DR does
not mandate that today.

## Consequences

- The "why are there two of these?" question now resolves to a DR, not to reading two
  docstrings and inferring. The three implementing files link here.
- Any future editor of the branch guard is on notice: the parity test is load-bearing, and a
  mirror is mandatory. A green `npm test` is the evidence the two halves still agree.
- The coupling is now a **named, costly-to-reverse** architectural artifact — future work that
  wants to collapse the duplication (Decision 1) knows it is a DR-superseding change, not a
  refactor it can land silently.
- No behavior changes. This is a documentation/discoverability record over shipped, tested code
  (evidence discipline: `resolveBranchDestination` and the parity table are cited to file:line
  above; the feature is `implementing`/live, not merely specified).

## Alternatives considered

- **Shell out to the hook from the TS side and read its exit code (one implementation).**
  Rejected. The guard must run *before* staging, and it must work in a fresh clone where the
  hook is often not installed or not executable — shelling out cannot distinguish "hook absent"
  from "hook allows," and would spawn a subprocess (with the user's own pre-commit hook chain)
  on every Alt+A. The whole point of #1064's fix is to decide *before* `git` is invoked.
- **Generate both from one source (real single-source-of-truth).** Rejected *for now*. The
  hook is already generated from `template-registry.ts`; the TS guard could in principle be too.
  But generating TypeScript *control-flow logic* from a template is a large mechanism to own for
  **one function** — far more machinery than the parity test it would replace. This is the
  alternative that starts to pay for itself if a *third consumer* of the same rule appears (see
  *Costly to Refactor* / Follow-ups).
- **Duplicate + behavioral parity test (what shipped).** Chosen. Lowest mechanism for a
  two-consumer rule: two direct, readable implementations, each idiomatic in its language, with
  a test that fails on any behavioral divergence in either direction.
- **Bind by a source-text ("both contain string X") assertion instead of a behavioral test.**
  Rejected for the shell↔TS pair: it passes against a guard whose conditions are named right and
  whose logic is wrong. Accepted only for the shell↔shell twin, where textual near-identity makes
  substring presence a faithful proxy.

## Costly to Refactor

**Costly:** the *existence of two implementations* (Decision 1) and *the parity test as their
binding* (Decision 2). Once additional call sites consume `resolveBranchDestination`, collapsing
to a single source is no longer a one-day change — and doing it *wrong* (dropping the behavioral
parity for a text check, or mirroring only half the contract, as the first two revisions of
#1089 did) re-opens the #1064 stranding or ships a false block with no user escape. That
irreversibility-in-under-a-day is the ADR filter tripping, and is why this is a DR.

**Cheaper to reverse:** *which* alternative wins if the duplication is ever undone (shell-out
vs single-generated-source — the answer flips the moment a third consumer appears); the
`.githooks` twin's binding *strength* (Decision 6, upgradeable to behavioral parity); and the
exact set of callers that consume the guard.

## Risks & Mitigations

- **Silent divergence between the two halves (constitution invariant #2 — no silent gate; DR-066).**
  A guard that under-blocks is an *inert gate* (the #1064 stranding returns); one that
  over-blocks is a *false gate* (a documented opt-out refused with no escape). Both are the
  never-wrong product's worst defect class. *Mitigation:* the T0 behavioral parity test is the
  gate on the gate — it fails on either divergence direction, against real repos, and is
  pinned as un-weakenable by Decision 2. The mirror obligation (Decision 3) is recorded *here
  only* — no source file names DR-077 yet ([#1221](https://github.com/AIClarityAU/minspec/issues/1221)),
  so until those tie-backs land, an editor who never opens this DR is relying on the parity
  test alone to catch a one-sided edit. That is the test doing its job, but it fails *after*
  the divergence rather than warning before it.
- **The DR drifts from the code it describes.** A future edit changes the guard but not this
  record. *Mitigation:* the load-bearing facts here (clause list, non-mirror at #1112, binding
  test name) are cited to file:line and test name, so a reviewer can check them cheaply; the
  authoritative signal remains the passing parity test, not this prose (the prose is
  model-/human-trusted and may drift — constitution's "enforce, don't trust the model").
- **The `.githooks` twin drifts in a way its substring test cannot see.** The twin is bound
  only by decisive-line presence, weaker than behavioral parity. *Mitigation:* Decision 6 caps
  the accepted risk to shell-to-shell textual copies; any logic growth there triggers the
  Follow-up to upgrade the binding.
