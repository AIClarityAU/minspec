## In plain terms

[#1555](https://github.com/AIClarityAU/minspec/issues/1555) asks for a code-quality stage in
the pre-commit gate MinSpec scaffolds into projects. Its checks come in two kinds. Correctness
checks state a fact a parser can be sure of: a shell script is malformed, a GitHub Actions
workflow is invalid, the project's types do not compile. Metric checks compare a number with a
threshold: how much code is duplicated, how complex a function is, how many circular
dependencies or unused exports there are. A threshold is noisy: the issue's examples are a
complexity or duplication limit tripping on a switch statement, a generated file, or three
branches that are similar but not identical. A gate that blocks on noise gets switched off
with `MINSPEC_GATE_OFF=1`, which switches off the secret scan in the same keystroke.

This record sets the rule by class. A correctness check blocks the commit. A metric check
prints its finding and lets the commit through, until a project opts that check into blocking.

Each of the three correctness checks is a new way for a commit to be refused. Earlier records
here say a check should advise, and later ones that added a blocking gate argued for it. This
record makes that argument for these three.

Only the first class is being built now. SPEC-080 (the v1 requirements) ships three
correctness checks - `shellcheck`, `actionlint` and the project's TypeScript typecheck - and
nothing in v1 warns on a finding. The metric checks, and the warn-by-default behaviour this
record gives them, wait for a v2 tracked as
[#2463](https://github.com/AIClarityAU/minspec/issues/2463).

What accepting this record accepts: three checks that can refuse a commit they could not
refuse before, in any project that has the matching tool installed; and a rule that the later
metric checks do not block by default.

## Context

[SPEC-080](../../specs/minspec/SPEC-080-pre-commit-code-quality-stage/requirements.md) is the
normative Specify-phase artifact for #1555. This record carries the decision its requirements
rest on, and that outlives its v1: which class a code-quality check belongs to decides what it
may do to a commit, including for the checks SPEC-080 defers.

Measured against the shipped template
(`packages/minspec/src/lib/template-registry.ts:1190-1547`; line numbers in this record were
read from `origin/main` at `821544d8`), the hook both blocks and warns today. Stage 0
(protected-branch guard, `:1200`) and Stage 1 (author-identity gate, opt-in, `:1325`) refuse
the commit when they trigger. Stage 2 (`gitleaks`, `:1431-1457`) blocks on a finding, and
warns and continues only when the *tool itself* is absent. Stage 3 (SDD validation,
`:1459-1547`) blocks on a frontmatter violation, such as a spec or a decision record with no
`id:`, and its three tiers fall through only when a *higher tier is unreachable*.

Stage 3 also prints warnings that let the commit through. The shell tier warns on a
`minspec:managed:` marker found outside the hooks directory ("the (2) leak is a warning only",
`:1470-1473`, printed at `:1519-1520`). The python tier (`validate.py`, the `VALIDATE_PY`
template in the same file) prints `WARN` instead of `FAIL` for a spec that declares no
`implements:`, unless the project's `.minspec/config.json` sets `ownershipDeclaration` to
`error` (`:1808-1825`, emitted at `:2055-2065`), and it warns and carries on when that config
file cannot be read (`:1818-1823`). So neither a finding that warns, nor a config key that
turns a warning into a block, is new to this harness. The first draft of this record claimed
the former was, under the title "the pre-commit harness gets a non-blocking outcome for the
first time". A review of that draft pointed at the shell tier's warning, and the claim is
withdrawn.

#1555 argues, with a specific mechanism: "a quality gate that blocks on thresholds will be
switched off," citing the harness's own Stage-0 comment ("a gate that over-blocks gets switched
off and a switched-off gate is worth nothing",
`packages/minspec/src/lib/template-registry.ts:1211-1212`). The switch in question is
`MINSPEC_GATE_OFF=1`, which exits the hook before any stage runs (`:1195`). Stage 0 and Stage 1
each have a scoped switch of their own (`MINSPEC_ALLOW_MAIN=1`, `:1246`; `EMAIL_GATE_OFF=1`,
`:1355`), but nothing scoped reaches Stage 2 or Stage 3, so a developer who reaches for
`MINSPEC_GATE_OFF=1` to get past a complexity false positive disables Stage 2's secret scan in
the same keystroke. That is a real, measured risk (the flag already exists and already covers
every stage; #1555 did not invent the coupling, it identified a new way to trigger it).

## Decision

Accept #1555's two-class policy for code-quality checks, and build it in two steps, pending
founder acceptance of this record:

1. **Correctness checks block.** A check whose finding is a parse, type or syntax fact
   (`shellcheck`, `actionlint`, the project's TypeScript typecheck, `tsc`) refuses the commit
   on a real finding and is skipped, visibly, when its tool is absent. That is the shape
   Stage 2 already has. It is also three new ways for a commit to be refused, and a new block
   has to be argued; "How this sits with 'only DR-012 blocks'" below makes the case.
2. **Metric checks warn by default.** A check whose finding is a threshold crossing
   (duplication %, cyclomatic complexity / function length, circular-dependency count, unused-
   export count) prints its finding and lets the commit through. A project's
   `.minspec/config.json` may opt a specific metric check into blocking; the shipped default
   is warn.
3. **The distinction is the check's class, not a per-project toggle at ship time.** Every
   adopter gets the same default split. A metric check's *threshold values* and its
   *opt-into-blocking* flag are config-adjustable; a correctness check's severity is not.
4. **v1 builds the first class only.** SPEC-080 ships exactly three checks, all of the
   correctness class (SPEC-080 FR-8). No metric check is built in v1, so after v1 nothing in
   the new stage warns on a finding and point 2 has no subject yet. The metric checks are
   deferred to a v2 tracked as
   [#2463](https://github.com/AIClarityAU/minspec/issues/2463); see "Deferred to v2" below.

Point 4 rests on SPEC-080's DQ-1 selection (v1 tool roster, option `a`). An agent session
recorded that selection on 2026-10-02, and only the founder's approval of SPEC-080 ratifies
it. If the selection is changed before approval, point 4 changes with it; points 1 to 3 do not
depend on it.

## Deferred to v2 - the metric checks

Not built by SPEC-080, and tracked as
[#2463](https://github.com/AIClarityAU/minspec/issues/2463):

| Check | Tool named in #1555 | What it would enforce |
|---|---|---|
| Copy-paste / duplication | `jscpd` | DRY, with a real threshold |
| Cyclomatic complexity and function length | eslint `complexity` / `max-lines-per-function`; `radon` (Python) | atomicity: small units that do one thing |
| Circular dependencies | `madge` | module boundaries |
| Dead code / unused exports | `knip`, `ts-prune` | dead-code hygiene |

What this record fixes for them now is points 2 and 3 of the Decision: when they are built
they warn by default, and making one block is the project's explicit act. What it leaves to
the v2 work: which tools, which thresholds, the config field names (SPEC-080's DQ-4 selection
records only that they go under a new top-level `codeQuality` key), whether general lint,
which #1555 lists beside the typecheck, joins the stage, and whether each check has been put
in the right class.

Why they warn and do not block. #1555 says complexity and duplication limits "produce false
positives constantly", on a switch statement, a generated file, or branches that are similar
but not identical, so blocking on them by default would train developers toward
`MINSPEC_GATE_OFF=1`, which also disables the secret scan. Correctness checks do not carry
that cost, because their false-positive rate is near zero.

Why they wait, where #1555 itself would ship them warn-only in the first release. Building
both classes at once means eight tool integrations in one build cycle instead of three, a
larger install burden for an adopter, and a bigger surface for the failure #1555 names: a
project that believes it has quality gating while every check is silently skipping. The price
of waiting is that DRY, small-unit and dead-code hygiene, the motivations that opened #1555,
stay unenforced until v2 is built.

## How this sits with "only DR-012 blocks"

Several accepted records state an advisory default. DR-025 rejects a hard block with "only
DR-012 blocks; every other MinSpec check is advisory", and DR-023 and DR-040 use nearly the
same words. Later records did add blocking commit gates, and argued for them where they did:
DR-051 (approvable commits on the primary checkout), DR-059 (commit-message deferrals, which
argues its bounded reach against that default in its §2) and DR-062 (code of an unapproved
approvable) are three, and DR-076 lists the validators, the frontmatter gates and the secret
hooks under "Keep - model-defending". So a new block is not ruled out, but it is argued and
not assumed. This record adds three. The first draft did not argue them: it described
blocking as what every stage already does, and treated the warning as the novelty.

Point 1 is a real widening. After v1, a commit that stages a malformed shell script or an
invalid workflow, or that stages TypeScript while the staged tree does not compile, is
refused wherever the tool is installed. Before v1 it was not.

The case for these three is #1555's. Each reports a fact a parser is sure of, not a judgement
about quality, and a false positive is rare. That is the kind of finding the hook already
refuses on: a spec or a decision record with no `id:` (Stage 3).

The reach is bounded three ways. A check runs only on a commit that stages a file of its own
type (SPEC-080 FR-5). A missing tool never blocks (SPEC-080 INV-2). And no metric check, the
class where noise and judgement come in, blocks unless a project opts it in (point 2).

The first bound is weaker for the typecheck than for the other two. `shellcheck` and
`actionlint` judge only the files a commit stages; `tsc` judges the staged tree as a whole
(SPEC-080 FR-2). What that and the other blocks cost is under Risks.

## What is new, and what is not

Not new: a finding that warns, and a config key that turns a warning into a block (Context);
and the opportunistic shape, where a tool that is absent is skipped and said so
([DR-037](DR-037.md), Stage 2).

New in v1: three more ways for a commit to be refused (above).

New in v2, and decided here: a class of checks, each with a threshold, that warn by default.
Stage 3's existing warnings were each decided where the check was written. Code-quality checks
are the first family where the choice has to be made for a whole class at once, and where
both mistakes have a named cost: block on noise and the gate gets switched off, warn on a fact
and the gate is weaker for nothing. Recording the rule now means the deferred checks are built
to it, and not argued one tool at a time.

## Alternatives rejected

- **Ship both classes in the first release (SPEC-080 DQ-1 option `b`).** This is what #1555
  itself recommends: the full table, with the metric checks warn-only. Not taken for v1, on
  the cost stated under "Deferred to v2": eight tool integrations in one build cycle, a larger
  adopter install burden, and a bigger surface for every check silently skipping. The metric
  checks are deferred, not dropped.
- **All Stage-4 checks block by default, metric checks included.** Rejected per #1555's own
  cost argument: complexity and duplication limits produce false positives "constantly", so
  blocking trains developers toward `MINSPEC_GATE_OFF=1`, which silently removes Stage 2 as a
  side effect. One rule for every check would be simpler to state, but the harness's own
  founding comment (Stage 0, over-blocking gets switched off) argues directly against it here,
  and so does the advisory default the earlier records state.
- **All Stage-4 checks warn, including the correctness class.** Rejected: a malformed shell
  script or an invalid GitHub Actions workflow is a fact a parser can state with the same
  confidence as a missing `id: SPEC-NNN` frontmatter line (Stage 3's own bar) — there is no
  false-positive-rate argument for warn-only on this class, and warn-only here would just be a
  weaker gate with no offsetting benefit. This is the outcome the advisory default would
  give; "How this sits with 'only DR-012 blocks'" is the argument for departing from it for
  this class.
- **No default split — leave every check's severity to project config from day one, with no
  shipped opinion.** Rejected: a harness that ships with no default behaves identically to no
  Stage 4 at all for every project that never opens `.minspec/config.json`, which is most
  projects. An unconfigured project should still get the checks with the near-zero
  false-positive rate blocking by default.
- **Route quality findings through `ai-review` (the existing LLM-based PR review) instead of a
  deterministic pre-commit stage.** Rejected per #1555's framing directly: duplication and
  complexity are "precisely the checks that should never have been given to a model" — they are
  parser-exact facts, `ai-review` costs tokens and runs on the PR rather than the commit, and a
  model can be talked out of a finding a parser cannot.

## Consequences

- **Adopters who refresh the harness gain a stage that can refuse a commit it would have let
  through before.** In v1 a staged shell script that does not parse, a staged workflow that is
  invalid, or a type error in the staged tree on a commit that stages TypeScript blocks, in
  any project where the matching tool is resolvable. Where the tool is absent the check is
  skipped with one advisory line (SPEC-080 INV-2), and a commit to which no check applies sees
  no output at all (SPEC-080 FR-4).
- **The new stage prints a roster on every commit** (SPEC-080 FR-3 and its DQ-3 selection): up
  to three lines in v1. That is new stderr output in every project where a v1 check applies.
- **Existing suites need an audit in v1.** The new stage adds stderr lines and three new ways
  to exit non-zero, and SPEC-080 FR-6 changes how Stage 3 exits, so a suite that snapshots the
  hook's output or expects a commit to succeed can be affected. Plan should audit for this
  rather than assume SPEC-080's new test is the only one touched. One case is known already:
  MinSpec scaffolds shell scripts and workflows of its own
  (`packages/minspec/src/lib/template-registry.ts:2474`, `:2615` and others), the new stage
  will lint them on an adopter's first commit wherever its tools are installed, and
  `packages/minspec/tests/scaffold-is-committable.test.ts` requires that commit to succeed
  (SPEC-080 INV-8). SPEC-080 INV-5 and AC-9 require Stage 3's verdict and its existing
  warnings to survive the exit change.
- **v1 adds no outcome the hook does not already have.** A v1 check passes, blocks or is
  skipped. The case "a code-quality finding was printed and the commit succeeded" arrives with
  v2 (#2463).
- **The `MINSPEC_GATE_OFF=1` bypass's blast radius is unchanged by this record.** SPEC-080's
  DQ-2 selection reuses it for the new stage and adds no scoped switch, so bypassing a
  code-quality block also skips the secret scan. SPEC-080 DQ-2 states that cost and keeps the
  option not taken on record.
- **v1 does not meet the motivations that opened #1555.** Until v2 is built, nothing MinSpec
  scaffolds measures duplication, complexity, circular dependencies or dead code.

## Risks

- **The deferred class may stay deferred.** v1 delivers the stage and none of the checks #1555
  was opened for. If #2463 is never picked up, points 2 and 3 of the Decision are a rule with
  no subject. The tracking issue is the only mitigation.
- **The typecheck judges a project, not a file.** As SPEC-080 FR-2 is written, one type error
  anywhere in the staged tree refuses every commit that stages TypeScript, so a project that
  adopts the harness with type errors already in it cannot commit TypeScript until they are
  fixed or the hook is bypassed. Narrowing the verdict to the staged files would trade that
  for the opposite hole: a staged change that breaks a file the commit does not stage would
  pass. #2471 puts that choice to Plan, with how the staged tree is built and what it costs
  per commit.
- **A blocking check gets bypassed with the whole-hook switch.** A correctness check rarely
  fires falsely, but a true finding the developer does not want to fix in that commit (a type
  error in work in progress) is still a block, and the only switch that passes it also turns
  off the secret scan. Unmitigated in v1; SPEC-080 DQ-2 keeps the scoped-switch option on
  record with its cost, and #2471 asks Plan to measure how often it happens.
- **For v2: a "warn" that nobody reads is worth less than no check at all if it trains people
  to ignore the stage's stderr output entirely,** the same failure #1555's own cost section
  names for the over-blocking alternative, approached from the opposite direction. Unmitigated
  by this record; the v2 work should revisit it with real usage data from v1's roster.
- **The correctness/metric boundary is a judgement call that could be wrong for a specific
  check** — e.g., a future contributor could reasonably argue circular-dependency detection
  (`madge`) has a low enough false-positive rate to belong in the blocking class. This record
  fixes the *policy shape* (two classes, correctness blocks / metrics warn), not a permanent,
  unreviewable assignment of every possible tool to one class forever.
