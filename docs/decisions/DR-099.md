# DR-099: A new outcome for the DR-037 harness — a check can run, find a real violation, and not block

## In plain terms

Every stage DR-037's pre-commit harness has today is **block-or-skip**: if the stage's tool is
present, a real finding always refuses the commit; the only way to not-block is for the tool to
be absent. [#1555](https://github.com/AIClarityAU/minspec/issues/1555) asks for a code-quality
stage whose metric checks (duplication, complexity, circular dependencies, dead code) are
expected to be noisy — false positives on switch statements, generated files, and genuinely-
similar-but-not-identical code are common — so blocking on them by default would train
developers toward `MINSPEC_GATE_OFF=1`, which also disables the secret scan. This record accepts
#1555's own recommendation: split checks into two classes. Deterministic-correctness checks
(shell syntax, GitHub Actions workflow syntax, a project's own typecheck) keep the existing
block-or-skip shape, because their false-positive rate is near zero. Metric checks get a THIRD
outcome this harness has never had — tool present, real finding, commit still succeeds — with a
printed warning, until a project's own config opts that check into blocking.

## Context

[SPEC-080](../../specs/minspec/SPEC-080-pre-commit-code-quality-stage/requirements.md) is the
normative Specify-phase artifact for #1555; this record exists because SPEC-080's own "Why a DR,
not just this spec" section identifies that the decision below is not an application of DR-037's
existing posture to a new file (the class SPEC-075 argued does *not* need a new DR) but a new
enforcement policy the harness has not carried before.

Measured directly against the shipped template
(`packages/minspec/src/lib/template-registry.ts:1183-1540`): Stage 0 (protected-branch guard)
blocks unconditionally when triggered; Stage 1 (author-identity, opt-in) blocks unconditionally
once configured; Stage 2 (`gitleaks`) blocks on a finding, warns-and-continues only when the
*tool itself* is absent (`:1428-1450`); Stage 3 (SDD validation) blocks on a real frontmatter/
egress violation, with its three tiers falling through only when a *higher tier is unreachable*,
never when a lower tier finds something and chooses not to act on it. In every existing stage,
"the tool ran and found a real violation" and "the commit is refused" are the same event.

#1555 argues, with a specific mechanism: "a quality gate that blocks on thresholds will be
switched off," citing the harness's own Stage-0 comment ("a gate that over-blocks gets switched
off and a switched-off gate is worth nothing",
`packages/minspec/src/lib/template-registry.ts:1204-1206`) and the fact that
`MINSPEC_GATE_OFF=1` is the *only* bypass this harness currently exposes — so a developer who
disables Stage 4 to get past a complexity false positive disables Stage 2's secret scan in the
same keystroke. That is a real, measured risk (the flag already exists and already covers every
stage; #1555 did not invent the coupling, it identified a new way to trigger it).

## Decision

Accept #1555's recommendation as the harness's new policy, pending founder acceptance of this
record:

1. **Correctness checks block.** A check whose finding is a parse/type/syntax-level fact
   (`shellcheck`, `actionlint`, a project's own `tsc`/`ruff`-class typecheck) keeps the existing
   block-or-skip shape every other stage already has. No new outcome is introduced for this
   class.
2. **Metric checks warn by default.** A check whose finding is a threshold crossing
   (duplication %, cyclomatic complexity / function length, circular-dependency count, unused-
   export count) gets the new third outcome: tool present, real finding, commit still succeeds,
   with the finding printed. A project's `.minspec/config.json` may opt a specific metric check
   into blocking (SPEC-080 FR-8/FR-9); the shipped default is warn.
3. **The distinction is the check's class, not a per-project toggle at ship time.** Every
   adopter gets the same default split; only the *threshold values* and the *opt-into-blocking*
   flag are config-adjustable (SPEC-080 DQ-4).

## Why this is not the same shape DR-037 already covers

DR-037's stages degrade on tool *absence*, never on the tool having run and found something.
Extending "opportunistic per tool" (absence → warn-and-continue) to this new stage would have
needed no new DR — SPEC-075 established that precedent for applying DR-037's existing posture
to a new file. What is new here is a stage that can **run successfully, disagree with the
commit, and let it through anyway, by design** — a policy question ("should a real, tool-
confirmed finding ever not block?") DR-037 never had to answer because none of its stages
produce metric-shaped findings.

## Alternatives rejected

- **All Stage-4 checks block by default (the DR-037-consistent option).** Rejected per #1555's
  own cost argument: the false-positive rate on metric checks is high enough ("constantly") that
  blocking trains developers toward `MINSPEC_GATE_OFF=1`, which silently removes Stage 2 as a
  side effect. Consistency with the existing four stages is real, but the harness's own founding
  comment (Stage 0, over-blocking gets switched off) argues directly against it here.
- **All Stage-4 checks warn, including the correctness class.** Rejected: a malformed shell
  script or an invalid GitHub Actions workflow is a fact a parser can state with the same
  confidence as a missing `id: SPEC-NNN` frontmatter line (Stage 3's own bar) — there is no
  false-positive-rate argument for warn-only on this class, and warn-only here would just be a
  weaker gate with no offsetting benefit.
- **No default split — leave every check's severity to project config from day one, with no
  shipped opinion.** Rejected: a harness that ships with no default behaves identically to no
  Stage 4 at all for every project that never opens `.minspec/config.json`, which is most
  projects (FR-1 in SPEC-075 records the same "default must be continuity/safety, not silence"
  reasoning for a different file). An unconfigured project should still get the checks with the
  near-zero false-positive rate blocking by default.
- **Route quality findings through `ai-review` (the existing LLM-based PR review) instead of a
  deterministic pre-commit stage.** Rejected per #1555's framing directly: duplication and
  complexity are "precisely the checks that should never have been given to a model" — they are
  parser-exact facts, `ai-review` costs tokens and runs on the PR rather than the commit, and a
  model can be talked out of a finding a parser cannot.

## Consequences

- **A new outcome class in a harness whose tests likely assume block-or-skip.** Any existing
  test asserting "this hook only ever exits 0 or 1 for reasons X/Y/Z" needs a new case for
  "exits 0 with a warning printed" — SPEC-080's T0 test owns proving this, but other suites that
  snapshot the hook's full stderr (if any) may need updating; Plan should audit for this rather
  than assume SPEC-080's new test is the only one touched.
- **Adopters who refresh gain a stage that can print warnings they did not have before,**
  without their commit being refused. This is within DR-037's existing "graceful, opportunistic"
  spirit but is a new category of stderr output on every commit in a project with the relevant
  language present — a UX cost DQ-3 (reporting cadence) in SPEC-080 has not yet resolved.
- **The `MINSPEC_GATE_OFF=1` bypass's blast radius is unchanged by this record** (SPEC-080 DQ-2
  is still open); this decision does not itself add or remove a bypass variable.

## Risks

- **A "warn" that nobody reads is worth less than no check at all if it trains people to ignore
  Stage 4's stderr output entirely,** the same failure #1555's own cost section names for the
  over-blocking alternative, approached from the opposite direction. Unmitigated by this record;
  SPEC-080 DQ-3 (reporting cadence) is the place this should be revisited once real usage data
  exists.
- **The correctness/metric boundary is a judgement call that could be wrong for a specific
  check** — e.g., a future contributor could reasonably argue circular-dependency detection
  (`madge`) has a low enough false-positive rate to belong in the blocking class. This record
  fixes the *policy shape* (two classes, correctness blocks / metrics warn), not a permanent,
  unreviewable assignment of every possible tool to one class forever; SPEC-080 DQ-1 leaves the
  v1 roster itself open.
