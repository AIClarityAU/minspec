# The ZCode container boundary (BND-1 to BND-6)

> ADR*). This record is `kind: direction`: it records a founder decision, which no
> delegation covers, and an agent never mints the sign-off. Nothing here records anyone as

> **On this record's number.** It was not taken from the collision gate

> session that wrote this may make no network call. It was read offline from the local

> and the one after it is left for SPEC-136 task 1.1 (the command-line record), which was

## In plain terms - what this changes for you

Nothing changes on your machine. This writes down, as a decision of yours that outlives
SPEC-136, the six rules that keep ZCode's container apart from the host: the host reads
nothing ZCode wrote except what came through GitHub (BND-1); no port links them (BND-2);
checks inside the container only help the agent there, and the merge gate stays on GitHub
(BND-3); an approval you make in ZCode counts only in that ZCode project (BND-4); nothing on
the host watches inside ZCode (BND-5); and the container is started so it cannot act as the
host (BND-6). You hold the last part, because it is how you start the container: one
`docker inspect` on the host (measurement 12) shows whether the running container matches.
The cost: a container shares the host's kernel, so a kernel exploit inside it breaks all six
rules at once. A VM did not share the kernel, and moving to a container accepted that.

## Context

ZCode (Z.ai's editor) runs apart from the host so that the host's editor and agents are
never "infected" by reading what ZCode wrote; SPEC-136 set six boundary rules for that and
said they outlive the spec and need a decision record. This is that record.

On 2026-10-13 the founder moved ZCode off the host into a VM, so that this
editor could not be "infected" by reading folders ZCode wrote. His words, verbatim from
SPEC-136 `requirements.md` (*Where this came from*):

> zcode. we just moved zcode into a VM and decided that it's safer for this (here) codium
> instance should not be able to be "infected" by reading from folders written to by
> zcode.

His answers to the first draft of SPEC-136, the same day, verbatim (*Answers received*):

> zcode: do as recommended, except for where approvals are made.  i should be able to
> approve specs for the current project in zcode.  unrelated: i don't expect COS to see
> inside zcode.

and, on the GitHub link (OQ-2, *Answered 2026-10-13*): "i gave it a fine grained PAT
instead." and "zcode repos only, oauth removed, no other logins".

ZCode then moved again, from the VM to an AppImage in its own docker container on the NixOS
host. SPEC-136 was revised for that in #2818 (tracked by #2703): BND-1 and BND-2 were
tightened for a container and BND-6 was added. The spec's *Terms* records that "the VM" in
his quoted answers now means this container. No verbatim founder sentence about the
container move is recorded in the spec; the move is stated there as a fact.

SPEC-136's *Decision records* section says the boundary "is a founder decision that
outlives this spec and belongs in a decision record or the constitution. Not written here."
SPEC-136 and SPEC-139 (the ZCode plugin shell, #2702) rely on it; a
later spec that touches ZCode must too, after SPEC-136 is done.

## Decision

The boundary below is the founder's, set 2026-10-13 and revised for the container in #2818.
The wording follows SPEC-136 `requirements.md`, *The boundary*; where the two ever differ,
this record is the decision and the spec is fixed to match.

1. **BND-1 - One bridge.** Nothing on the host reads a file ZCode wrote, except content that
   arrived through git by way of GitHub. No shared folder, no mounted drive, no copied
   directory. ZCode's working trees live only in the container's own storage (its
   filesystem or a docker-managed volume), never in a host bind mount; no host path is
   mounted into the container, read-only or otherwise; and no display, clipboard or audio
   socket of the host (X11, Wayland, PulseAudio, PipeWire) is shared with it. If the
   AppImage needs a display, it gets one that lives inside the container or is reached only
   through a viewer that passes no files.
2. **BND-2 - No listener.** Nothing MinSpec ships opens a network port on the host for the
   container to call, and nothing in the container is given a port on the host. The
   container does not use the host network (`--network host` is forbidden) and publishes no
   ports (no `-p` or `--publish`).
3. **BND-3 - The container is not the gate.** A check that runs inside the container is help
   for the agent working there; whatever is being kept out of the host can switch it off.
   The checks that decide a merge run on GitHub.
4. **BND-4 - An approval made in ZCode counts only inside that ZCode project.** It takes
   effect there at once. The host never reads, trusts or builds on an approval that
   originated in the container, and never builds a ZCode project. ZCode's GitHub grant is a
   fine-grained personal access token that reaches ZCode repositories only (stated by the
   founder, not measured), never MinSpec and never any repository a host builder acts on.
5. **BND-5 - No supervision reaches in.** Nothing on the host watches, lists, messages or
   steers sessions inside the container, and nothing MinSpec runs in the container reports
   to the host. The host learns of ZCode work only from GitHub.
6. **BND-6 - Container confinement.** The container cannot act as the host. It is not given
   the docker socket (`/var/run/docker.sock` or a rootless equivalent); it is not run
   `--privileged`; it has no added capabilities (no `--cap-add`) and no security profile
   switched off (no `seccomp=unconfined`, `apparmor=unconfined` or `label=disable`); it
   shares no PID or IPC namespace with the host (no `--pid host`, no `--ipc host`); and root
   inside it is not root on the host (rootless docker or a user-namespace remap; a non-root
   user inside is not enough on its own). Together with BND-1 this keeps the host's
   credentials (`~/.claude`, `~/.ssh`, the founder's GitHub login, every `.env`) out of the
   container's reach.

**Who holds what.** BND-2's "nothing MinSpec ships opens a port", BND-4's "the host never
trusts a ZCode approval" and BND-5's "nothing MinSpec runs in the container reports to the
host" are properties of MinSpec's code, and SPEC-136's `boundary.test.ts` and
`vm-approval.test.ts` pin them (FR-10, FR-20 to FR-25). BND-1's mounts, BND-2's network
mode and ports, and all of BND-6 are properties of how the founder starts the container:
nothing MinSpec ships can check them from inside the container, and BND-5 forbids the host
from supervising it. Those are checked by measurement 12, below. BND-4's token scope is
measurement 8.

## The check: measurement 12

Measurement 12 (SPEC-136 `requirements.md`, *To measure before Plan*; scheduled as
`tasks.md` task 17.1) is the founder's own run, on the host, of `docker inspect` on ZCode's
container plus `docker info`. It reads the container's configuration, not anything ZCode
wrote, so it does not cross BND-1. The running container matches this record when every row
holds:

| Field read | Matches when | Rule |
|---|---|---|
| `Mounts` (every bind and volume) | No `bind` entry with a host source path; volumes are docker-managed only | BND-1 |
| `Mounts` | No docker socket (`/var/run/docker.sock`, or `$XDG_RUNTIME_DIR/docker.sock` for rootless) | BND-6 |
| `Mounts` | No X11 (`/tmp/.X11-unix`), Wayland (`$XDG_RUNTIME_DIR/wayland-*`), PulseAudio or PipeWire socket | BND-1 |
| `HostConfig.NetworkMode` | Not `host` | BND-2 |
| `HostConfig.PortBindings` | Empty or null | BND-2 |
| `HostConfig.Privileged` | `false` | BND-6 |
| `HostConfig.CapAdd` | Empty or null | BND-6 |
| `HostConfig.SecurityOpt` | No `seccomp=unconfined`, `apparmor=unconfined` or `label=disable` | BND-6 |
| `HostConfig.PidMode`, `HostConfig.IpcMode` | Neither is `host` | BND-6 |
| `docker info` `SecurityOptions`, `HostConfig.UsernsMode`, `Config.User` | Docker is rootless (`name=rootless`) or runs with a user-namespace remap (`name=userns`), and `UsernsMode` is not `host`. `Config.User` is recorded but does not satisfy the row alone | BND-6 |

The result goes into SPEC-136 `design.md` under a *Measurements* heading with the ZCode
version, as task 17.1 says. **State at the time of writing: not yet run** (`design.md` has no
*Measurements* heading). Until it is run, BND-1's mount half, BND-2's network half and
BND-6 are stated, not observed.

A row that fails means the container is out of line with this decision. The fix is the way
the container is started, not this record; a change to the rules themselves needs a new
decision record that supersedes this one. Measurement 12 is a one-time observation: a
later change to how the container is started is not watched by anything (BND-5 forbids a
host-side watcher), so it is re-run after any such change.

## Accepted cost

- **Shared kernel.** A container shares the host's kernel. A kernel exploit run inside the
  container escapes it, and then BND-1 to BND-6 all fail at once. A VM did not share the
  kernel; moving to a container accepted this.
- **The bridge carries files that run.** A pull brings files onto the host, and some run
  there. `.claude/`, `.vscode/` and a project's `.minspec/hooks/` are not in the
  machinery-path set that forces a human look today. Until #2708 lands, BND-1 rests on
  review for those paths, not on a gate.
- **No proof an approval in ZCode was his.** Inside a ZCode project a session can build on a
  spec it approved itself. The protection is that the host never trusts or builds a ZCode
  project; it rests on the token's scope (measurement 8, stated, not measured) and is gone
  the day the host starts building a ZCode project.
- **No live check.** Container configuration can drift after measurement 12 with nothing to
  notice, because the host may not supervise the container (BND-5).
- **Text still crosses.** Text a misbehaving ZCode session writes can be read by a host
  agent after it merges through GitHub. The founder accepted the spec's recommendation on
  this (SPEC-136, *What "infected" covers - answered: as recommended*): files that run on
  the host are the hard line; text is reviewed data that arrives through GitHub.

## Rejected alternatives (DR-086 section 4)

- **Put the boundary in the constitution instead.** SPEC-136 named both homes. Rejected:
  the constitution holds invariants of MinSpec as shipped to every adopter (blast radius,
  DR-074), while BND-1 to BND-6 describe one founder's machine and how he starts one
  container. A record can be superseded by a later founder decision without amending the
  constitution. Cost of this choice: the boundary is not in the invariants every session
  reads first; it is reached through SPEC-136's INV-4 and this record.
- **Leave it in SPEC-136 alone.** Rejected: the spec says the boundary outlives it, and
  SPEC-139 (the plugin, #2702) depends on it too. A spec marked `done` stops being read.
- **Have a host script run `docker inspect` on a schedule and fail visibly.** Rejected for
  now: BND-5 forbids the host from watching or listing what runs in the container, and
  SPEC-136 makes measurement 12 the founder's own act. Cost: drift goes unseen (above).
- **A VM instead of a container.** Rejected by the founder's move to a container (#2818),
  which accepted the shared-kernel risk above.
- **A host-side tool server for the container to call.** Rejected by BND-2 (SPEC-136,
  *Alternatives considered and rejected*).
- **An outside GitHub review before a ZCode approval reaches main (OQ-1 Option B).** Kept as
  the fallback if measurement 8 shows the token reaches a host-built repository; not adopted
  now. DR-056 and DR-081 are relied on, not amended.

## Consequences

- SPEC-136's INV-4 and every FR that cites BND-1 to BND-6 trace to this record; so does
  SPEC-139.
- Any future MinSpec feature that would read ZCode files on the host, open a port between
  host and container, report from the container to the host, or let the host build on a
  ZCode approval contradicts this record and needs a superseding record first.
- Every MinSpec check inside the container is advisory to the agent there; merge-gating
  stays in GitHub Actions (BND-3), consistent with "no silent gate" (constitution
  invariant 2).
- MinSpec stays Tier 0 inside the container (DR-004): the boundary adds no network call.

## Rollback

Supersede this record with a new founder decision. No code keys on this record's content
(a grep for its id on 2026-10-28 found only this file, INDEX.md and an unrelated test
fixture in SPEC-252), so withdrawing it removes no behaviour; the tests that pin the MinSpec-side rules live in
SPEC-136 and change only with that spec.
