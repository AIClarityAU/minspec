# DR-074: MinSpec's blast radius is the project it is installed in

> **Born `proposed` per DR-029** — acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note.

## In plain terms — what this changes for you

**What happened.** You opened an unrelated project — your NixOS config, no MinSpec in
it, no MinSpec extension installed in that editor — and the agent still refused to file a
GitHub issue for you. It had read a MinSpec rule that lives in your machine-wide
`~/.claude/CLAUDE.md`, found that rule stated as an absolute MUST with no way to satisfy
it in that repo, and stopped.

The agent's reasoning was right at every step. The rule's *reach* was wrong.

**What this DR decides.** MinSpec only governs a project that opted in, and the opt-in
marker is a `.minspec/` directory at the repo root. In a repo without one, MinSpec's rules
do not apply, do not partially apply, and are not something to work around — they are not
there. Inside a MinSpec project a rule may still be as absolute as it likes.

**Why it needs a decision.** MinSpec is a methodology as much as an extension, and
methodology travels as prose. A convention written into a machine-wide config file reaches
every project on the machine, silently, forever, with nothing to stop it — no marker, no
uninstall, no signal to the person in the other project that a rule from somewhere else is
now binding on them. That is a one-way door, and it is exactly how a helpful tool becomes
one you resent.

**The one sanctioned exception.** If you administer an org and you *want* MinSpec required
across it, you can say so explicitly. That widens the gate on purpose, by an admin's
deliberate act. Nothing else widens it — not a GitHub App installation, not a user
setting, not an agent inferring that this repo looks like it should have MinSpec.

**What you get:** a project you did not opt into behaves exactly as it did before MinSpec
existed on this machine.

## Context

MinSpec's harness has always been careful about *files*: every managed region is
marker-bounded so a refresh overwrites MinSpec's part and preserves yours (#249, DR-037),
and DR-073 §3 extended that to a foreign tool's config file under a four-part
never-clobber contract. DR-073's rejected alternatives already contain this DR's ruling in
miniature:

> **Install the hook globally in `~/.claude/settings.json`.** Rejected by the maintainer:
> a per-project harness must not reach into the user's machine-wide config.

That was a ruling about one hook, recorded where rejected options go. #1147 shows the
general case was never written down, and had already been violated by prose rather than by
code.

**The instance.** `~/.claude/CLAUDE.md` — the user's global, all-projects Claude Code
memory, loaded in every session on the machine — carried a section headed *Agent GitHub
Identity (minspec#995)* opening with an unconditional absolute:

> **Agent GitHub writes MUST be bot-attributed, never posted under the human's account.**

Three facts then collide:

1. The rule is **global and unconditional**. No scope sentence, no marker, no way for a
   reader in another project to know it was not meant for them.
2. The mechanism that satisfies it is **org-scoped and repo-selected**.
   `gh-app-token.sh` resolves an installation per org, defaulting `MINSPEC_APP_ORG=AIClarityAU`;
   App `4212099` is installed there on four selected repos. **Machine-local evidence, not
   citable from this repo** — the script lives at `~/.claude/scripts/`, outside every
   checkout, so a reader cannot re-run this from the diff. Observed 2026-07-31:
   `MINSPEC_APP_ORG=harvest316 gh-app-token.sh --check` → *App 4212099 is not installed on
   org 'harvest316'*; `gh api /installation/repositories` → `minspec`, `scroogellm`,
   `sealbox`, `scroogellm-feedback`. The last of those **is** reproducible with a token from
   any AIClarityAU repo.
3. In any repo outside that installation, **no token path satisfies the MUST**. Posting
   under the founder's account would be borrowed identity, which a separate standing rule
   correctly forbids. So the agent stopped and reported.

The behaviour was right; the scope was wrong. A global MUST backed by a four-repo
mechanism silently converts every other repo on the machine into *the agent cannot write
to GitHub at all*.

**Why not just install the App more widely.** That was the first-pass fix and the founder
rejected it: *"i dont want it installed on harvest316/nixos."* Widening the mechanism to
match an over-broad rule is the wrong direction — it grants MinSpec's bot write access to
repos that never asked for MinSpec, to make a rule true that should never have applied
there. The rule narrows; the mechanism stays where it is.

## Decision

**1. The invariant.** MinSpec's blast radius is the project it is installed in. Nothing
MinSpec ships — extension write, harness file, hook, CI workflow, convention, or prose
rule — may change behaviour in a repo, org, or machine-wide config that did not opt in.
Proposed as a new **Invariant**; the redline is §5 below and it lands at Accept-ADR, not
with this record (DR-029). Nothing in `.minspec/constitution.md` changes in this DR's own
commit — that is the DR-066 sequence (`dfc6302` proposed, `c512187` accepted, `a0de4df`
applied the redline).

**2. The opt-in marker is `.minspec/` at the repo root.** One marker, checkable by a
human, an agent, or a script, with no ambiguity and no inference. "This repo looks like it
uses MinSpec", "this repo is in an org that uses MinSpec", and "the GitHub App can reach
this repo" are **not** markers and must never be treated as one.

Note what the marker is **not** today: there is no single canonical "is MinSpec active
here" check to point at. `activate()` (`packages/minspec/src/extension.ts:60`) runs
**unconditionally** — `activationEvents` is `[]` (`packages/minspec/package.json:63`) — and
the `.minspec/` reads that do exist are per-feature: `.minspec/constitution.md` gates the
constitution *nudge* (`packages/minspec/src/extension.ts:694`, inside
`surfaceConstitutionProposeNudge`) and `.minspec/config.json` is the first-init marker
(`packages/minspec/src/commands/init.ts:1028`). This decision
names the marker; it does not claim the codebase already funnels through it. That gap is
part of what [#1150](https://github.com/AIClarityAU/minspec/issues/1150) has to close.

**3. Machine-wide surfaces are out of bounds for a per-project write.** `~/.claude/**`,
`~/.gitconfig`, `~/.config/**`, and shell profiles are the user's, not a project's. MinSpec
does not write them. This restates DR-073's rejected alternative as a general rule rather
than a one-off ruling.

**4. A MinSpec rule that must live on a machine-wide surface carries its own scope gate,
in its own text, at the top.** Some MinSpec conventions genuinely have to sit in global
memory to be useful — they govern agent behaviour before any project is open. Those are
permitted, on one condition: the rule states the `.minspec/`-presence gate before it states
the rule.

The triggering rule, `~/.claude/CLAUDE.md` §*Agent GitHub Identity*, was amended to this
shape on the machine on 2026-07-31. **That claim is not verifiable from this repository** —
the file is unversioned and machine-local, so it appears in no diff and no reviewer can
check it. It is recorded here as context for why the incident stops, not as evidence this
DR ships. What this DR ships is the rule that such an amendment is mandatory.

**5. Inside scope, absolute is fine; outside scope, the rule does not exist.** This is the
founder's framing and it is load-bearing in both directions. A scoped rule does not get
softened into a default or a preference to make it safe to apply everywhere — softening is
how a gate becomes advisory (DR-066, no silent gate). It gets a boundary instead, and
inside that boundary it keeps all its teeth.

**6. The three cases are enumerated, so "blocked" is never the fallback by accident.**

| Repo state | Behaviour |
|---|---|
| No `.minspec/` | MinSpec rules do not apply. Normal `gh` identity. A missing App installation is not a blocker and must not be reported as one. |
| `.minspec/` present, App installation covers the repo | The absolute rule applies. Mint the bot token. |
| `.minspec/` present, no App installation | Do **not** fall back to the human account — that is borrowed identity. Report the unfiled item with a ready-to-run command and continue. This is the designed path, stated as such. |

The third row is what #1147 hit while in the *first* row. Naming all three removes the
gap where an agent infers a blocker from an unstated case.

**7. The only widening is an explicit org-admin opt-in policy** — tracked as
[#1149](https://github.com/AIClarityAU/minspec/issues/1149), not shipped by this DR. It
must be set by an admin, discoverable from inside any repo in the org, widening-only (it
can pull an unmarked repo into scope; it can never push a `.minspec/` repo out, and never
reaches outside the org), and visible in the repos it captures. Absence of the policy means
per-repo scope. A GitHub App installation is **not** this policy and must not be read as
consent.

## §5 — Proposed constitution amendment (redline at Accept-ADR)

Add one **Invariant** (an absolute never-break rule, not a Principle: a MinSpec rule
reaching into a repo that did not opt in has no legitimate exception — the sanctioned
widening in decision 7 is an *opt-in*, which is consent, not an exception to it).

Nothing in `.minspec/constitution.md` changes in this DR's commit. The redline applies when
the human accepts, per DR-029 and the DR-066 sequence.

Proposed addition to `## Invariants`:

```
- MinSpec's blast radius is the project it is installed in — nothing MinSpec ships
  (extension write, harness file, hook, CI workflow, convention, or prose rule) may change
  behaviour in a repo, org, or machine-wide config that did not opt in, and the opt-in
  marker is `.minspec/` at the repo root. Machine-wide surfaces (`~/.claude/**`,
  `~/.gitconfig`, `~/.config/**`, shell profiles) are out of bounds for a per-project
  write, and any MinSpec rule that must live on one carries its own `.minspec/`-presence
  scope gate in its text. Inside scope a rule may be absolute; outside scope it does not
  exist. The only widening is an explicit, opt-in org-admin policy, never an implicit
  reach. (DR-074; the narrow precedent is DR-073's rejected "install the hook globally in
  `~/.claude/settings.json`" alternative, generalised, with DR-073 §3's four-part contract
  governing how a foreign file may be written once it is in scope; instance: minspec#1147.)
```

**At Accept, also regenerate the harness mirrors.** The `## Invariants` summary in
`CLAUDE.md`, `AGENTS.md`, and `.cursorrules` is generated from this list, so applying the
redline without *MinSpec: Refresh Harness Files* leaves them claiming two invariants where
the constitution has three. No CI gate enforces that parity today (#890), which is why it
is written down here rather than assumed.

## Consequences

- The #1147 incident stops: a session in a non-MinSpec repo posts under the normal `gh`
  identity and files the issue, because the rule that stopped it no longer reaches there.
- MinSpec gains a stated containment boundary it can be held to, rather than one that
  existed only as a maintainer's instinct in a rejected-alternatives list.
- Every future MinSpec rule now has a placement question with a defined answer: does it
  need a machine-wide surface, and if so where is its scope gate? DR-073's four-part
  contract governs *how* MinSpec writes a foreign file; this DR governs *whether* it may.
- **The enforcement is prose, therefore model-trusted, therefore it will drift.** That
  directly contradicts the constitution principle *"Don't hope an LLM will follow rules —
  enforce it via code."* Filed honestly as
  [#1150](https://github.com/AIClarityAU/minspec/issues/1150) rather than left implied;
  until it lands, the invariant is an honour-system clause and should be described that way.
- The scope gate costs a lookup: an agent must check for `.minspec/` before applying a
  MinSpec rule. Cheap — but note decision 2: no single canonical "is MinSpec active here"
  check exists in the codebase today for that lookup to reuse.
- Until the human accepts, the constitution is unchanged and the containment rule is a
  *proposal*. The `~/.claude/CLAUDE.md` amendment is already live on the machine, so the
  #1147 incident stops either way; what acceptance settles is whether the rule binds
  MinSpec generally.

## Alternatives considered

- **Install the App on `harvest316` (and/or switch AIClarityAU to all-repos).** Rejected by
  the founder. It widens a *mechanism* to satisfy a rule whose *reach* is the actual
  defect, and it grants bot write access to repos that never opted into MinSpec.
- **Soften the rule to a default — "prefer bot attribution".** Rejected: a gate that
  degrades to a preference is the failure DR-066 exists to prevent, and the founder was
  explicit that absolute is correct inside scope. Boundary, not dilution.
- **Delete the section from `~/.claude/CLAUDE.md` and move it into each MinSpec project's
  CLAUDE.md.** Rejected for now, though it is the most orthodox reading of decision 3. The
  rule governs agent GitHub identity *before* a project is necessarily open, and the harness
  CLAUDE.md is a generated managed region (#705/#763) that is regenerated by the extension,
  not hand-edited. Decision 4's in-text scope gate gets the containment without a harness
  change. Revisit if #1150's backstop makes the migration cheap.
- **Detect MinSpec by the extension being installed in the editor.** Rejected: it is a
  property of the *editor*, not the *project*, so it would re-create the exact bug in
  mirror image — the host-side Codium in #1147 had no MinSpec installed and was still
  governed by MinSpec rules, and a machine that *does* have it installed would have every
  project captured.
- **Let the GitHub App installation define scope.** Rejected: it conflates a credential
  grant with a methodology opt-in. A repo can be reachable by the bot without being
  MinSpec-managed, and a MinSpec repo can exist in an org with no App at all (row 3 above).
- **Write the invariant into `.minspec/constitution.md` in this same commit.** Rejected on
  review: DR-029 makes acceptance a separate human act, and every existing invariant traces
  to an *accepted* DR (DR-066, DR-071). Doing both at once has the record enact its own
  outcome — the same borrowed-authority failure as an agent minting a human sign-off. §5
  carries the exact redline instead.

## Costly to Refactor

Moderate, and asymmetric. Narrowing scope later is cheap — a rule stops applying and
nothing that depended on it was legitimate. Widening is what costs: once a MinSpec
convention has been binding machine-wide for a while, other work quietly starts assuming
it, and the removal reads as a regression. That asymmetry is the argument for the strict
default. Decision 7 (org-admin opt-in) is the pressure valve; if it is ever made implicit
or inferred, this DR is void and needs replacing rather than amending.
