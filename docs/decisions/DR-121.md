# DR-121: Plan artifacts merge on AI review once their spec is approved

> **Born `proposed` per DR-029.** Acceptance is a separate human act (*MinSpec: Accept
> ADR*). This record is `kind: direction` and widens a delegation, which DR-108 (the
> delegated-approval record) section 2 says no agent may do ("Agents may tighten or suspend
> a delegation, but never widen one"), and DR-108 section 4 says a queue item cannot carry
> consent. So nothing here takes effect until the founder accepts it, and no code changes
> before then.

> **On this record's number.** The id one below this is held by open pull request #3497. This is the next
> id above the highest on `main` (DR-119, at `5594e446`) and in every open pull request,
> read 2026-11-06. The collision gate re-checks it on this record's own pull request.

## In plain terms

You said on 2026-09-30: "i never want to approve a design.md or tasks.md". The delegated
lane was then written to refuse every plan pull request, and to leave them for you. That
refusal came from a summary of your words, not your words. With this decision, a
`design.md` or `tasks.md` pull request is merged by the bot, with no keystroke from you,
once three things hold: the spec it plans is already approved on `main`, the AI review
passed on the exact commit being merged, and CI is green on it. Everything else you kept
stays yours: memory-fabric, decision records, the constitution, the delegation file, the
stop list, `--admin`, and anything labelled `hold:*`.

The cost you accept: a plan with a defect the AI reviewer missed reaches `main` without a
human look. A plan is guidance for the build, not the build itself, and the build still
goes through its own review and CI. Accepting this replaces reviewing about 35 plan pull
requests one by one, and every later one.

## Context

a design.md or tasks.md'. That is a statement about which documents need his attention. It
names no exception for plan artifacts.

once AI review passes; memory-fabric, plan-only pull requests and governance files stay

**What earlier records said.** SPEC-031 (reviewer for all approvables) OQ-1, resolved:

only on the high-criticality types." SPEC-283 (new approvables land on main), D3 option A,
says plans "follow the spec's own approval", and marks that as "current practice,
unverified in a DR". This record is that DR.

**Where the exclusion lives in code** (read at `5594e446`):

  and `:186-188` refuses any pull request carrying such a path with reason `plan-artifact`.
- `scripts/lib/delegated-approval-caller.ts:73` holds a second copy of the same regex.

**What it costs today.** Measured 2026-11-05T21:15Z by the runner and job

## Decision

### 1. The amendment

DR-119 section 5 is amended: **plan artifacts are removed from "What stays the founder's"**,
under the conditions in section 2. Every other class in that list stays the founder's:
memory-fabric; any decision record; the constitution; `.minspec/delegations.json`; DR-086
(the autonomy stop list); the bot-merge record; `--admin`; and any pull request with a
`hold:*` label. Nothing else in DR-119 changes.

### 2. When a plan pull request may be merged by the delegated lane

All of these hold, read fresh on every run. Anything unreadable refuses, and an error turns
the run red (constitution invariant 2).

1. **This record is `accepted` on `main`.** The repository is AIClarityAU/minspec;
   memory-fabric is refused by its hard-coded name, as now.
2. **The diff is plan artifacts only, for one spec.** Every changed path is
   `specs/<project>/SPEC-NNN-<slug>/design.md` or `.../tasks.md`, added or modified, all
   under the same spec directory. A pull request that also touches that spec's
   `requirements.md`, an approval record, a decision record or any other path is not a plan
   pull request and is judged (or refused) as it is today.
3. **The spec it plans is approved on `main`.** On the base tip, the spec's
   `requirements.md` has an approval record whose `specHash` equals `specHash()` of that
   `requirements.md` (the approval is not stale), and its `status:` is `planning`,
   `implementing` or `done`, never `new` or `specifying`. A plan for a spec that is not
   approved waits, however good it is (see Cost).
4. **The same pins as DR-119 section 1,** applied to this pull request:
   - the author is user type `Bot`, login `minspec-sdd[bot]`, and every non-merge commit is
     attributed to that account (item 2);
   - labels: `ai-review:pass`, and no `ai-review:changes`, `ai-review:blocked` or `hold:*`
     (item 3);
   - the AI review passed on the head sha being merged, read again from the check-run and
     the latest review comment, not trusted from a label alone (item 9's re-read);
   - CI green on the head: every latest check finished SUCCESS, SKIPPED or NEUTRAL, every
     required check present and green; zero, pending, failing or missing refuses (item 10);
   - the merge is pinned to the judged head sha; never `--admin`, never native auto-merge,
     never a force-push (item 11).
5. **The delegation and its tripwire hold.** `evaluateDelegation` passes against the base's
   `.minspec/delegations.json`, and DR-119's tripwire is not tripped. A plan merged this way
   and later reverted counts toward that tripwire.

### 3. Code that changes after acceptance, not before

None of this changes in this record's pull request. Once accepted, a build issue changes:

- `scripts/lib/delegated-merge.ts`: the `plan-artifact` refusal at `:186-188` becomes a
  branch that admits a pull request meeting section 2, and the `PLAN_ARTIFACT` regex at
  `:82` stays as the classifier for that branch.
- `scripts/lib/delegated-approval-caller.ts:73`: unchanged in what it does. That caller
  approves; plans are never approved separately under this record, so it keeps refusing
  them.
- `scripts/drain-inbox.sh:1685-1699`: stops skipping plan pull requests before judging, so
  they reach the judge; the regex at `:1694` stays, and the parity test in
  `packages/minspec/tests/drain-delegated-merge.test.ts` keeps pinning it to the judge's.
- Tests: one per condition in section 2, each with a mutant that removes the guard and goes
  red, plus the regression for #2872 (a plan pull request with `ai-review:pass` whose spec is
  approved lands).

The build follows this repo's normal review and merge; it is code, not a delegated act.

## Cost and risk

- **A plan merged early invites building early.** SPEC-283 D3 says exactly this: "a plan
  landing before its spec is approved invites building early". That is why section 2 item 3
  is in: no plan lands unless its spec is approved on `main` and the approval is not stale.
  A plan written against a spec that later changes is caught the same way, because a changed
  `requirements.md` stales the approval and holds the next plan pull request.
- **A wrong plan lands with no human look.** What stands between it and `main` is the AI
  review panel, CI and the conditions above. The build that follows a plan has its own
  review, so a plan defect is caught there or costs a plan revision, not a shipped defect.
  This is the same risk SPEC-031 OQ-1 accepted for the dogfood.
- **More merges to `main` in a burst.** About 35 pull requests while the backlog drains,
  putting other open pull requests behind more often for those hours.
- **A defect in the judge lands something unreviewed.** Bounded as in DR-119: the judge runs
  from `main`, each guard has a test whose mutant goes red, and the ruleset still decides.

## Rollback

Move this record to `deprecated`. The judge reads its `status:` on every run, so plan pull
requests go back to being refused at once, and DR-119 section 5 reads as it did. A single
wrong plan is undone by reverting its squash commit, which also counts toward the tripwire.
A `hold:*` label stops one pull request.

## Rejected alternatives (DR-086 §4)

- **Keep plans with the founder.** Rejected: it contradicts his verbatim words, and a human
  gate must name the error only it catches (core tenet 1). It also stalls the drain today.
- **Merge plan pull requests whatever their spec's state.** Rejected: SPEC-283 D3's
  "invites building early" risk, with no compensating saving, since a spec still waiting for
  approval does not need its plan on `main` yet.
- **Have the bot approve plans as a delegated act, with approval records.** Rejected: plans
  are not signed off separately (SPEC-283 D3), so an approval record per plan adds a file and
  a review round per plan for no new check.
- **Change the code now and record the decision later.** Rejected: DR-108 section 2 forbids
  an agent widening a delegation, and section 4 says a queue item cannot carry consent. The
  founder's acceptance of this record is that consent.

## Consequences

- Plan pull requests for approved specs stop reaching the founder's queue, and #2980 can
  close once the build lands.
- The drain's held count falls by the plan pull requests that qualify, so spec-writing can
  resume under `MAX_HELD`.
- The audit trail shows `minspec-sdd[bot]` as merger, truthfully.

## Text to change

`scripts/validate-frontmatter.ts` (`validateDrAmendments`) fails an accepted record whose
target never mentions it, and MinSpec: Accept ADR refuses on the same condition. This

bot-merge record's note: the hash stays a true fingerprint of the text the founder accepted.
