# DR-078: Where standing push consent is stored

> **Born `proposed` per DR-029** — acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note.

## In plain terms — what this changes for you

When you click **"Always push from now on"**, MinSpec remembers that choice **for this
project only**. Open a different MinSpec project tomorrow and it will ask you once there
too.

Before this decision, the plan was to write it into your editor's global settings — one
click in one project would silently have turned pushing on for every repo on your machine,
including ones you had not thought about when you clicked.

## Context

Two accepted decisions pull in opposite directions, and SPEC-050 FR-8 sits exactly on the
seam.

- **[DR-071](DR-071.md) corollary** — `always` is a *personal* decision and belongs in a
  user's own settings, **not a shared repo file**. The failure it guards against is a
  standing consent committed into `.vscode/settings.json` and thereby imposed on everyone
  who clones the repo. That concern is real and unchanged.
- **Constitution invariant #3** (added by [DR-074](DR-074.md), accepted 2026-07-31) —
  MinSpec's blast radius is the project it is installed in. Nothing MinSpec ships may
  change behaviour in a repo, org, or **machine-wide config** that did not opt in, and the
  opt-in marker is `.minspec/` at the repo root. `~/.config/**` is named explicitly.

**SPEC-050 FR-8** resolves the first by reaching for `ConfigurationTarget.Global`, which
violates the second. Both were in force when the spec was approved; the spec's INV-1 is
thorough about DR-071's five conditions and silent about invariant #3.

The concrete failure ([#1225](https://github.com/AIClarityAU/minspec/issues/1225)): a
developer with MinSpec projects A and B clicks "Always push from now on" while approving
in A — a named, deliberate act scoped, in their mind, to A. The write is machine-wide. The
next `Alt+A` in B pushes to B's origin and auto-opens a PR there, with no prompt and no
moment at which B was consented to.

**The two decisions were never actually in conflict.** DR-071's corollary rules out a
*shared* location. Invariant #3 rules out a *machine-wide* one. "Personal settings" was
read as "VS Code User settings" because that is the familiar per-developer store — but it
is not the only one, and it is the one invariant #3 forbids. The conflict is an artifact
of that reading, not of the principles.

## Decision

**1. Standing push consent is stored per-project, in `.minspec/preferences.json`.**
Not `ConfigurationTarget.Global`. Not `ConfigurationTarget.Workspace`.

That file is already gitignored (`.gitignore:79`), already scaffolded
(`scaffold.ts:284`), and already holds FR-8's own one-time-offer memory under
`answeredSignatures`. It is therefore **per-developer** (never committed, so never imposed
on a co-contributor) **and** per-project (inside the `.minspec/` opt-in marker). It
satisfies DR-071's corollary and invariant #3 simultaneously, with no amendment to either.

**2. The offer and the consent it grants live in the same store.** The audit on #1224
found FR-8's "shown once" memory is per-repository while the setting it writes is Global —
so a developer who answers "Not now" in one project is re-offered in every other, while a
developer who answers "Always" silently changes all of them. Both halves now share one
scope, and that asymmetry cannot recur.

**3. `minspec.pushOnApprove` remains a real VS Code setting, and the contributed default
stays `prompt`.** DR-071 condition 1 is untouched. A user who *deliberately* sets
`pushOnApprove: 'always'` in their own User settings is exercising an ordinary editor
setting on their own initiative — that is not MinSpec writing machine-wide config, and
nothing here forbids it. What this DR governs is **what MinSpec itself may write**, which
is only ever the project-local store.

**4. Read order is project-local first, then the VS Code setting.** The project preference
is a narrower, more recently-expressed intent than a global default, so it wins where both
are present. Absent a project preference, the VS Code setting (and its `prompt` default)
applies unchanged, so existing configurations keep working.

## Consequences

- **SPEC-050 FR-8's text is superseded on this point.** It says "writes … to the user's own
  (Global) settings — never the workspace file". The parenthetical is now wrong. SPEC-050
  is hash-locked (approved 2026-08-05, #1175), so correcting the text costs a re-approval
  — see [#1179](https://github.com/AIClarityAU/minspec/issues/1179) for why that is more
  expensive than it should be. Until then **this DR is the authority** and the spec's
  parenthetical is the stale artifact; implementers follow the DR.
- **Reading a setting gains a second source.** Two-source reads are how silent
  disagreements start ([#1111](https://github.com/AIClarityAU/minspec/issues/1111) is a
  live example of exactly that). Mitigation: exactly one accessor function returns the
  effective mode, and no call site reads either store directly.
- **Cross-project convenience is deliberately given up.** A developer who genuinely wants
  push-always everywhere must set the VS Code setting themselves, once, by hand. That is
  the correct amount of friction for a machine-wide standing consent, and it is a
  *deliberate* act rather than a side effect of a click in one project.
- **FR-1..FR-7 are unaffected.** They never touched this axis; #1224's Slice 1 and the
  FR-1..FR-7 half of Slice 2 can land independently of this decision.

## Alternatives considered

- **`ConfigurationTarget.Global` (what FR-8 says) — rejected.** Violates constitution
  invariant #3 as written. Choosing it would require amending the invariant, four days
  after it was accepted, to permit the exact category of write DR-074 was written to stop.
- **`ConfigurationTarget.Workspace` — rejected.** Lands in `.vscode/settings.json`, which
  is commonly committed. That is precisely the shared-repo imposition DR-071's corollary
  names.
- **Amend constitution invariant #3 to carve out user-initiated named writes — rejected as
  unnecessary.** It would be honest, but it widens the invariant to solve a problem that
  option 1 solves without widening anything. Reserve amendments for conflicts that are
  real; this one dissolves under a better reading.
- **Drop FR-8, keep `prompt` — rejected as premature.** This is SPEC-050's own recorded
  contingency and remains available, but the zero-click outcome the founder asked for is
  achievable without violating anything, so paying a click per approval forever is not
  warranted.

## Costly to Refactor

Cheap to reverse — one accessor and one write target; no schema, no migration, and the
store already exists. Recorded because it settles an apparent conflict between two accepted
decisions, and a future reader finding FR-8's "Global" wording needs to see why the
implementation does something else.
