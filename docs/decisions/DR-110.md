# The verdict carry ignores where the base put the change

> **Born `proposed` per DR-029.** Acceptance is a separate human act
> (*MinSpec: Accept ADR*), and DR-086 keeps DR acceptance on the stop list (section 2,
> class 2). An agent never mints the sign-off. This record's live status is its
> frontmatter `status:` field, not this note.

> **On this record's number.** Taken from the collision gate
> (`scripts/check-dr-id-collision.ts`), which on #2926 on 2026-10-18 reported this record's id as
> the next free one across `main` and every open pull request.

## In plain terms - what this changes for you

When `main` edits a file your pull request also edits, but away from your change, updating
the branch used to re-run the whole review panel even though every line the reviewers read
was the same. With this record, that update carries the earlier pass instead, the same way
the earlier verdict-carry decision already carries one when nothing at all changed. A binary file is the exception: its
content is invisible in the diff, so any change to it is still reviewed.

its Alternatives rejected says:

> A position-insensitive identity, to also catch the 7 moved-hunk rounds. The context
> lines are part of what a voter reads, and a normaliser that ignores positions is a place
> a change can hide. Worth about 1.4 percent of quota on a sample of 7. Tracked as #2635.

2026-10-18, 4 base merges that refused the carry; in 2 of them the pull request's own

## Decision

**1. What the carry's input identity ignores.** Inside the `<untrusted_diff>` block only,
and only in a file section whose content is shown as text hunks:

- the blob ids on the `index <old>..<new> <mode>` line (the mode stays), and
- the start line numbers on each `@@ -a,b +c,d @@` hunk header (the lengths, and the
  function text git prints after the second `@@`, stay).

Everything else counts byte for byte: every added, removed and context line, whitespace
included; file headers, modes and renames; and the approval-provenance block after the
diff. The identity is versioned (`review-input/v2`), so no round recorded under the verdict-carry record's
byte-exact identity can be read as matching it.

**2. Why this is narrower than what the verdict-carry record rejected.** Its worry was that a normaliser
ignoring positions is a place a change can hide. The context lines are kept, so a base edit
next to the change is still reviewed; the hunk header's function text is kept, so a rename
of the enclosing function is still reviewed. What is given up is the line number, and the
claim is that a voter reading the same lines with different numbers would reach the same
verdict.

**3. Binary files keep their blob ids.** `scripts/review-branch.sh` runs a plain
`git diff`, so a changed binary file shows as the constant line "Binary files a/x and b/x
differ", and the blob ids are the only trace of its content. Dropping them, as the first
version of #2926 did, would let a pull request passed with binary content A carry that pass
to content B at the same path and mode. So the ids are dropped only from a section that
has at least one text hunk and no binary marker ("Binary files ... differ" or
"GIT binary patch"). A binary section, and any section with no hunk at all (an empty file
added, or a form the parser does not recognise), is hashed as written. The default is to
count, never to drop. A regression test with a real binary swap pins this
(`packages/minspec/tests/ai-review-verdict-carry.test.ts`, "#2926 T3").

**4. Everything else in the verdict-carry record stands.** What is carried (a pass only), the reviewer key,
the whole-listing rule, the disclosure, the staleness guard and default-on are unchanged.

## What this record changes in the verdict-carry record, and what it leaves alone

- **Changes.** The verdict-carry record's Decision, section 3 sentence that the input is "the exact bytes the
  voters are given", for the two positional fields in section 1 above; and its rejection of
  "a position-insensitive identity", which this record takes in the narrower form above.
- **Leaves alone.** Every other section of that record.

The verdict-carry record is not edited by this pull request. It is accepted, and a note there saying it has
been amended would be false while this record is proposed. On acceptance, add a note at
its Alternatives rejected entry pointing here, and add this id to that record's
`relates_to:` (#2927).

## What would reverse this decision

- A carried round, re-run, that does not pass where only positions moved. #2636 (measure
  the carry once live) is the sampling that would show one.
- A defect reaching `main` on a carry where only positions moved, that a voter reading the
  renumbered hunks would plausibly have caught.

Reversing is cheap: `planVerdictCarry` goes back to `patchFingerprint` of the raw input.
Every open pull request then re-reviews once, because the identity version changes.

## Alternatives rejected

Recorded per DR-086 section 4.

- **Keep the verdict-carry record's byte-exact identity.** Zero added risk. Leaves the base merges that only
  move the change paying for a full panel; the #2926 sample put that at 2 pushes in 26.
- **`git patch-id`.** Ignores whitespace, which is content in Python, YAML and Makefiles.
  Rejected again for the same reason the verdict-carry record gave.
- **Normalise blob ids everywhere, binary files included.** The first version of #2926. A
  swapped binary carries a pass unseen. Rejected by the security voter, and here.
- **Run `git diff --binary` in `review-branch.sh` so binary content is in the input.**
  Puts base85 blobs in front of the voters, costing tokens for content no voter can read,
  and changes the prompt for every pull request. Keeping the ids is the smaller change.

## Costly to Refactor

1. **The identity version** (`review-input/v2`). Any further change to what is normalised
   must bump it, or an old record could be read as matching. Check: a test asserts the
   normalised key never equals the un-normalised one.
2. **The binary-section rule.** If `review-branch.sh` ever changes how it prints a diff,
   the set of markers must follow. Check: the rule defaults to keeping the ids, so a form
   it does not recognise is reviewed, not carried.

## Consequences

- Base merges that only move the pull request's change carry the pass. Small: about 2 of
  26 pushes on the one sample.
- The guard is in the reviewer key, so every open pull request re-reviews once after this
  lands.
- A binary change always re-reviews, as before.
