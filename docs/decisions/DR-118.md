# DR-118: Issues labelled pipeline-blocker skip spec-first

> **Born `proposed` per DR-029.** Acceptance is a separate human act (*MinSpec: Accept
> ADR*). This record is `kind: direction`: it writes down a founder decision, which no
> delegation covers, so an agent never mints the sign-off. The quoted founder answer
> above is the decision being recorded, not an acceptance of this record.

> **On this record's number.** Taken from the collision gate
> (`scripts/check-dr-id-collision.ts --repo AIClarityAU/minspec --pr 3369 --base main`,
> run 2026-10-30), which printed `Next free id: DR-118` across `main` and every open pull
> request. The gate re-checks it on this record's own pull request; if it reports a clash,
> renumber to the id it prints.

## In plain terms - what this changes for you

An issue carrying the exact label `pipeline-blocker` no longer waits for a spec you read
first. When triage judges it a T3/T4 that an agent can build, it goes straight to a full
build (`agent-ready`) instead of the spec-only route (`agent-ready-specify`). Every other
T3/T4 still waits for your spec read exactly as before. The label never lifts a hold you
asked for (human-only), never builds something the triage agent declined, and never
builds something it could not size. The cost: for these issues, the one review-shaped
human moment DR-076 kept (reading a T3/T4 spec before building) is gone, so a wrong
design can be built and merged before you see it; the merge-time AI review still runs.

## Context

DR-076 (solo mode, accepted 2026-08-01) keeps "genuinely human moments", the first of
which reads: "**T3/T4 spec approval.** Reading a spec before building from it is where one
human-hour has the highest leverage." #1169 implemented that in the triage gate
(`scripts/triage-decide.sh`): an auto-buildable T3/T4 resolves to `agent-ready-specify` /
hold `specify`, so an agent may write the spec but nothing is built until the spec is
approved.

The spec-writing queue can be paused, and some issues are what unblocks the pipeline that
writes and builds everything else (#3282 and its siblings). Waiting for a spec read on
those stalls every issue behind them. On 2026-10-30 the founder answered queue item
pb1030 with the decision quoted in `triggered_by` above.

This record removes one of DR-076's enumerated human moments (the T3/T4 spec-first read)
for pipeline-blocker issues only, so it carries `supersedes_partial: [DR-076]`, as DR-081
did for the docs-lane park row. DR-081 added its "Amended by" note to DR-076 in a
follow-up commit after DR-081 was accepted (2cba847a, #1408), not while it was proposed.
This record follows that: DR-076 is not edited while this record is `proposed`, and the
note to add on acceptance is prescribed under "Text to change once accepted" below.

## Decision

1. **Scope.** Only an issue carrying the label named exactly `pipeline-blocker` (no case
   folding, no trimming, no prefix or look-alike) is affected, and only when the triage
   gate would otherwise have emitted the specify class: tier T3/T4, decision
   `agent-ready`, `human_only` explicitly `no`.
2. **Effect.** For that case the gate emits `agent-ready` / hold `none` instead of
   `agent-ready-specify` / hold `specify`. The `--fields` projection adds
   `exception=pipeline-blocker` only when the exception fires; the line is absent
   otherwise, so the record says which rule fired and every other output is unchanged.
3. **Where it lives.** Inside `scripts/triage-decide.sh`, the single deterministic gate,
   as an explicit `--label <name>` input that `scripts/triage-inbox.sh` fills from its own
   `gh issue view`, and only when the label's last applier is on the dispatch author list
   (see "Who can put the label there"). The verdict record triage writes is therefore the
   gate's real output, never a parent-side override of it. (The first draft of #3369 overrode the gate's
   label/hold pair in `triage-inbox.sh`; the review rejected that, rightly.)
4. **What does not move.** A human-only hold (asserted, missing or garbled), needs-info,
   a T3/T4 the agent did not affirm, an unsized tier, and a missing verdict block all keep
   their existing outcomes. T1/T2 are unchanged.

## Safety argument

- **Fail closed.** With no `--label` input, the exception is off. `triage-inbox.sh`
  passes no `--label` when it cannot read the label list, so an unreadable list keeps the
  spec-first route.
- **The agent cannot ask for it.** The triage agent reads the untrusted issue text and has
  no credentials; it only emits a verdict. Labels reach the gate from the parent's own
  `gh issue view`, and the agent's input vocabulary is unchanged.
- **Who can put the label there.** The author gate (`dispatch_issue_gate`,
  `scripts/lib/dispatch-author-gate.sh`) covers who wrote the issue's text and says nothing
  about labels, and anyone GitHub lets apply a label can put one on a listed author's
  issue. So `triage-inbox.sh` passes `pipeline-blocker` to the gate only when
  `dispatch_issue_label_gate` finds that the account in the label's most recent `labeled`
  event is on that same dispatch author list. Removing the label and applying it again
  replaces the applier. A non-listed applier, a missing actor, no such event among the
  newest hundred label events, or a failed or malformed read all withhold the input: the
  issue takes the spec-first route, the refusal is printed, and the triage comment says
  why. No issue template applies `pipeline-blocker`
  (`.github/ISSUE_TEMPLATE/agent-task.yml` applies only `inbox`; `bug.yml` and
  `feature.yml` apply `bug` or `feat` plus `inbox`, checked 2026-10-31), and a template's
  application would not pass this check unless its actor is on the list.
- **What this check does not cover.** It runs at triage, so removing the label after
  triage does not undo a record already written; the dispatcher reads the record, not the
  label. It trusts the App as an applier, so every path that can make the App apply a
  label is trusted too, the same residual the author gate states for `Bot:299695933`. I
  believe the event reports a label's current name, so renaming a label a listed account
  applied could satisfy the check; that is unverified, because testing it means mutating a
  real repository label.
- **Tests.** `packages/minspec/tests/triage-decide.test.ts` sweeps every T3/T4 x decision
  x human_only x label-set combination and asserts plain `agent-ready` appears only with
  the exact label, an affirmative decision and `human_only: no`, and that the label/hold
  pairs never cross. `triage-verdict-record.test.ts` pins that triage feeds the labels in
  and records the gate's output. `triage-label-applier.test.ts` drives the real
  `triage-inbox.sh` against a listed applier, a non-listed one, a failed read, and an
  unlabel then relabel by a non-listed account.

## Rejected alternatives (DR-086 section 4)

- **Override in `triage-inbox.sh`** (the first draft of #3369). Rejected: it moved class
  derivation out of the single gate, minted a verdict record the gate never emitted, and
  falsified the gate's documented invariant.
- **A new agent-emitted decision token** (for example `decision: build-now`). Rejected:
  the agent reads untrusted text, so an injected issue body could ask for it.
- **Edit DR-076 in place.** Rejected: DR-076 is accepted, and its earlier change went
  through a separate record (DR-081); an agent never rewrites an accepted record.
- **State that repo triage permission guards the label, and add no check.** Rejected: the
  label skips a human gate, and that permission is granted for unrelated reasons, which is
  why the author gate refuses to use it. The check costs one read, on labelled issues only.
- **Route the named issues by hand-editing labels.** Rejected: it leaves no verdict record
  for dispatch to check (#983) and does nothing for the next pipeline blocker.

## Consequences

- Pipeline-blocker issues reach a build without waiting on the spec queue or the founder.
- The founder loses the pre-build design read on those issues; the merge-time AI review
  and every other gate still apply.
- `shadow-triage.sh` runs the same gate without `--label`, so on a pipeline-blocker issue
  its shadow verdict records the specify route and logs a disagreement. That is
  measurement only (the shadow changes no outcome, #1338), but it inflates the
  disagreement count by one per such issue.
- The label becomes load-bearing: adding an issue template that applies
  `pipeline-blocker`, or adding an account to the dispatch author list, widens who can
  fire the exception, and neither should be done without revisiting this record.

## Rollback

Drop the `--label` handling from `scripts/triage-decide.sh` (or stop `triage-inbox.sh`
passing labels). Issues already routed keep their labels; re-run triage on them to put
them back on the specify route.
