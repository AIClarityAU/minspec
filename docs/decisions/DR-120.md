# MinSpec owns the adopter's parity workflow

> **Born `proposed` per DR-029.** Acceptance is a separate human act (*MinSpec: Accept
> ADR*). This record is `kind: direction`, because it claims a file in other people's
> repositories, and SPEC-079's plan reserves acceptance for the founder. No task accepts
> it. SPEC-079 task 5, the first write that reaches an adopter, waits for that acceptance.

> **On this record's number.** The collision gate's script needs a pull request number and
> `gh`, and this dispatch has neither. So the gate's own decision function,
> `decideDrIdCollision` (`scripts/lib/dr-id-collision.ts:324`), was run over `main` at
> `e116efe1` and every remote-tracking ref in this checkout (399, fetched within the
> hour). Seven refs add a decision record, and it answered the id in the frontmatter. An
> open pull request not fetched here is invisible to that, so the gate re-checks on this
> record's own pull request; renumber if it says so. Bodies here do not spell local ids of
> 100 and above, per the parent-register reference gate (#2148).

Triggered by: #1884, #2060. Build issue: #3418. Whole-spec build issue: #3251.

## In plain terms - what this changes for you

Each repo that uses MinSpec runs a workflow, `minspec-ci-parity.yml`, that checks its copies
of MinSpec's review files against the originals. Nobody at MinSpec ships that workflow: each
adopter wrote its own. That causes two faults. A sanctioned refresh writes an `ai-review.yml`
that the check can never accept, so red becomes normal. And its list of files is typed by
hand and has fallen behind, so unlisted files go stale with the check green.

With this decision MinSpec ships the workflow itself, generated from the same table that
decides what gets scaffolded. Both faults close at once.

**What it costs you, and why it needs your signature.** This is the first time MinSpec claims
a file an adopter wrote, and that door does not close easily:

- A repo that takes the managed copy cannot get rid of it by deleting it. The next refresh
  writes the file back, with its weekly fetch and its possibly red check. No opt-out exists
  today; the only way to keep the workflow out is an unmarked file at that path (decision 3).
  MinSpec cannot recall a copy already merged.
- The workflow fetches from fixed paths on minspec's `main`, so those paths become a promise
  to every adopter. Moving one turns their checks red until each refreshes.
- Every later change to the workflow reaches an adopter only when a human there pushes the
  refresh, one repo at a time.
- A repo with `.minspec/` and no copy gains a new CI job on its next refresh. That job may go
  red at once, on drift that was already there.

Nothing is overwritten without asking. A hand-written copy stays exactly as it is until a
human picks **Re-scaffold (overwrite)** on a message that says plainly what is happening.

## Context

Adopters check MinSpec's review files with a workflow MinSpec does not ship, so the check rejects what a sanctioned refresh writes and its file list falls behind what MinSpec scaffolds.

**Why one record.** SPEC-079 DQ-2 requires a record if it takes option (D), and SPEC-228 DQ-4

## Decision

### 1. MinSpec ships the workflow as a managed template

`.github/workflows/minspec-ci-parity.yml` becomes one `MANAGED_REGION_TEMPLATES` entry, with no
`condition`. Its file table and its trigger are rendered from the registry, so the list cannot
fall behind (SPEC-228 FR-1 to FR-3) and no second copy of the localization exists (SPEC-079
FR-1). `localizeMachineryPathsComment` is untouched: the check is made to accept the localized
region, and the region is not made to match the raw file, so DR-090 stands as written. SPEC-079
and SPEC-228 share this one entry and this one record.

### 2. It is named as a first claim

Every other managed file is one MinSpec wrote from the start. This one adopters wrote
themselves, and MinSpec says so to the person affected rather than shipping it as an ordinary
update (SPEC-079 FR-5, SPEC-228 FR-7).

### 3. How a refresh meets each state of the file

Only inside a repo with `.minspec/` at its root (`assertOptedIn`,
`packages/minspec/src/lib/scaffold.ts:1824`, DR-074).

| The adopter's file | What a refresh does | Source |
|---|---|---|
| Absent | Writes it, like any other managed file. This is SPEC-228 DQ-3 (a) | `scaffold.ts:1226-1229` |
| Hand-written, no markers (body not byte-identical to the template) | **Leaves it untouched** and warns, naming the first claim. Offers the consent-gated **Re-scaffold (overwrite)**, a whole-file replacement that happens only on that click | `scaffold.ts:1258-1270`, `:870`; `packages/minspec/src/commands/init.ts:1359,1375` |
| Managed copy with markers | Replaces the region and keeps the adopter's lines around it | `scaffold.ts:1273-1275` (managed-region rule, DR-037) |

The warning sentence is new and is set for this template only; every other template's warning
stays as it is (design.md *Taking over a hand-written copy*). Re-scaffold discards any local edit
in the hand-written copy, which is why the message tells the reader to compare first.

**Declining is possible only with a file in place.** Deleting the managed copy does not decline:
the next refresh finds the file absent and writes it back (the first row; `scaffold.ts:1226-1229`,
which skips only a template whose `condition` fails, and this entry has none). No opt-out or
tombstone exists today. The one way to keep the workflow out is an unmarked file at that path.
A repo with no file at all, such as the two #1817 reports, cannot decline.

**An adopter that keeps a hand-written copy may decline, and declining keeps the faults.** A kept copy stays on its old list and
stays red on `ai-review.yml`, and each refresh repeats the warning. MinSpec does not force the
change, and it does not hide that the change is pending.

### 4. Repos with `.minspec/` and no copy get one on refresh

They opted in through `.minspec/`, so constitution invariant 3 allows it, and they are the worst
case, with no parity witness at all. They cannot decline by doing nothing, and deleting the file
afterwards is undone by the next refresh (decision 3): the workflow, its weekly fetch and its
possibly red check come back. The added network access is the adopter's own CI job fetching
from minspec's `main` on a weekly schedule, on the pull requests its paths match and on demand.
MinSpec's extension, build and validate make no fetch, so constitution invariant 1 is untouched.

### 5. The canonical for a localized region is a generated file on `main`

Each template declares what a downstream check compares it against: the file at the same path on
`main` (`source`), a file generated from the template's own content (`rendered`), or nothing, with
a stated reason (`excluded`). `ai-review.yml` and the parity workflow itself are `rendered`, under
`parity-canonical/` at the repo root. `npm run validate` fails on a stale or hand-edited copy
(design.md *The parity declaration*, *The generator*).

**This creates a public contract.** The adopter's job fetches
`https://raw.githubusercontent.com/AIClarityAU/minspec/main/<canonicalPath>` and fails closed on a
failed fetch, as constitution invariant 2 requires. So a repo rename, a move of `parity-canonical/`,
or a `source` file moved on `main` reddens every adopter still holding the old table, until each one
refreshes. Any such move has to keep the old path serving through a transition, and the old table
has to be treated as still in use.

### 6. Every later change reaches an adopter only through a human-pushed refresh

Any change under an adopter's `.github/workflows/` needs a person to push it. No broader token and
no non-workflow path sourced at run time may route around that (SPEC-228 FR-9, where the App's lack
of `workflows: write` is reported, not checked from this repo). The rendered workflow is its own
parity row, so a stale copy reports drift on the adopter's next scheduled run. That means every change
to the parity set or workflow, however small, turns each adopter's check red until a human there
refreshes. Whether an adopter has made that check required is its own configuration and is not
established here; where it has, the red blocks merges until the refresh lands.

### 7. No sequencing on SPEC-068

In every adopter, the first write of this file is either a first scaffold or no write at all (a
hand-written copy is left alone, and Re-scaffold is a human act). DR-092 section 1 puts first scaffold
outside its gate. Later refreshes of the region are SPEC-068's general case, like every other managed
file. Until SPEC-068 is built, a refresh from an older extension build can write an older region, which
is DR-092's backward write; decision 6 makes that visible as drift on the next scheduled run, and it
stays possible in the meantime (SPEC-079 design.md DQ-4 row, SPEC-228 DQ-5).

### 8. DR-092 follow-up (d) stays separate and stops applying where the copy is replaced

The managed workflow carries a remedy line written to be true: update the extension to its latest
release, then refresh. So MinSpec does not re-ship the self-defeating advice (d) names. Correcting
sealbox's hand-written text remains (d)'s job, and it goes moot in any repo that takes the managed copy
(SPEC-079 FR-4, DQ-3). DR-092 is not edited.

### 9. The workflow skips itself in minspec's own repo

MinSpec's own CI-review files are the canonical and carry no markers, so the job could only report false
drift there. MinSpec commits the file but the job carries `if: github.repository != 'AIClarityAU/minspec'`
and is not a required check here. The skip is visible in checks as *skipped*, not silent.

## What this does not decide

- SPEC-228's remaining requirements (the counted fail-closed check, delivery of missing files) and its
  approval. Note for its Plan: its FR-6 and AC-2 name `gen-ci-templates.mjs` as what regenerates and checks
  the rendered copy, while SPEC-079's design adds `scripts/gen-parity-canonical.ts`. This record fixes only
  that the canonical is generated and held current by `npm run validate`; SPEC-228's plan reconciles its
  wording with that one generator.
- Parity eligibility for `minspec-validate.yml` and `.minspec/hooks/*`, and for conditionally scaffolded
  files. They are `excluded` by name, with reasons.
- Repairing any adopter by hand, which is operational work in another repository.

## Cost

- **Named risk: a defect in this template reddens every adopter that took it, at once.** They all compare
  against one `main`. Bounded by the FR-2 equality test, the validate staleness check, and the job's shell
  being run in a test (SPEC-079 design.md *Testing*). The fix then still needs a human push per repo.
- **Merge friction in adopters that require the check** (decision 6): a change here creates work in every
  adopter. That cost is the same in kind as today's parity check, with a wider list.
- **Immediate red on takeover.** A repo moving from 10 or 12 checked files to the full list is told about
  files it does not have. That is true drift, and SPEC-228 FR-8 requires the same refresh to deliver them.
- **Upkeep.** Editing `ai-review.yml` needs a second regeneration, and validate's error names both commands.

## Reversal

Before SPEC-079 task 5 ships, moving this record to `rejected` costs one revert of tasks 2 to 4, none of which
reaches an adopter. After it ships, reversal cannot be completed from this repo. Removing the registry entry
stops new writes, but every copy already merged keeps running and keeps fetching. Retiring it would take, I
believe (reasoned from the design, not tried): a last region that does no fetch, a human refresh in each
adopter, and only then deleting `parity-canonical/`. This is the one-way door the record exists for.

## Rejected alternatives (DR-086 §4)

- **(A2) Publish the transform for each hand-written copy to import.** Rejected: no distribution mechanism
  exists, and the compare logic stays hand-written in every adopter.
- **(B) Drop the localization.** Cheapest and fully reversible. Rejected: it re-opens #1486, and every adopter's
  `ai-review.yml` again names paths and a test that do not exist there (DR-090).
- **(C) Exempt `ai-review.yml` from parity.** Rejected: MinSpec cannot edit each adopter's file centrally, and it
  removes the one automated check on the most consequential file.
- **(E) A managed manifest the workflow reads (SPEC-228).** Rejected: `paths:` cannot be read from a file, it needs
  a one-time hand edit per adopter, and SPEC-079's compare defect stays.
- **(F) Fetch the list at run time, (G) a canonical-side check reading each adopter (SPEC-228).** Rejected: (F) leaves
  the trigger and compare logic hand-written; (G) needs cross-repo tokens and a network call from this repo's gates
  with no consent record.
- **Replace a hand-written copy automatically on refresh.** Rejected: it would drop adopter lines unseen. The marker
  rule says never clobber a file it cannot prove safe (`scaffold.ts:1267-1270`).
- **Hold takeover until SPEC-068 ships.** Rejected: nothing in the first write is gated by it (decision 7), and #1884
  is measured and live.

The design-level alternatives (re-applying the localization in shell, hashes in the workflow, generating all 16
canonicals) are recorded in SPEC-079 design.md and not repeated here.
