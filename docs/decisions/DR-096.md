# DR-096: Adopters get a frozen pre-strip basis and a third verdict

> Numbering note: the two numbers immediately above DR-093 are already claimed by open pull
> requests (#1956, and #2109/#2110 which claim the same one as each other). This record takes
> the lowest number no open pull request claims, the same convention DR-093 used. The numbers
> are written without their `DR-` prefix here on purpose, so the reference checker does not
> read a claim-in-flight as a dangling decision record.

## In plain terms

When ownership declarations leave the approval hash, every approval record minted before the
change stops matching. Locally that is a one-off migration. In somebody else's repo it is
not, because the thing that recomputes those hashes over there is a merge-gating review
input, and MinSpec ships it no gate, no snapshot and no migration to go with it.

Left alone, an adopter's reviewers would open a pull request and read `MISMATCH - a real
finding` against approvals that are perfectly valid. The fix is to give the tool enough
information to tell the two apart: ship a frozen copy of the old hash basis alongside the new
one, and let the tool say so in its own words rather than guess.

## Context

DR-088 decided that ownership declarations leave the canonical approval hash. Its "Still
open" item 2 asked what adopters get, and assumed the answer could be a flag on the
scaffolded spec-gate. SPEC-070's FR-11 established that the premise is false: the spec-gate
is not scaffolded. What MinSpec actually writes into an adopter repo is two managed
templates - `scripts/hooks/canonical.py` (registry entry `canonical-hasher-python`) and
`scripts/approval-provenance.py` (registry entry `approval-provenance-script`), which imports
the former at load time. `scripts/validate-frontmatter.ts` does not travel, so Rule 12 does
not travel either, and neither does the `ownedAtApproval` producer, which lives in the
extension.

So the adopter-facing consequence of the strip is a **silent hash-basis change underneath a
merge-gating review input**. `scripts/review-branch.sh` invokes the provenance tool on every
review, so the first thing an adopter would learn about DR-088 is their own review panel
calling their own valid sign-offs a finding.

SPEC-051 INV-2 anticipated that a change to the DR-034 hashing contract needs its own DR and
explicit human sign-off. DR-088 is that DR for the strip itself. This is a second decision,
about delivery rather than about the hash, and it exists because DR-088 could not answer its
own item 2 from a false premise.

## Decision

Adopters receive **option (d)**, raised while planning SPEC-070 and accepted by the founder
on 2026-09-25:

1. The widened `canonical.py` ships **immediately, to everyone, with no flag and no opt-in.**
   The strip reaches adopter repos the moment they refresh.
2. A **frozen, diagnosis-only copy of the pre-strip basis** is scaffolded alongside it. It is
   versioned once and never changes again. It can be read; it can never mint.
3. `scripts/approval-provenance.py` gains a **third verdict**: a record that fails under the
   live basis but matches under the frozen one reports

   > `PRE-STRIP BASIS - matches under the pre-ownership-strip hash; re-approve to move it forward`

   which is distinct from `MATCHES`, distinct from `MISMATCH`, and never green. It names the
   exit in the same breath, because re-approval is the only way forward and a verdict that
   does not say so is a dead end wearing a diagnosis.

Normatively this lives in SPEC-070 FR-11 and AC-23, with the register entry at SPEC-070's
OQ-2. This record is the decision and its price; the spec is the requirement.

### Why this is not the state DR-012 forbids

SPEC-070's OQ-2 names the risk exactly, in the course of rejecting option (b): a second basis
that must be kept alive and tested in both twins is "the 'two canonical forms' state DR-012
exists to avoid."

The distinction that makes option (d) survivable is **minting**. Two canonical forms are
dangerous because a signature stops meaning one thing when two different forms can both
produce one. The frozen copy produces nothing. It is read-only by construction, answers
exactly one question - "was this record valid before the strip?" - and no code path mints an
approval from it. A repo with the frozen basis installed still has exactly one way to create
a signature.

That is a real distinction, and it is not a free pass. See Consequences.

## Alternatives rejected

- **(a) An adopter-side migration alongside the template refresh.** Cleaner in principle, and
  rejected because it ships a corpus-rewriting script into repos MinSpec cannot test against.
  A script that rewrites human sign-offs is the last thing that should run untested.
- **(b) A hasher-version or `.minspec/config.json` flag, defaulting to the old basis.** The
  strip then does not reach adopters at all until somebody flips a flag they have no reason
  to know exists, so the #1649 equivalent stays blocked in their repos indefinitely. It also
  pays most of (d)'s cost - a second live basis in both twins - while additionally keeping
  that second basis **mintable**, which is the part DR-012 actually forbids.
- **(c) Accept the break and document it.** Zero engineering, and it puts `MISMATCH - a real
  finding` in front of adopters' reviewers on valid records. That trains people to distrust
  the one block that is never supposed to be noise, which costs more than the template does.
- **Keeping the `MISMATCH` and adding prose to the README.** A variant of (c). Prose does not
  reach the person reading a review comment at the moment they read it.

## Consequences

- **A new managed template** for the frozen hasher: an entry in `template-registry.ts` and a
  regenerated `ci-review-templates.ts`.
- **The membership pin moves.** `packages/minspec/tests/managed-region-enumeration.test.ts:94`
  asserts 31 today.
- **A fourth artifact under INV-5's twin-parity obligation.** The frozen Python basis and the
  frozen TypeScript basis must be proven to agree, exactly as the live twins are. This is the
  cost option (d) shares with the option it beat, and naming the frozen copy "diagnosis-only"
  does not reduce it by one test.
- **It is adopter-facing, so it cannot be un-shipped.** Reverting a commit does not reach a
  repo that already refreshed. Constitution invariant 3 is satisfied - `.minspec/` at the
  root is the opt-in marker and an adopter has one - but opting in to MinSpec is not the same
  as being told the hash basis moved, which is what the third verdict exists to say out loud.
- **AC-23 gets stricter as a direct result.** The acceptance criterion now proves "widened" by
  **executing** the scaffolded hasher and requiring it to agree with the shipped TypeScript
  `specHash` while differing from the frozen basis. Asserting that a file exists would have
  passed while shipping nothing.

## Risks

- **The frozen copy stops being frozen.** Its whole safety argument is that it never changes
  and never mints. Nothing structural enforces that yet; today it rests on the word "frozen"
  in a spec, which is the shape the constitution names as the failure mode. Tracked in #2116.
- **The third verdict becomes a third kind of noise.** `PRE-STRIP BASIS` is never green, so a
  repo with many old records sees it a lot until they re-approve. If that volume trains people
  to skim past it, (d) has reproduced (c)'s failure with extra steps. The mitigation is that
  the verdict names its own exit, so the reader always knows the action.
- **An adopter on a stale installed build hashes differently from one that refreshed** (#1492).
  Unchanged by this decision, and the third verdict makes it legible rather than silent.
