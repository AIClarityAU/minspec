## In plain terms

The AI review runs four independent voters. If one of them dies - a session limit, an API
5xx - the panel fails closed and the whole review is discarded, so the re-run pays for all
four again. This decision says the three that answered may be kept, **but only for a
re-review of the exact same commit.**

## Context

**The problem is recurring, not transient.** #535 and #2126 are both open and both describe
a voter dying mid-run. I originally filed #2142 calling it transient infrastructure; those
two issues refute that, and the correction is on the issue.

**The obvious sibling was already rejected.** #1840 proposed skipping the whole panel when
the patch was unchanged. It was closed not-planned on measurement: 7.3% of fingerprinted
runs re-reviewed an already-passed patch (3 of 41 over 7 days), **all three repeats on one
pull request, and all three new-SHA-identical-patch** - that is, base moves. So the saving
and the #1394 semantic-conflict risk were the same event, and about 32% of runs are
machinery `neutral`, which cannot be re-attested from at all. The instrument that measured
it is `scripts/review-churn-report.sh` (#1965).

That measurement is what makes this decision look suspicious, and it is why this record
exists: **per-voter reuse must not smuggle back in what whole-panel reuse was refused
for.**

## Decision

This is the contract of `selectVotersToRun` as implemented on #2163 (`ai-review-guard.js`),
not a sketch of one to be written. Reuse a single voter's verdict block on a re-run when
**all** of:

1. the record sits on an `ai-review` check-run whose `app.slug` is allowlisted -
   provenance, because this repository is public and any actor can forge a comment;
2. that check-run's `head_sha` **equals the head under review**;
3. its recorded `patch-fingerprint` equals the fingerprint of the patch under review;
4. the base64 payload round-trips to its recorded sha256 (a truncated record is dropped,
   never half-parsed);
5. the record is structurally a verdict block - not the fail-closed placeholder the
   workflow substitutes for a silent voter, not a `REVIEW_UNAVAILABLE` marker, not prose.

Among candidates on that SHA the **most recent wins**, by `checkRunTime` - the same helper
and the same rule `verifyHeadPassCheckRun` already uses.

Reuse copies the block **verbatim** and the caller re-combines, so a reused `changes` stays
`changes`. Reuse can never upgrade a verdict.

It deliberately does **not** require the prior run to have passed. A whole PASS needs no
reuse; the case worth salvaging is the run that failed overall *because* a voter never
reported.

### Why this is safe where whole-panel reuse was not

> **Amendment proposed on 2026-10-09 by the verdict-carry record; not in force until that
> record is accepted.** That record is the one in this register titled "An ai-review pass is
> carried across a push that changes nothing the voters are given". Its id is the last entry
> of this record's `relates_to:`; it is not spelled out here because the parent-register gate
> reads any decision id of one hundred or more, written in prose, as a reference into the
> parent register (#2148).
>
> It proposes carrying a whole panel's pass across a push that leaves the voters' input
> byte-identical under an unchanged reviewer. That includes the base-moved case the "#1840
> whole-panel" column below describes as refused. If it is accepted, that column stops being
> this repository's position for that one case: the #1394 exposure in its last row is then
> accepted, on a larger measurement (#2588) and inside the bounds that record lists, and
> "that is what closed it" becomes history.
>
> **What still stands either way:** this record's own decision. Per-voter reuse stays bound
> to one head SHA (condition 2), and nothing in the verdict-carry record relaxes
> `selectVotersToRun`.

| | #1840 whole-panel | this record |
|---|---|---|
| what is reused | the panel's PASS | one voter's verdict block |
| across commits? | yes, that was the point | **no - same head SHA only** |
| gate's claim afterwards | "this patch passed", on a different merge result | "these four voters reviewed this SHA", unchanged |
| #1394 exposure | yes, that is what closed it | none - the merge result is the same one |

The distinction is condition 2, and it is the whole decision. #1840's benefit **was** the
base-moved case; this record's benefit is a re-run of the same commit, so binding to the SHA
costs it nothing and removes the risk entirely.

### Why the SHA binding is in the code and not in a comment

**It was in a comment first, and the comment was false.** At #2163 `6c626a37` the docblock
of `selectVotersToRun` asserted "this reuses within ONE head SHA ... unlike #1840 there is
no base-moved semantics to trade away" while the function compared only the patch
fingerprint - so it reused across commits, which is precisely base-moved reuse, justified
by a sentence denying it. Its own test fed two different SHAs and proved the behaviour.
Three of the four voters on #2163 flagged it; the architect and skeptic blocked on it. It
was corrected at `f8db3489`.

**That commit is the only place the false comment exists.** It was never merged, so grepping
`main` for the quoted sentence returns nothing - which reads as a fabricated anecdote if the
address is missing. It was missing in this record's first revision, and the skeptic voter
blocked it for exactly that.

Root cause: **the safety property existed only as prose.** No test could fail if reuse
crossed a commit, so the claim and the code were free to disagree from the first commit -
and the test that should have caught it asserted a *different* property (recency) that the
code also did not have. `headSha` is a required argument whose absence reuses nothing
(#2163 @ `f8db3489`), and four mutants covering the binding and the ordering each fail a
test (`voter-survivor-reuse.test.ts`, same branch).

This is the constitution's *enforce, don't trust the model* applied to a comment, and it is
the same failure DR-003's evidence-discipline addendum names: a mechanism claim licensed by
a plausible inference from a true adjacent premise. The adjacent premise here was true -
`findReattestableVerdict` really does re-attest across SHAs - and the inference to "so this
one is fine" was wrong.

## Alternatives rejected

Recorded per DR-086 §4: under `autonomy: act` nobody sees these live, so this is the only
review path.

- **Widen the claim instead of narrowing the code** - keep cross-SHA reuse and rewrite the
  comment to admit it. Rejected: it re-adopts what #1840 was closed over, and the measured
  repeat population is *entirely* base moves, so it maximises exposure for a saving #1840
  already judged not worth it.
- **Reuse the whole panel when the head SHA is unchanged.** Tempting and nearly free, but a
  re-run on an unchanged SHA usually happens *because* something was wrong, and a whole-panel
  skip would make a genuinely re-triggered review a no-op. Per-voter keeps the re-run useful.
- **Require the prior run to have concluded `success`**, matching
  `findReattestableVerdict`. Rejected: it makes reuse impossible in exactly the case it is
  for. The prior run failed - that is the premise.
- **Carry the records in a PR comment** rather than a check-run. Rejected: a gate must not
  read a mutable surface, and in a public repo any actor can write a comment (#397).
- **Automatically re-run the dead voter** as well as reusing the survivors. Deliberately out
  of scope; the founder chose survivor-reuse only, so the expensive half stays
  human-triggered.

## Consequences

- The re-run cost of a partial failure falls from four voters to the ones that were
  actually missing.
- One more thing on the check-run output to keep compatible. It is feature-detected the way
  the `patch-fingerprint` marker is (#1925): the guard comes from the BASE checkout and may
  predate this, and every failure path yields *no reuse*, never a skipped voter with no
  verdict.
- **A silently-inert failure mode.** If the workflow stops passing `headSha`, or the
  allowlist is unset, reuse quietly does nothing while looking wired. That is safe but
  undiagnosable from the outside, which is why every refusal is written to the run log with
  its reason - including naming the allowlist specifically when the allowlist is what is
  missing.
