# The drain service defaults to concurrency 8

> **Born `proposed` per DR-029.** Acceptance is a separate act. This record is
> `kind: engineering`, so the delegated-approval path (DLG-001) can cover it, but only
> after the pull request that carries it is merged with an `ai-review:pass`, and only
> from a session that did not write it. Nothing here records anyone as having accepted it.

## In plain terms - what this changes for you

The background drain service (`scripts/drain-service/drain-service.sh`) now starts the
drain with 8 agents in parallel per cycle instead of 1, unless you set
`MINSPEC_DRAIN_CONCURRENCY` yourself. You asked for the weekly tokens to be burned and
for the machine to be busy unless tokens are the limit; at concurrency 1 the host sat
near idle with quota open. The cost: two queued issues that touch the same file can open
competing pull requests.

## Context

`scripts/drain-inbox.sh` defaults to concurrency 1 and carries a caveat (around lines
407-411): two queued issues touching the same file still produce competing pull requests,
because each agent branches from `origin/main` and cannot see an unmerged sibling, so
"keep the default at 1 until same-file serialisation exists, and de-duplicate the queue
first". That caveat was written for the session-start drain.

The host drain service passed no concurrency, so it inherited 1. Measured 2026-10-26: the
service drain logged "dispatching 30 agent-ready issue(s) (concurrency=1)" with load about
1 on 12 cores and quota open. The founder's standing instruction (quoted in
`triggered_by`) is to spend the week's tokens and keep the CPU busy unless tokens are the
throttle.

Prior practice, stated precisely: the keeper briefs `drain-keeper-1015b` to
`drain-keeper-1015d` (2026-10-15) started the drain with `MINSPEC_DRAIN_CONCURRENCY=8`.
The live drain observed on 2026-10-23 had no override and ran serial
(`specs/minspec/SPEC-230-quota-scaled-drain-concurrency/requirements.md:50`). So 8 is a
value earlier keepers chose, not the value the drain was running at when this was decided.

## Decision

1. `drain-service.sh` exports `MINSPEC_DRAIN_CONCURRENCY` with a default of 8, only when
   it is unset. An explicit value (including 1) passes through unchanged.
2. `drain-inbox.sh` is untouched. Its own default stays 1, so session-start drains and any
   direct invocation keep the caveat's conservative behaviour.
3. The drain's existing safety (per-item flock, claim-unique worktrees, the
   pull-request-per-head compare-and-swap, the sequential merge gate, from DR-067) is what
   makes parallel dispatch safe. The quota cap still throttles whatever the concurrency.

## Accepted cost

Same-file collisions: two queued issues editing one file may each open a pull request.
The racer that loses stands down cleanly or leaves a competing pull request for review; it
corrupts nothing. This is true serially as well, only slower to hit. The mitigation is
the pull-request review and merge gates, not the concurrency number.

## Rejected alternatives (DR-086 section 4)

- **Raise `drain-inbox.sh`'s own default to 8.** Rejected: the caveat there was written
  for session-start drains, which the founder's instruction did not address.
- **Keep 1 until same-file serialisation exists.** Rejected: it leaves the paid week
  unspent, against the founder's three quoted instructions.
- **Wait for quota-scaled concurrency (SPEC-230).** Rejected as a blocker: it is the
  long-term replacement and has not shipped. This default is the stopgap and is
  superseded by it when it does.

## Consequences

- Throughput of the service drain rises up to 8-fold when quota is open.
- More concurrent same-file races; review load rises with them.
- When SPEC-230 ships, this default is replaced by the quota-scaled value.
