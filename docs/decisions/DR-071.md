# DR-071: Standing consent for a fixed, same-origin, repeating network action

> **Born `proposed` per DR-029** — acceptance was a separate human act
> (*MinSpec: Accept ADR*); this record's live status is its frontmatter `status:`
> field, not this note. The shipped default remains `prompt` (per-action consent):
> accepting this DR authorises the standing-consent *rule*, and turns it on for
> nobody — a user still has to choose `always` themselves.

## In plain terms — what this changes for you

*Plain-language lead summary (SPEC-049 FR-2 shape: context → decision → product impact).
The technical Rationale / Alternatives / Costly-to-Refactor sections below stay dense on
purpose; this section is the one a product owner should be able to decide from.*

**What happens today.** You press `Alt+A` to approve a spec. MinSpec saves the approval,
then asks *"Push it so the sign-off isn't stranded?"* — **every single time**. You click
Push. If you don't, that approval exists only on your laptop, and the record can strand
(the defect that produced three duplicate recovery PRs in one day: [#996], [#1017], [#1018]).

**Why it asks.** Pushing touches the network, and the standing rule ([DR-050](DR-050.md))
was: never touch the network without asking — *each time*.

**What this DR decides.** For one narrow job — sending **your** approval to **your own**
repo, immediately after **you** pressed the key — a setting you deliberately switched on
counts as your permission. So you can choose "always" once, and stop being asked.

**The five guard-rails**, so this cannot become a loophole for anything else:

1. **Out of the box it still asks.** Silence is something you choose; never a default.
2. **The setting says what it does**, at the moment you choose it — not in a changelog.
3. **Your own repo only** — never a destination that came out of a file, a diff, or a PR.
4. **Only right after you press the key** — never on a timer, at startup, or in the background.
5. **If it fails, you are told.** A silent failure would make the permission meaningless.

Plus: "always" belongs in **your own** settings, not the repo's shared settings file — so
you cannot switch it on for teammates by accident.

**If you accept this:** nothing changes immediately. Approvals keep asking. What it unlocks
is the *option* — [SPEC-050](../../specs/minspec/SPEC-050-silent-approval-pr/requirements.md)
FR-8 then offers that choice inside the prompt you already see, once, and afterwards
approving is a single keystroke with no follow-up questions.

**If you reject this:** approvals keep asking forever, one click each, and SPEC-050's FR-8
is dropped (its FR-1–FR-7 — opening the PR for you — are unaffected either way).

**What it does not do:** it does not authorise telemetry, update checks, model calls, or any
background traffic. Guard-rails 3 and 4 exist precisely to stop it being stretched that far.

## Context

### The invariant, and the rule that implements it

Constitution invariant #1: *core functionality works offline — no network calls without
explicit user consent.* **DR-050** implements it, and its rule #2 is explicit:

> **Explicit per-action consent.** Every action that will cause a network call [names it
> and asks].

DR-050 was minted for `gh`/CLI shelling, where the action's *target* varies per
invocation — an arbitrary URL, an arbitrary API call, an arbitrary repo. Per-action
consent is exactly right there: the user cannot pre-approve a target they have not seen.

### The new case does not fit that shape

**#1022**: approve-on-commit commits the approval doc + record and **never pushes**.
Approvals are made on `main`; `main` is protected (PR + CI required), so even a manual
`git push` is *rejected*. There is no path from Alt+A to the remote at all, and the
approval toast says `· committed`, which reads as done for a record that exists on
exactly one machine. On 2026-07-27 this produced **three duplicate recovery PRs for the
same two records** (#996, #1017, #1018), two of which were closed as duplicates.

The fix has to push. That makes it the **second** push lane in the product (the first is
SPEC-039's docs-lane), and raises the question the Architect flagged on #1023: is an
`always` setting — standing, not per-action — still "explicit user consent"?

### Why per-action consent is the wrong instrument *here*

A maintainer approves specs and accepts DRs **dozens of times a day**. A modal per
approval produces one of two outcomes, both bad:

1. **Consent fatigue** — the prompt is clicked through without reading, which is not
   consent in any meaningful sense; it is a habit. The prompt then provides the
   *appearance* of a control while providing none.
2. **The user turns it off** — and every approval strands again, which is the exact
   defect this is meant to fix. A safety control that reliably gets disabled has
   negative value: it costs friction and delivers nothing.

The action being consented to is also *not* variable. It is the **same fixed action every
time**: push a commit the user just deliberately created, to **the repository's own
`origin`**, which they already push to by hand. There is no target for the user to
inspect per-action, because the target never changes.

## Decision

**A named, explicitly-set configuration option is valid "explicit user consent" under
invariant #1 — for a network action that is fixed, same-origin, and repeating — provided
all five conditions hold.** Where any condition fails, DR-050's per-action rule stands
unchanged.

1. **Per-action consent is the DEFAULT.** The shipped default must be the prompting mode.
   Standing consent is only ever reached by a user deliberately changing a setting.
   (`minspec.pushOnApprove` ships as `prompt`.)
2. **The setting NAMES the network action** in its description, at the point of choosing —
   not in a changelog or a doc page. The user must be consenting to a described thing.
3. **Same-origin only.** The destination is the repository's own configured remote. This
   rule does NOT extend to user-supplied or diff-supplied destinations, which remain
   per-action under DR-050. A standing consent cannot be transitive to a target the user
   has not seen.
4. **Fixed shape, user-initiated.** The action must be the direct, predictable consequence
   of a deliberate user gesture (here: pressing Alt+A). Standing consent never authorises
   background or ambient traffic — nothing on a timer, on startup, or on file-watch.
5. **Failure is surfaced, never swallowed.** If the action fails, the user is told the
   state is not what they asked for (`· push failed — still local only`). A silent failure
   would make the consent meaningless because the user could not audit the outcome.

**Corollary — do not commit standing consent into shared workspace settings.** Standing
consent is a *personal* decision, so `.vscode/settings.json` in a shared repo keeps
`prompt`; `always` belongs in a user's own settings. (Raised by the ai-review Security
voter on #1023 and adopted.)

**Corollary — the single-push-lane claim is retired.** `invariants.test.ts` asserted in a
comment that SPEC-039's docs-lane was *"the ONLY command that pushes"*. With approve-push
that is false, and the comment is reconciled to name **two** lanes. Both are Tier-1
delegations to the user's own `git` (DR-004): MinSpec opens no socket itself.

## Consequences

- The `child_process` allowlist gains its **first entry that genuinely makes a network
  call**. Its justification says so plainly rather than reusing the "local git only"
  wording its neighbours carry — it is allowlisted on the *consent* clause, not on a
  Tier-0 claim. An allowlist entry that misdescribes itself is how a network lane sneaks
  in unnoticed later.
- **Offline still works.** With the default, or with `never`, MinSpec makes no network
  call at all; the approval is committed locally exactly as before.
- **Scope creep risk is real, and condition 3 is the guard.** "A setting is consent" could
  be stretched to justify telemetry, update checks, or model calls. It cannot: those are
  ambient (fails #4), or not same-origin (fails #3), or not the direct consequence of a
  user gesture (fails #4). Any future use of this DR must state which of the five
  conditions it satisfies.
- The audit story is unchanged: the push is the user's own `git` against their own remote,
  visible in reflog and in the PR list.

## Alternatives considered

- **Keep per-action consent for everything (status quo).** Rejected: it produces consent
  fatigue or gets turned off, and either way the records keep stranding — the defect is
  already recurring, with three duplicate PRs in one day as evidence.
- **Push silently with no setting at all.** Rejected outright: that is a network call
  without consent, a direct invariant #1 violation, regardless of how convenient.
- **Prompt once per session rather than per action.** Rejected: a session is not a unit
  the user reasons about, the boundary is invisible, and it is strictly harder to audit
  than a setting they can read at any time.
- **Open a PR via `gh` instead of pushing a branch.** Deferred, not rejected — it needs
  `gh` auth and is a larger network surface. The branch push already removes the
  stranding, and the PR is one click from the offered link.
- **Let the drain sweep local approvals.** Rejected: it does not work across machines,
  and it moves an approval-authorship act to an automated agent, which cuts against the
  no-self-approval rule.

## Costly to Refactor

Moderate. The five conditions are a *rule*, not code — but once a second and third feature
cite this DR to justify standing consent, tightening it means revisiting each. That is
precisely why condition 3 (same-origin) and condition 4 (no ambient traffic) are written
as hard limits rather than guidance: they are the two that would otherwise erode first.
