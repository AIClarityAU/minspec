# DR-115: The App secrets are optional; the scaffolded review falls back to `GITHUB_TOKEN`

Triggered by: #2982

> **Born `proposed` per DR-029.** Acceptance is a separate act. Nothing ships with this
> record; the behaviour is specified in SPEC-268 and built only after that spec is approved.
> **Amends [DR-054](DR-054.md)** (shared reviewer App + OIDC broker): DR-054's long-term route
> is unchanged; this adds a no-App fallback for repos that have not set the App up.

## In plain terms - what this changes for you

A new repo set up by MinSpec gets AI review with just the Claude login secret. Without the
App secrets, review comments and labels show as `github-actions[bot]`, and the merge gate
still goes green on a real pass. Repos that have the App secrets (this one) behave exactly as
before. The cost: in a repo without the App, forging a review pass is easier.

## Context

`ai-review.yml` refuses to run unless `CLAUDE_CODE_OAUTH_TOKEN`, `MINSPEC_APP_ID` and
`MINSPEC_APP_PRIVATE_KEY` are all set (`.github/workflows/ai-review.yml:204-215`), and the
setup probe mirrors that (`packages/minspec/src/lib/ruleset-advisor.ts:734-738`). DR-054
intended consumer repos not to hold the App key (the shared broker, SPEC-034, is still in
planning). Until the broker exists, every new repo needs the two App secrets set by hand, and
the founder could not get review on a new work-PC repo without them.

## Decision

1. Only `CLAUDE_CODE_OAUTH_TOKEN` gates the scaffolded review. With both App secrets present,
   the App identity is used exactly as today. Otherwise the workflows write with
   `GITHUB_TOKEN`; a half-set App (one secret only) is reported as a warning.
2. `ready-to-merge` trusts `github-actions[bot]` as a reviewer identity **only** in a repo
   where the App secrets are absent, never on a fork PR, and never when the operator has set
   `AI_REVIEW_BOT_LOGINS` explicitly.
3. In that no-App mode, a pull request touching machinery paths (`.github/`, `scripts/`)
   cannot go green through a `github-actions`-attributed pass (parity with the App mode,
   where a machinery PR never gets a pass witness).
4. Because writes made with `GITHUB_TOKEN` start no new workflow run, `ready-to-merge` gains a
   trigger that re-evaluates it when an `ai-review` run completes (mechanism chosen in
   SPEC-268 D1; `workflow_run` recommended). It stays the single writer of the status.

## Accepted costs (founder, queue item av1)

- **Identity.** Without the App, comments, labels, check-runs and statuses post as
  `github-actions[bot]`, not `minspec-sdd[bot]`.
- **Trigger.** Label changes made with `GITHUB_TOKEN` do not fire `labeled`, so the merge gate
  needs the new completion trigger; SPEC-268 FR7/AC5 require it to be tested, never left
  silently not firing.
- **Forgery.** In a no-App repo, any workflow already on the default branch that holds a
  write-scoped `GITHUB_TOKEN` posts as the same identity as the reviewer, so a pass can be
  forged by such a workflow. Decision 3 closes the PR-adds-a-workflow route; the residual (an
  existing default-branch workflow, or a maintainer who edits one through a reviewed machinery
  PR) is accepted for a private solo repo. Repos that need the stronger guarantee set the App
  secrets, or adopt the broker when SPEC-034 ships.

## Alternatives considered

- **Keep the App secrets required** until the broker ships: rejected by the founder (blocks
  new repos now; broker is still in planning).
- **Ship the App private key in the scaffold:** rejected - DR-054 forbids shipping it into
  customer repos (`DR-054.md:122`), and `no-app-private-key-shipped.test.ts` guards it.
- **Always allowlist `github-actions[bot]`:** rejected - weakens the forge defence in repos
  that do have the App (`.github/scripts/ai-review-guard.js:1695-1700`).
- **Explicit mode variable instead of secret presence:** rejected - re-adds a hand-set step.

## Reversibility

Reverting is a template change plus a scaffold refresh in each adopting repo; repos that ran
in no-App mode keep `github-actions[bot]`-attributed history. More than a day to unwind across
adopters, hence this record.
