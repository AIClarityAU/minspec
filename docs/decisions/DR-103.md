## In plain terms - what this changes for you

You offered to give agents the Marketplace token so the listing stays current. This
record recommends you do not hand it over, and proposes a way to get the same result.

Three facts decide it:

- **The token is not "publish MinSpec". It is you.** It works on every extension your
  account publishes, it can create new ones, and it can remove the MinSpec listing for
  good, after which the name can never be used again.
- **Microsoft switches that kind of token off on 1 December 2026.** Anything built
  around it lasts eight weeks, and so does the command you paste today.
- **Nothing an agent needs requires reading it.** Agents need a way to cause a
  release. They do not need the credential.

What is proposed: a release workflow on GitHub that signs in to the Marketplace with
nothing stored anywhere. At most once a day it publishes whatever is on `main` to the
**pre-release channel**, which people receive only if they chose it or run the Insiders
build of VS Code. Releasing to **everyone** stays yours: one approval in GitHub, when
you choose, of a build that has already been out on the pre-release channel. You stop
pasting commands.

What it costs:

- Code no person has read reaches whoever follows the pre-release channel, on the
  strength of the AI review alone.
- Today that review can be bypassed by the agents it is meant to check (see "Who can
  put a change on `main`"). So the automatic half stays switched off until that is
  closed (#2589, the reviewer identity).
- There is one-time setup only you can do: an identity in Azure, two environments in
  the repository's settings, and one workflow file to push.
- Building it is Phase 2 work that displaces Phase 1 work, which the constitution
  forbids unless a record like this one allows it.

Whatever you decide, two things to do and one that has been checked. All three are in
#2590 (the Marketplace sign-in):

1. **Revoke the Marketplace token that predates 2026-09-11.** The host register still
   lists it as readable from the container that ran agent sessions for six months, with
   revoking it an open item for a person (`/etc/nixos/docs/decisions/DR-079.md:270-276`;
   the same record's section "The bus, measured", `:132-135`, says the keyring returned
   it). Whether it has been revoked since is not known from here, and the listing is
   now public.
2. **Checked: the agent container holds no saved Marketplace token today.** Measured by
   the chief-of-staff session on 2026-10-07 at about 03:31 UTC, inside the container,
   from file names and variable names only, never contents. It found no saved-token file
   (`~/.vsce`, `~/.config/vsce`, `~/.ovsx`, and none under `/root` or `~/code`), no
   environment variable named like a publish token, no mount of the host's home, and no
   keyring socket, so the host keyring cannot be reached from there. By that session's
   account, the steps you were given for 0.1.27 said "In a terminal on your machine",
   and no publish ran through the queue runner. Not checked: the contents of any file,
   the host itself, and whether the older token in point 1 has been revoked. The
   session that wrote this record did not repeat the check.
3. **Pick the sign-in that replaces the token before 1 December**, or releases stop.

## 1. The asset: what the credential is and what it can do

From Microsoft's documentation, read 2026-10-06 UTC. Links are under Sources.

| Question | What Microsoft says |
|---|---|
| What does `vsce publish` need? | The Marketplace runs on Azure DevOps. `vsce` takes a Personal Access Token, or a Microsoft Entra ID token (`--azure-credential`, vsce 2.26.1 or later). [S1] |
| Which token? | One created with Organization "All accessible organizations" and scope Marketplace "Manage". Choosing one organization is listed as a cause of 401 and 403 errors. [S1] That is a **global** token. |
| Whose is it? | "PATs are always associated with the user who created them." [S3] It is not tied to a publisher or an extension, and the token form has no field for either. [S1] |
| Can it be limited to one extension? | No field for it. With an Entra identity the unit is the publisher: the identity is added as a publisher member with a role, and the page says to assign Contributor. [S1] Contributor "can publish and manage extensions". Creator "can publish extensions, but can't view or manage extensions published by other users". [S5] No role is per extension. |
| Can it create a new listing? | Yes. When the extension named in the packaged file does not exist, `vsce` creates it (`src/publish.ts`, lines 272 to 278). The publisher and the name come from the file. |
| Can it unpublish? | `vsce unpublish` "Removes an extension from the marketplace", takes the same token or `--azure-credential`, and has `--force` to skip the confirmation (`src/main.ts`, lines 345 to 350, in microsoft/vscode-vsce). Removal is irreversible, and "its extension name is permanently reserved and cannot be reused, even by the original publisher". [S1] |
| Maximum lifetime? | "All existing global PATs stop working on December 1, 2026." [S3] The blog adds that new ones can still be created until then. [S2] |
| Is its use logged? | "Because token access isn't logged, don't use the audit log to classify a PAT as active or stale." [S3] |
| Sign-in with no stored secret? | Yes, by the route Microsoft recommends: Microsoft Entra ID with "workload identity federation and managed identities", which "eliminates long-lived secrets such as Personal Access Tokens (PATs)". The steps on the page are for **Azure Pipelines**. [S1] |
| From GitHub Actions? | Two routes, neither documented by Microsoft for the Marketplace today. (1) The same Entra identity federated to a GitHub Actions environment, then `vsce publish --azure-credential`. `vsce` accepts a signed-in Azure CLI (`src/auth.ts`, lines 3 to 11). A community guide describes it and names GitHub's own `vscode-codeql` workflow as an example. [S7] (2) Trusted publishing, `vsce publish --oidc`, which exchanges a GitHub token for a Marketplace session token "valid for up to 15 minutes". [S6] It is in vsce 4.0.0, but a vsce maintainer wrote on 2026-10-05: "`--oidc` is not yet fully supported by the marketplace backend. It will be soon." [S8] |
| With no token at all? | A packaged file can be uploaded in the browser on the publisher management page. [S1] |

**The pre-release channel.** [S1], "Pre-release extensions":

- It is a flag on a published version: `vsce publish --pre-release`. It is not the
  manifest's `preview` field, which only adds a badge.
- Users get it by choosing "Install Pre-Release Version". [S4] VS Code builds that are
  not the stable product, Insiders among them, prefer the pre-release version by
  default. That is read from VS Code's source, not its documentation
  (`abstractExtensionManagementService.ts`, line 71:
  `preferPreReleases = this.productService.quality !== 'stable'`).
- Versions are `major.minor.patch` only, and a pre-release and a release may not share
  one. "VS Code will automatically update extensions to the highest version available,
  so even if a user opted-into a pre-release version and there is an extension release
  with a higher version, the user will be updated to the released version." Microsoft
  recommends "`major.EVEN_NUMBER.patch` for release versions and
  `major.ODD_NUMBER.patch` for pre-release versions".
- It needs `engines.vscode` of 1.63.0 or later. MinSpec declares `^1.90.0`
  (`packages/minspec/package.json:24-26`).

**How fast a published version reaches a machine.** [S4] The editor checks for
extension updates and installs them by itself. Since VS Code 1.123 an automatic update
waits first, and since 1.125 the wait is a setting: "The default value is `12` hours."
A new install, an older editor, and anyone who presses Update get the new version at
once. The same page says an extension has the same permissions as the editor itself.

**Not confirmed** (each is marked unverified where it is used):

1. A general maximum lifetime for a token. The current page gives none. The issue in
   Microsoft's Marketplace tracker, opened by a member of the Microsoft organisation,
   says "max 1 year". [S7] The December date caps it either way.
2. Whether a token with the narrower Marketplace "Publish" scope is enough for `vsce`.
   Azure DevOps documents that scope for its own extensions. [S9] The VS Code page says
   Manage.
3. The federated route from GitHub Actions end to end. It was not tried, and nobody
   should try it with a real identity as part of writing a record.
4. When trusted publishing will work. "Soon" was also the answer in August. [S8]
5. Whether a Creator identity can update an extension another account published.
6. Whether the Marketplace refuses a version lower than the newest. `vsce` checks only
   for an identical version (`src/publish.ts`, lines 240 to 251).
7. Whether the public listing page shows the README of the newest version when that
   version is a pre-release.
8. What kind of Microsoft account owns the `aiclarity` publisher, and whether an Azure
   subscription exists.

## 2. Threat model

### What a bad publish costs

A published version runs with the user's permissions on every machine that takes it.
New installs take it at once. Copies that update by themselves take it after the
editor's delay, 12 hours by default on current VS Code and none on older editors,
which MinSpec still supports. Nothing recalls an installed copy. The newest version
cannot be deleted. The remedy is a higher fixed version, or unpublishing the whole
extension, which stops downloads. [S1]

The gallery counts 2 installs today. The preview-publish record says why it was
published: the founder's Windows work PC. So the machine a bad version is most sure to
reach is, by that record's own account, the one he works on for someone else.

### Who can put a change on `main` with no human

This is the path every option depends on, so it is stated exactly. Read on
`origin/main` `db4b2cd6`; live values measured 2026-10-06 UTC.

1. The ruleset on `main` has three rules: required status checks (strict), no force
   push, no deletion. The required checks are `lint`, `test`, `build`,
   `MinSpec SDD validation`, `ai-review` pinned to integration 4212099, and
   `ready-to-merge` pinned to integration 15368, which is GitHub Actions. There is no
   pull-request or human-approval rule.
2. `ready-to-merge` goes green when `ai-review:pass` was last applied by a login on an
   allowlist after the head commit (`.github/scripts/ai-review-guard.js:828-864`), and
   the head commit carries an `ai-review/pass` status or an `ai-review` check-run from
   that same allowlist (`:874-913`, `:944-995`). The allowlist defaults to
   `minspec-sdd[bot]` (`.github/workflows/ready-to-merge.yml:161`).
3. The honest route to those signals is the review workflow: up to four voters
   (reviewer, security, architect, skeptic; `.github/workflows/ai-review.yml:409-437`)
   with no tools, reading the diff as untrusted data, posting as that App with a key
   held in repository secrets (`:189-195`). A change that touches machinery
   (`.github/`, `scripts/`, `.githooks/` and two generator files,
   `packages/minspec/src/lib/machinery-paths.ts:52-78`) is given no passing witness
   (`.github/workflows/ai-review.yml:42-50`), so `ready-to-merge` stays red and only the
   founder's `--admin` merge lands it.
4. For everything else, dispatch arms GitHub's own auto-merge
   (`scripts/dispatch-issue.sh:1163`), which is switched on
   (`.minspec/config.json:54-58`). It withholds on the docs corpus, `.minspec/`,
   machinery and `sites/**` (`scripts/dispatch-issue.sh:135`, `:206-208`). It does not
   withhold on `packages/minspec/src/**`, `packages/minspec/package.json`,
   `package-lock.json`, `packages/minspec/README.md`, `CHANGELOG.md` or
   `packages/minspec/media/**`.
5. This route is in daily use. Of the last 200 merged pull requests (2026-09-09 to
   2026-10-06), 48 were merged by an App, and 21 of those changed
   `packages/minspec/src/`. The other 152 show the founder's account as the merger.
   That does not establish a keystroke each, because host-side automation has pushed
   with his token (`/etc/nixos/docs/decisions/DR-079.md:311-314`).

**The weak point.** The identity the gate trusts is the identity every agent session
holds. A session comment on #2410 and the review verdicts on #2566 were both posted
through App 4212099, and the `ai-review` check-run on #2566's head reports the same
App. The host register records that any process in the agent container can obtain a
token for it (`/etc/nixos/docs/decisions/DR-079.md:206-209`) and that the token carries
`checks`, `statuses`, `issues`, `contents`, `pull_requests` and `actions` write
(`/etc/nixos/docs/decisions/DR-085.md:114-115`, verified there 2026-09-26, not measured
again here). So the label, the head witness and the merge call are all things a
session's own token may write. For a machinery change the hold is only the absence of
a witness, and the gate reads the newest one.

**This was not exercised.** It is read from the code and the live ruleset. Proving it
would mean writing a false review verdict. It is filed as #2589.

What it does not reach: workflow files. The App's `workflows` permission was removed on
2026-09-11 (`/etc/nixos/docs/decisions/DR-079.md:265-267`), so GitHub refuses a push
from it that changes `.github/workflows/**`.

So "every pull request needs CI and a four-voter review, and machinery needs the
founder" is true of sessions that follow the rules. Against a session led astray it is
a rule the model is trusted to keep, which constitution principle 8 says not to rely
on (`.minspec/constitution.md:22`).

Two more, found while tracing the above.

- **The release path's own steps.** `npm run package` reads its steps from

  trusts that script block for its gate can be switched off by an ordinary pull
  request. Under c and d the publishing step must run nothing from the repository
  (#2591).
- **Approval as a reflex.** An agent can start the stable job as often as it likes, and
  each start asks the founder to approve. He has said his reading is not a check. So
  the approval must not be sold as one. It is a brake: only he can release to everyone,
  and only what has already been out on the pre-release channel.

## 3. Options

For each: where the credential lives, who can trigger a publish, what a session led
astray could achieve, what the founder still does, what has to be built and who must
push it, and what it does to the other records and the host boundary.

### a. As now: the founder pastes one command per release

- **Credential:** wherever `vsce` saved it on the machine he ran it on. That is not
  the agent container, by the check of 2026-10-07 (file names and variable names only;
  see "In plain terms"). After 2026-12-01 it does not work, so the paste becomes a
  browser upload or a different sign-in.
- **Trigger:** the founder.
- **A session led astray:** can put code on `main` and write the command, and for
  0.1.27 a session built the file. It cannot publish at a time of its choosing or
  remove the listing, unless the token is readable (source 2).
- **The founder does:** one paste per release, of a command that by his own account
  he does not review enough for it to mean anything.
- **To build:** nothing now. The sign-in before December (#2590).
- **Other records:** none change. The host boundary holds only while the token is not
  in the container, which is what the check of 2026-10-07 found.
- **For:** nothing to build, and it is what the accepted record says. **Against:** the
  act is not a check, releases wait for him so the listing goes stale, and it ends in
  eight weeks.

### b. What he offered: the token where agents can read it

- **Credential:** a file or variable in the agent container. Every session, every
  install script and every test run there can read it, and it can leave the machine.
- **Trigger:** any session, at any time, with any file, any version and any extension
  name under any publisher his account belongs to.
- **A session led astray:** everything. It can publish a file that was never on `main`,
  create new listings, and remove `aiclarity.minspec` for good.
- **The founder does:** nothing per release. Rotation, if he learns of a leak. The
  token's use is not logged.
- **To build:** nothing.
- **Other records:** it reverses the preview-publish record's section 4 outright, and
  DR-086's stop class 1. The host register's gate would not notice. That gate is about
  GitHub credentials (`/etc/nixos/tests/agent-container-no-user-credential.sh:1-4`); it
  scans four named files and two environment variables for GitHub-shaped tokens
  (`:600-631`) and says itself what a green does not cover (`:1095-1109`). The token
  would not be the first founder credential in the container. The host record lists the
  Anthropic sign-in and the `.env` files under `~/code` as still there
  (`/etc/nixos/docs/decisions/DR-079.md:186-202`). It would be the first put there on
  purpose since the split. The same record names the Marketplace publisher token of
  that time among those that were readable for six months and still need revoking
  (`:270-276`). Whether the token offered now is that one, and whether that one has
  been revoked since, is not known.
- **For:** the fastest way to a current listing, with nothing to build, and with 2
  installs few machines are exposed today. **Against:** what is at risk is not the
  number of installs. It is the listing, the name and the publisher, none of which can
  be got back, and the machine it was published for is his work PC. It also lasts
  eight weeks.

### c. A host-side publish broker

The token stays on the host. Agents ask a socket for a release, the way they ask for a
GitHub token today. The broker reads nothing from the caller, which is the whole
control in the existing broker (`/etc/nixos/docs/decisions/DR-085.md:113`). It resolves
`main` itself, builds, runs the supply-chain check with catalogs and fails closed,
checks the version, publishes, and tells the founder.

- **Credential:** on the host only. After December that means an Entra service
  principal's certificate or secret on the host, which is a new long-lived secret, or
  the founder's own interactive sign-in.
- **Trigger:** any session can ask. It cannot choose the commit, the version, the
  channel or the extension.
- **A session led astray:** can cause a release of whatever is on `main`, and can put
  things on `main` (source 3). It cannot read the token, publish another file or remove
  anything.
- **The founder does:** writes or accepts the host configuration, keeps the machine on,
  rotates the credential.
- **To build:** the broker, a build sandbox and the notice, all in the host
  configuration, which only he can apply.
- **Other records:** "no agent holds a Marketplace token" stays true. "Publishing stays
  a human act" does not, unless the broker waits for him. The host boundary keeps the
  credential out of the container but gains a new duty: building agent-written code.
- **For:** it matches the pattern the host already uses, depends on no cloud service,
  and can notify on the desktop. **Against:** the build is the problem. `npm ci` and
  the build run code from `main` as the founder on the host, where the host record
  says a hostile process reaches his SSH key, the unlocked wallet and the docker socket
  with no escape step (`/etc/nixos/docs/decisions/DR-079.md:52-54`). So it needs a
  sandbox, or it must publish a file CI built, and that needs a workflow change anyway.
  It is the largest build of the five.

### d. A release workflow on GitHub in a protected environment

A workflow builds from `main` on GitHub's runners and publishes from a job that
belongs to a protected environment.

- **Credential:** none stored, if the sign-in is federated: GitHub issues a short-lived
  token to a job in that environment of this repository, and the Marketplace accepts it
  through an Entra identity today or through trusted publishing when it exists. The
  alternative, the token as an environment secret, works until December and is not
  recommended.
- **Trigger:** whatever the workflow's `on:` names. A manual start needs `actions:
  write`, which the bot holds, so an agent can start it.
- **What an agent can do:** start a run, cancel a run, switch a disabled workflow back
  on (all `actions: write`), and change what is on `main` except workflow files
  (source 3). [S10]
- **What an agent cannot do:** change the workflow file (no `workflows` permission);
  change an environment's reviewers, branch rule or secrets (that needs Administration
  or Environments); approve a waiting job (that needs Deployments, and required
  reviewers are "users or teams"). [S10] [S11] It cannot get the sign-in from a job
  outside the environment either. All of this rests on the bot's permission list as the
  host register recorded it on 2026-09-26, and on #1810 (the App was granted
  Administration write on 2026-09-05), which is still open.
- **The founder does:** the one-time setup, and an approval wherever the environment
  requires one.
- **To build:** the workflow (he must push it), the environments (repository settings,
  his), the identity and its publisher membership (Azure and the Marketplace, his).
- **Other records:** the same sentences as c. The host boundary is untouched: no
  credential sits on any machine of his.
- **For:** the build happens on a disposable runner and not on his host, there is no
  secret to leak, GitHub enforces the controls, and the bot lacks the permissions to
  change them. It is also the direction Microsoft is pushing every publisher in. [S1]
  **Against:** it needs an Azure subscription and setup only he can do, the GitHub
  Actions form of the federated route is not documented by Microsoft, and the
  documented publisher role covers every extension under the publisher, removal
  included.

### e. A split by channel

Not a mechanism but a policy on top of c or d: automatic to the pre-release channel,
the founder's act for the stable one.

- **Credential, build, records:** as the mechanism under it.
- **Trigger:** automatic for pre-release. For stable, anyone may ask and only the
  founder can approve.
- **A session led astray:** reaches people on the pre-release channel. It does not
  reach everyone else without him.
- **The founder does:** one approval per stable release, and chooses which channel his
  work PC follows.
- **For:** it puts the one human act where an agent cannot perform it and where it is
  rare enough not to become a reflex. If the work PC follows the pre-release channel,
  it also gives him what he asked for with no act at all. **Against:** two version
  lines to keep apart, the pre-release audience includes anyone installing on VS Code
  Insiders, and with almost no pre-release users the "already been out" period shows
  whether a build breaks, not whether it is hostile.

### Alternatives rejected

- **Automatic to everyone after a waiting period, unless the founder stops it.** It
  needs no act from him. Rejected because a veto nobody exercises is no control, and by
  his own account he does not review such things closely.
- **The token as a repository secret with a workflow, and no environment.** Any job in
  the repository could then use it, and it lasts eight weeks.
- **Add `packages/minspec/package.json` to the machinery set**, so that every version
  bump is the founder's merge and the merge is the release. It makes every dependency
  change his too, and a merge is not a control an agent cannot reach (source 3).

## Decision

**(rec) Options d and e together**, behind the preconditions in the next section: a
release workflow on GitHub that signs in with no stored credential, publishes the tip
of `main` to the pre-release channel by itself, and publishes to everyone only when
the founder approves the job. Its main cost: everything on the pre-release channel is
code no person read, resting on the AI review being right, and none of it can be
switched on until the review can no longer be bypassed by the agents it checks, the
supply-chain check fails closed, and the founder has done account setup only he can
do. Until then releases stay as they are, and that way stops working on 2026-12-01.

What accepting this record accepts:

1. **No publishing credential is stored where an agent can read it, and none is given
   to an agent.** The offer of the token is declined.
2. **The sign-in is federated**: an Entra identity bound to this repository's release
   environments, or Marketplace trusted publishing if it works first. Which one, and
   the fallback if neither is ready by December, is #2590.
3. **One workflow, two environments.** Both accept `main` only. The job that can sign
   in runs nothing from the repository: it takes the packaged file from a build job
   that holds no credential, checks it, and publishes it (#2591).
4. **Pre-release is automatic**, at most once a day, with a wait before each publish so
   it can be cancelled.
5. **Stable needs the founder's approval** in GitHub, as the environment's only
   required reviewer. What he approves is a commit that has already been published to
   the pre-release channel. The approval is a brake and not a review, and the job shows
   him the commit, the version, what merged since the last stable release and how long
   it has been out.
6. **The stop list changes** as section 5 states, and nowhere else.
7. **A standing exception to the phase order**, limited to the preconditions below and
   the release workflow. The preview-publish record's exception closed with the
   publish, so keeping the listing current needs its own.

Two choices inside it are the founder's, each with a recommendation and its cost.

- **Which channel the Windows work PC follows.** **(rec) Stable at first**, then
  pre-release once the automatic channel has run for a few weeks without a stop. Cost:
  fixes reach that machine only when he approves a stable release, which is the delay
  he asked to be rid of. The other choice puts unread, agent-merged code on his work
  PC about half a day after it merges.
- **When to build it.** **(rec) The sign-in now, the rest after the reviewer identity
  (#2589).** Cost: the listing stays as stale as it is today until both are done. Only
  the sign-in has a date. Everything else can also wait for Phase 1, at the cost that
  releases stay manual.

Three points where this is stricter than "automatic pre-release, human stable" taken
by itself:

- The review is not yet something an unattended publish can rest on. It can be bypassed
  by the identity it checks, so closing that is a precondition and not a refinement.
- The human act on stable is a brake. Calling it a review would recreate the reflex the
  founder has just described.
- There is no guarded credential at all. A broker that hides a token (option c) was
  weighed and set aside, because it moves the build of agent-written code onto the
  host.

## Costly to Refactor

1. **A published version.** It cannot be recalled from a machine that took it, its
   number cannot be used again, and the newest one cannot be deleted. Check: P2, P5 and
   P7 before the first automatic publish.
2. **The two version lines.** Once a stable 0.2.0 and a pre-release 0.3.x exist, the
   parity is set, and it can only be changed by moving forward. Check: #2592 decides it
   before anything is published under it.
3. **The reviewer identity** (#2589). A second App changes the ruleset, the review
   workflow and the default identity MinSpec scaffolds for adopters. Check: decide the
   adopter question in that issue, not here.
4. **Removing the listing.** Not something this record does, but the documented
   publisher role allows it. Check: the job that can sign in runs no repository code
   (P4).
5. **Low: the workflow and the environments.** Deleting them, and removing the identity
   from the publisher, returns to today within minutes.
6. **Low: the stop-list edit.** Another record can restore the wider wording.

## Consequences

- The founder stops pasting release commands. His remaining acts are the one-time
  setup, an approval per stable release, and reading a notice.
- The listing's pre-release channel is at most a day behind `main`. The stable channel
  is as current as he chooses.
- The AI review carries more than it did. It was the last reader of most code. It
  becomes the last reader of code that reaches users' machines with no human act, for
  everyone on the pre-release channel.
- An agent session gains one new ability: to ask for a release of `main`. It gains no
  credential.
- The command he pastes today stops working on 2026-12-01 whatever is decided here, so
  P3 has a date even if this record is rejected.
- Work on preconditions P1 to P9 may run ahead of Phase 1 work. That is the
  displacement the constitution forbids by default and this record would permit for
  these items only.
- If Microsoft ships trusted publishing first, the Azure identity is not needed and
  the publisher gains no member that can remove a listing. The rest is unchanged.
