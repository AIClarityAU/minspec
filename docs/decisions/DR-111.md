# The founder's editor approval is the merge keystroke for a PR that carries nothing else

## In plain terms - what this changes for you

When you approve a spec (or accept a record) in the editor, the editor opens a pull request
under your account. Today that pull request waits for you to press merge as well, so you approve
the same thing twice. With this decision, a check run from `main` reads that pull request and,
if it carries **only** your approval (the approval record plus the `status:`/`phases:` lines your
approval wrote, and not one other byte), the bot merges it once every required check is green.
Anything else, or any doubt, leaves it for you exactly as today. The risk you accepted: a bug in
the check could let another change ride along. The check fails closed and is mutation-tested to
keep that risk small.

## Context

The constitution's merge-gate conservation rule (DR-070 §4) says no unit of work ever reaches
`main` with zero human keystrokes. For agent-built work the keystroke is the founder's merge.
For an editor approval, the founder's keystroke already happened: Alt-A in the editor is the
explicit human act DR-012 defines approval to be, recorded under his identity (DR-056 refuses
an agent identity at record time). The pull request that carries it adds no new content for
him to judge, so asking for a merge keystroke as well counts the same act twice.

Before this decision, approval pull requests such as #2998 (SPEC-140 approval) sat at
`awaiting-approval` waiting for that second keystroke.

## Decision

1. **A pull request is merged by `minspec-sdd[bot]` with no further keystroke when, and only
   when, the approval-only check finds it eligible and every required status check is green.**
   The check is `scripts/alta-self-merge.ts`, with the judge in
   `scripts/lib/alta-approval-only.ts`; the workflow is `.github/workflows/alta-self-merge.yml`.
2. **Eligible means all of:** the PR is the founder's (author and every non-merge commit
   attributed to his account), from this repository, targets the default branch, is up to date
   with it, and carries `ai-review:pass` with no `hold:*`; its diff is approval records under
   `.minspec/approvals/` for approvable artifacts plus, in those artifacts only, the frontmatter
   `status:` line and `phases:` block, and nothing else; each record is read by the repo's own
   sidecar reader, attributed to the founder, not migrated, and its hash equals `specHash()` of
   the artifact on the head; and the artifact is otherwise byte-identical to the base.
3. **Fail closed.** Any error, unreadable input, empty diff or unknown file means "needs the
   founder". A failure is reported as a red workflow run, never as a pass (constitution
   invariant 2).
4. **The merge is bound to the judged head** (`sha=` on the merge API, squash). A push after
   the judgement makes GitHub refuse it. The bot never uses `--admin`; the ruleset still decides.
5. **The check runs from `main`.** It is triggered by `workflow_run` and `workflow_dispatch`,
   which run the default branch's workflow and scripts; the pull request is read as data and
   never executed. So no pull request can change the check that judges it, and a change to the
   check is itself machinery that needs the founder's merge.

**DR-070 §4 is kept, not relaxed.** Every unit of work still has one human keystroke: for an
approval pull request, that keystroke is the approval itself. This decision changes where the
keystroke is counted for one narrow shape of pull request; it does not remove one. It does not
cover acceptance of a constitution amendment (DR-070 §5.5 stays absolute), and it never merges
anything an agent authored.

## Cost

- **Accepted risk (the founder's, in36):** a defect in the check could let a non-approval change
  merge without his review. Bounded by: the check runs from `main` only; every guard has a test
  that a mutant removing it turns red; GitHub's ruleset still requires every required check;
  the merge is bound to the judged head.
- **Commit attribution is GitHub's email mapping**, which anyone with push access could spoof.
  The pull request author (attested by GitHub; no agent holds the founder's credential) and the
  content rules are the binding guards.
- **Residual base window:** GitHub's merge API pins the head, not the base. The check re-reads
  the base tip just before merging, and the ruleset's strict up-to-date requirement makes GitHub
  refuse a merge onto a base that moved. If strict mode is ever turned off, this window opens.
- One more workflow run per completed required-check workflow on a pull request.

## Rejected alternatives (DR-086 §4)

- **Arm native auto-merge at judgement time.** Rejected: auto-merge stays armed across later
  pushes by anyone with write access, so a commit pushed after arming would land judged only by
  the AI review. A direct merge with `sha=` is atomic against that.
- **A `pull_request` workflow.** Rejected: it would run the pull request's own copy of the
  check, which the pull request could edit.
- **Compare with `specHash()` alone.** Rejected: the canonical form collapses relative link URLs
  and trailing whitespace, so it cannot prove "no other byte".
- **Hard-code the allowed status transitions.** Rejected: they would drift from the editor's
  own; lifecycle fields are outside the approved hash by design, and the line-shape check bounds
  what they may contain.
- **Keep the second keystroke.** Rejected by the founder's in36 answer.
- **Admit decision-record acceptances that also edit `docs/decisions/INDEX.md` or the record's
  Status section.** Not taken here: outside the founder's "nothing else" rule. Put to him as #3001.

## Consequences

- Spec approvals (and frontmatter-only decision-record or epic acceptances) reach `main` with no
  second keystroke once green.
- A decision-record acceptance that edits INDEX.md or its Status section still needs the
  founder's merge until #3001 is decided.
- The founder's identity (login and approval email) is fixed in the workflow file, so changing
  who counts as the founder is a machinery change he must merge himself.
