# DR-098: The approval flow may create MinSpec's own missing `docs-lane` label

## In plain terms - what this changes for you

If you approve a spec in a repository that has MinSpec's docs-lane workflow but has never
had a `docs-lane` label, MinSpec now creates that label the first time an approval needs
it, and the approval's own message says so. Before, the approval stopped at an "Open PR"
button, and the pull request you then opened by hand could not auto-merge. Nothing else
about labels changes. MinSpec still never creates, edits or reads any other label, never
edits a `docs-lane` label that already exists, and does none of this unless you have
already agreed to push the approval. Setting `minspec.approvalPr` to `manual` turns it
off, together with the automatic pull request.

## Context

MinSpec scaffolds a workflow into adopters that auto-merges a docs-only pull request
carrying the `docs-lane` label, but never created the label, and `gh pr create` refuses to
open a pull request naming a label the repository lacks. So where the label was missing,
every approval fell to a manual `Open PR` step and a manual merge (#2243). Creating the
label is a new kind of forge write, and it narrows a statement MinSpec ships to every
adopter.

Line numbers below were read on 2026-10-01 on the head of #2259.

- **The lane keys on a label object.** SPEC-050 (silent approval PR) FR-2 opens the
  approval PR with `gh pr create ... --label docs-lane`, and the lane workflow runs only on
  a PR carrying that label (`.github/workflows/docs-lane.yml:36`).
- **gh refuses a PR that names a missing label, and creates nothing.** It resolves every
  `--label` to an id first and reports `could not add label: 'docs-lane' not found`
  (captured verbatim with gh 2.100.0 against voip-sms-inbox, recorded at
  `packages/minspec/src/lib/approval-pr.ts:359-365`).
- **Nothing provisioned the label.** MinSpec scaffolds the lane workflow into adopters
  (`packages/minspec/src/lib/template-registry.ts:2455-2456`, the `docs-lane-workflow`
  template), but not the label it gates on. This repository's label was created by hand
  when the lane shipped (#575): colour `0e8a16`, description "Docs-only PR — docs-lane
  workflow auto-merges once checks pass" (read from the forge on 2026-10-01). The
  ai-review workflow self-heals the labels it applies (`.github/workflows/ai-review.yml:215`);
  the lane workflow cannot, because it only runs on a PR that already has its label.
- **So adopters silently lost the feature.** In voip-sms-inbox every approval fell to
  SPEC-050 FR-5's manual `Open PR` surface, the hand-made PR carried no label, and each
  needed a manual merge (#2243). The founder's report: "i dont like that the voip project
  requires "Open PR" and manual merging, when other projects dont - pls fix that and ensure
  we get that shipped in the minspec vsix". The issue rules out a per-repository workaround.
- **A shipped statement stood in the way.** The `.minspec/labels.md` template (#1251, the
  label vocabulary) said "MinSpec never creates, edits, or reads a label on any forge",
  pinned by a T0 test. Its stated reason is constitution invariant 1: no network call
  without explicit consent.

#2259 implemented provisioning. The ai-review Architect blocked it for having no decision
record behind a new forge write that narrows that statement and reinterprets the consent
boundary, and for a capability SPEC-050's approved requirements do not state. This record
answers the first; the section on SPEC-050 below answers the second.

## Decision

**The approval flow may create MinSpec's own `docs-lane` label in the repository its
approval PR targets, when and only when all six conditions hold.** Where any fails,
nothing is created and the approval degrades to the FR-5 manual surface, which now names
the missing label.

1. **Only that label, only by create.** The argv is fixed: `gh label create docs-lane
   [--repo <slug>] --color 0e8a16 --description "..."` (`buildLaneLabelCreateArgs`,
   `approval-pr.ts:382`). The name is MinSpec's constant `DOCS_LANE_LABEL`, never a name
   taken from gh's error or from any input; a maintainer's own missing label stays theirs
   to create. No `--force`, so an existing label, including one a maintainer customised, is
   never edited. No `gh label list` or `view` either: the flow learns the label is missing
   only from gh's own refusal of the PR create (`missingLabelFrom`, `approval-pr.ts:368`).
2. **Only inside a consented push.** The create runs inside `openPullRequest`
   (`approval-pr.ts:830`), and only for a caller that opts in. The one caller that does is
   `openApprovalPr` (`packages/minspec/src/commands/commit-on-approve.ts:746`), which runs
   only after a push the user consented to under `minspec.pushOnApprove`: a click on the
   prompt, or the standing consent DR-071 and DR-078 define. `never`, or a declined prompt,
   reaches none of it (SPEC-050 INV-1 and AC-7).
3. **Only where the label has a consumer.** The approval caller opts in only when the PR
   carries the lane label, so SPEC-050 INV-2 has already judged it docs-only, AND the
   checkout carries `.github/workflows/docs-lane.yml` (`laneWorkflowPresent`,
   `commit-on-approve.ts:372`, applied at `:825`). A repository that never installed the
   lane gets no label. The check is a local file read, and any error answers "no".
4. **Only in the PR's own repository.** The same `cwd` and `slug` as the PR create, so gh
   resolves one base repository for both writes: DR-071 condition 3 (same-origin), and
   constitution invariant 3, since that repository carries `.minspec/` and MinSpec's own
   lane workflow.
5. **At most once per approval, and never silent.** One create, then one retry of the PR
   create through the same classifier as the first attempt (`attemptCreate`,
   `approval-pr.ts:870`), never a loop. Success appends `created the missing docs-lane
   label` to that approval's message (`commit-on-approve.ts:860`); failure names the label
   and says it could not be created (`:882`). A concurrent approval's "already exists" is
   treated as provisioned by someone else, and the retry proceeds (`createLaneLabel`,
   `approval-pr.ts:903`). This is DR-071 condition 5, and constitution invariant 2.
6. **Named where it is chosen, and switchable off.** The `minspec.approvalPr` setting's
   description names the label creation (DR-071 condition 2), and `manual` turns it off
   together with the automatic PR. SPEC-039's `MinSpec: Push Docs Lane` does not opt in;
   its classification is pinned by SPEC-050 AC-10, and #2257 tracks it.

**The consent question, answered.** Is consent to push an approval also consent to create
the label its pull request needs? Yes, for this one label under these six conditions, and
no further. SPEC-050 already rests on the reading that opening the PR for a consented push
"is the same authorized act completing, not a new boundary"
(`specs/minspec/SPEC-050-silent-approval-pr/requirements.md:62`, and INV-1). The label
create is a precondition of that same act in a repository that lacks the label. It is
fixed in shape, same-origin, started by the same keystroke, disclosed, and surfaced on
failure, which are DR-071's five conditions, and its only effect is to let the consented
PR be the PR FR-2 describes.

What it is not is a licence for repository configuration writes in general. A label is
repository configuration, not part of the PR: it outlives the PR and is visible to the
whole repository. That difference is why this is recorded here rather than folded silently
into INV-1, why the approval that makes the write says so, and why a second kind of
configuration write would need its own record.

**The shipped statement is narrowed, not dropped.** The `labels.md` template now says
MinSpec never creates, edits, or reads any of the vocabulary labels, and names `docs-lane`
as the single exception (`template-registry.ts:79-90`). The T0 scan in
`packages/minspec/tests/labels-template.test.ts` pins exactly one sanctioned call site (a
create of `DOCS_LANE_LABEL` in `lib/approval-pr.ts`), exactly one opt-in caller
(`commands/commit-on-approve.ts`), and this record as the site's decision.

## How this sits with SPEC-050's scope

The Architect is right that SPEC-050's approved requirements never mention creating the
label: they were written against this repository, which had one. It is also right that the
capability widens the forge-write surface. Two parts of the finding do not hold:

- **FR-4 ("No second `gh pr create` implementation") holds.** It governs the PR-opening
  path. The retry goes through the same `attemptCreate` classifier as the first attempt,
  and the label create lives in the seam (`approval-pr.ts`), not in a caller.
- **The `T3` in the parity test's header was the regression-test tier**, not the SDD
  ceremony tier. The test-tier scale is T0 invariant, T1 contract, T3 regression, and the
  headers now say which is meant. The ceremony tier of #2243 is T3 by its triage verdict,
  and it is met through the owning spec rather than a new one: this record is the
  decision, and SPEC-050's `design.md` and `tasks.md` gain the provisioning design, its
  tests and its task block.

**What is deliberately left undone is SPEC-050's `requirements.md`.** Its body is inside
the approval hash, because `packages/shared/src/canonical.ts:14-15` strips only `status:`
and `phases:`, so any edit voids the founder's 2026-08-12 approval and SPEC-050 would read
as unapproved on `main` until he re-approves it. DR-078 met the same cost for the same
kind of correction (its Consequences, first bullet) and set the precedent followed here:
until the requirements catch up, the decision record is the authority and the spec's text
is the stale artifact. The requirements-level wording (an FR-2 addendum, INV-1's footing,
and an acceptance criterion for the six conditions) is tracked in #2330, with a
recommendation to fold it in at the next re-approval SPEC-050 needs for any other reason.

## Alternatives rejected

1. **Document it:** a copy-paste `gh label create` in `labels.md` or the setup notes. That
   is a per-repository workaround, which #2243 rules out, and every adopter would meet the
   failure first, as voip-sms-inbox did.
2. **Create the label at scaffold time**, when Initialize or Refresh Harness Files writes
   the lane workflow. Scaffolding is Tier 0 and offline, with no consent moment for a
   network write (DR-050 condition 2). It would add a forge write to a command that makes
   none, and it would not reach adopters who scaffolded before this.
3. **Let a workflow provision it.** The lane workflow cannot, because it only runs on a PR
   already carrying its label. A new scheduled or on-push label-sync workflow would add a
   workflow and a write permission to every adopter to create one label, and would not
   help until it had run once.
4. **Key the lane on something other than a label**, such as the approval branch prefix
   or the PR title. That changes the lane's trigger contract in every adopter and here,
   and drops the label that is MinSpec's docs-only vouch (INV-2's first check). It is a
   larger machinery change that would need its own spec.
5. **Stop at naming the cause.** Keep the manual surface, but say the label is missing.
   Kept as the failure path, since the reason is now named; rejected as the whole fix,
   because the founder's report is that the manual step exists at all.

## Costly to Refactor

Low. The code reverts in under a day, and `minspec.approvalPr: manual` already switches it
off. The one thing a revert does not undo is labels already created in adopter
repositories; they are inert without the workflow and deletable in one command. The
commitment that costs most to walk back is the narrowed sentence in `labels.md`, which
ships into every adopter. A second exception must not arrive as a quiet edit, and the T0
pin turns an attempt into a failing test.

## Consequences

- Approvals land the same way in every adopter that carries the lane workflow, whether or
  not the label already existed. `approval-lane-label-parity.test.ts` runs both repository
  shapes through both push paths and asserts identical outcomes.
- The approval path now makes two kinds of forge write, the PR and, once per repository,
  the label, both behind the same push consent. This record is where a third would have to
  argue its case.
- A maintainer who wants the lane off must remove the workflow or set `approvalPr` to
  `manual`. Deleting only the label no longer disables it, because the next approval
  recreates it, and says so.
- The T0 scan now sees argv-form `gh` label calls, the form every `gh` call in this
  codebase uses, which it previously could not.

## Risks

- **Fork checkouts.** A fork may carry the workflow while its PR targets an upstream the
  contributor cannot write to. The create is refused, and the approval falls to the manual
  surface naming the label, so no write happens. Raised by the first Architect review of
  #2259; covered by the "cannot create" tests.
- **The gate reads a path, not a workflow.** `laneWorkflowPresent` checks that a file
  exists at MinSpec's scaffold path, not what it contains. An unrelated file at exactly that
  path would satisfy it; the write is still only MinSpec's own label, so the worst case is
  an unused label. Raised by the Reviewer on #2259.
- **A label deleted on purpose comes back.** See Consequences. It is disclosed each time,
  and `manual` is the off switch.
