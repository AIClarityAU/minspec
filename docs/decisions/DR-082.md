# DR-082: How agent GitHub writes get a bot identity

> **Born `proposed` per DR-029** — acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note.

## In plain terms — what this changes for you

Agent-run scripts no longer write to GitHub as you. Issues, comments, labels and merges
they make are recorded as `minspec-sdd[bot]`, so the audit trail stops attributing agent
work to a human — and GitHub stops subscribing you to every thread an agent opens.

If a script cannot get a bot identity, it stops rather than falling back to yours.

## Context

minspec#995 decided that agent GitHub writes must be bot-attributed. DR-074 decided
*where* that rule applies (only in repos with `.minspec/`). Neither recorded *how*, and
the how was left to prose in CLAUDE.md.

Prose did not hold. At the time #1355 was filed there were 76 write call sites across 11
paths in `scripts/`, and **not one** used the App token. Every agent-filed issue, comment,
label and merge was recorded as the founder. The notification flood was the visible
symptom; the audit trail lying about who acted was the actual defect.

This is the constitution's own diagnosis — a rule the model has to remember is a rule that
drifts — so the fix had to be a gate, not better prose.

Three properties were in tension:

1. **Coverage.** 76 call sites in a live, auto-merging pipeline. Rewriting each is a large
   diff with a large chance of breaking something mid-flight.
2. **Read-only paths must keep working with no credential.** Several of these files expose
   pure entry points and are sourced by tests as libraries. CI has no App key at all.
3. **Fail closed.** Constitution invariant 2: a missing witness must fail visibly, never
   best-effort. Falling back to ambient auth *is* the bug.

## Decision

**1. A shell function shadows `gh`, installed by `gh_bot_init`.**
Shell functions take precedence over PATH, so every existing `gh …` call routes through
the wrapper with no call-site edits — one source line per script instead of 76 rewrites.

**2. Acquisition is lazy: reads pass through, the first WRITE mints.**
This is a correctness requirement, not an optimisation. An earlier version exported
`GH_TOKEN` eagerly at source time and broke every read-only consumer — pure entry points,
source-text assertions, and a library sourced for its pure functions. It looked green
locally, because the dev container holds the App key, and failed 30+ tests under CI
conditions. `vitest.setup.ts` now pins credential state so a test result cannot depend on
which machine ran it.

**3. Unguessable input is refused, never guessed at.**
- A mint failure aborts loudly; there is no fallback to ambient auth.
- An inherited `GH_TOKEN` is verified. A bot login or a positively-identified 403
  (installation token, which has no user) is accepted; a human login is refused by name;
  an *unverifiable* probe is refused, because "not login-shaped" is not proof of anything.
- `gh api graphql` counts as a WRITE by default, because a document passed in a variable
  cannot be classified from argv. A genuine read declares itself with
  `gh_bot_graphql_read`.

**4. One write vocabulary, two consumers.**
The runtime predicate and the CI guard read the same `GH_BOT_WRITE_NOUNS` / `_VERBS` /
`_METHODS`. They were separate copies at first and disagreed three separate times — each
disagreement a hole where the runtime minted but the guard did not require attribution.

**5. `scripts/check-gh-bot-attribution.sh` gates merge.**
A file with a write must both source the helper *and* call `gh_bot_init` — both, because
the helper is inert until armed. Human-only scripts are allowlisted with a written reason,
printed on every run.

**6. `approve-issue.sh` is deliberately excluded.**
It is human-only by design: TTY-required, no `--yes`, and it refuses when the
authenticated identity is a bot. Its `APPROVER` *is* the authenticated human, so
attributing its writes to that human is correct. Converting it would break approval.

## Consequences

- Agent writes are recorded as `minspec-sdd[bot]`; the human is no longer auto-subscribed
  to threads an agent opens.
- A missing or broken App key **stops** an agent script at its first write. That is
  intended: half a run attributed to the human is worse than no run.
- Adding a `gh` write to a script now requires two lines and is enforced by CI.
- Dev-time only. Nothing here ships in the extension (DR-074 blast radius, invariant 3).
- The guard is textual, so it raises the floor rather than proving absence. Its limits are
  stated in its own header, and the subshell case is flagged rather than silently missed.

## Alternatives considered

**Edit all 76 call sites (`GH_TOKEN=… gh …`).** Rejected: a large diff across a live
auto-merging pipeline, and it decays — the 77th call site is written by someone who did
not read this.

**Export `GH_TOKEN` eagerly at source time.** Tried and reverted. It cannot distinguish a
read-only path, so it broke pure entry points and library sourcing, and it failed only
where the App key was absent — which is CI, not the author's machine.

**`export -f gh`, so the wrapper survives into child processes.** Rejected: it travels as
`BASH_FUNC_gh%%` into *every* descendant including the `claude -p` agents that are
credential-free by design (INV-5), and it is bash-only — a partial fix that reads as a
complete one. The subshell gap is flagged by the guard instead.

**Leave it as prose and rely on review.** This is what already existed, and it produced
zero compliance across 76 sites.

## Costly to Refactor

Low. The mechanism is one library plus one guard, and reverting is a single `git revert` —
the ADR filter would not have demanded this record on reversibility grounds alone. It is
written because the *policy* (agent identity, fail-closed credential handling) is
cross-cutting and touches invariant 2, and because minspec#995 and DR-074 between them
recorded the decision and its scope but never the mechanism.
